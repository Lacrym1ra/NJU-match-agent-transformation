## 2. AI 贡献分析（Q1）

- AI 在类图结构化、SOLID 原则分析、API 文档标准化和数据库规范化设计方面表现突出
- 通过“坏代码 → 好代码”的对比式教学，有效传达了设计模式和最佳实践
- 自动识别了初始设计中的缺陷（例如 God Object、臃肿接口），提升了设计质量
- 文档完整度覆盖 G2 的 Circle、Card、Friend、Contact Unlock、Teamup、实时聊天和通知相关接口/表，减少了团队重复工作

## 3. AI 误导性分析（Q2）



**最严重的设计问题：** AI 呈现出三类缺陷：

1. **SOLID 原则违反（8 项）：**
   - 单一职责原则（Single Responsibility Principle，S）：部分服务类承担了过多职责（God Object），例如混合业务逻辑、数据访问和日志记录
   - 接口隔离原则（Interface Segregation Principle，I）：接口定义过于宽泛，包含不必要的方法，迫使实现类依赖不需要的功能
   - 其他 4 项：开闭原则（Open-Closed Principle）2 项、依赖倒置（Dependency Inversion）2 项。里氏替换原则（Liskov Substitution Principle）未发现独立违反项。

2. **设计可行性问题（超出教学范围）：**
   - 假设存在完整的 OOP 继承层次和类层次设计，与轻量级教学项目风格不一致
   - 默认采用企业级基础设施（DI container、EventBus、CacheService、MessageQueue），在一个学期内实现和学习都有难度
   - 对进度约束（6 小时设计、后续开发工作量）和团队规模（3 个学生小组）考虑不足
   - 设计复杂度与教学目标和进度缺乏适当匹配

3. **ER 图格式不规范，缺乏详细设计信息：**
   - AI 初次生成的 ER 图**未严格遵循 Chen 氏 ER 图规范**，仅绘制了实体名（矩形）和联系（菱形/连线），完全缺失以下关键信息：
     - 实体的**属性定义**（如 `users` 表的 `email`、`nickname` 等字段）
     - **主键（PK）/ 外键（FK）标注**
     - 联系的**基数说明**（1:1、1:N、M:N）
     - 属性的**数据类型与约束**（如 `NOT NULL`、`UNIQUE`、`CHECK`）
   - 虽然 AI 绘制的实体关系连线基本正确，但由于缺乏属性和键信息，该 ER 图无法直接用于指导 DDL 编写，**实质上退化为一张"实体关系概览图"而非完整的 ER 图**
   - **人工决策与修正过程**：
     - 人工逐步为 20+ 张实体补充全部属性定义、数据类型、约束条件
     - 人工标注所有主键（PK）、外键（FK）、唯一约束（UK）
     - 人工补充 Mermaid `erDiagram` 语法中的属性块（如 `text id PK`、`text circle_id FK`）
     - 最终将 AI 的"骨架图"改造为符合学术规范的完整 ER 图，该部分工作约占 ER 图总工作量的 **60%**
   - **反思**：AI 对"ER 图"的理解偏向于高层关系概览，而非数据库课程要求的包含完整属性与约束的详细设计图。后续使用 AI 生成 ER 图时，需在 Prompt 中**明确要求包含所有属性、主外键标注和基数说明**




**关键影响：**
- SOLID 问题需要逐项调整类设计来修正，属于设计优化范围
- 设计范围问题需要重新定义，明确什么是“必须做”，什么是“未来可选扩展”
- ER 图格式问题导致大量返工，凸显了 AI 对学术规范理解的不足——AI 倾向于生成"够用"的简化版本，而课程要求的是完整、规范的设计文档
- 数据库审查发现的索引和范式问题表明：AI 能生成"可运行"的 DDL，但缺乏对**查询模式**和**数据完整性**的深度思考，需要人工进行专业审查与优化

## 4. Prompt（提示词）改进计划（Q3）

**上一阶段改进措施的验证：** 有效。具体验证如下：

1. **内容生成与格式化指令分离** — 上一阶段尝试了该措施；本阶段验证了其有效性。生成类图和 API 文档时，AI 先生成特定模块的核心内容，再用单独指令约束格式对齐，避免格式要求影响内容质量。

2. **上下文隔离** — 上一阶段建立了清晰的范围界定协议。本阶段使用了类似“仅关注 Circle 模块和接口定义”的隔离指令，防止 AI 自主扩展全局架构，确保每个小组设计的唯一性和具体性。

**本阶段新增改进措施：**

1. **跨文档命名一致性验证** — 为确保 API 字段、数据库 DDL 和类类型定义保持一致的命名约定（API/类中使用 camelCase，SQL 中使用 snake_case），团队进行了大量人工验证与同步。该细致验证约占设计工作的 20%，确保各层之间可以无缝集成。

2. **隐私感知的 API 错误响应** — 为敏感操作（加入 circle、contact unlock 请求）补充与隐私/权限相关的 HTTP 状态码（403 Forbidden），明确将 API 错误处理与 PrivacyEngine 设计逻辑关联起来。

3. **交付要求对照复核** — 按上传的 P3 详细设计要求，人工检查了以下方面：
   - API：统一 URL/method、请求参数、成功/失败响应、错误码；登录注册只保留跨组依赖说明
   - 数据库：补齐 PK/FK、关键字段、索引、3NF/性能说明和隐私字段处理
   - 安全与校验：标注 JWT、Zod schema、成员身份校验、联系方式加密、chat 房间权限
   - 设计模式：保留策略模式、状态机、数据访问边界、通知/实时广播等说明，并区分当前实现与未来演进

## 5. 本阶段核心工程决策

**决策内容：**
在三组分工的前提下，设计文档目标是“易于实现，眼光长远”。每个小组聚焦自身模块设计，同时通过统一的 API 和数据库标准进行协同。设计考虑包括：进度约束（6 小时）、人力成本（避免过度设计）、教学目标（标准化文档）。设计文档应反映理想化的架构思考，同时保持在可达范围内可实现，确保质量与时间线之间的平衡。

本次对齐后，G2 交付文档将实时聊天视为独立大功能：Circle Chat 与 Teamup Chat 都包含历史消息、发送、软删除、已读状态和 WebSocket room 广播。文档中的 Mermaid 图已按重制要求拆分为可审查的小图，并在 `docs/P3/g2/Mermaid图表源码汇总.md`、`docs/P3/g2/mermaid源码汇总/` 与 `docs/P3/g2/mermaid图像汇总/` 同时提供源码和生成图片；正文、API、SQL 和 Mermaid 图共同以当前代码为一致性准绳。

**为什么 AI 无法做出该决策：**
- AI 只能看到技术完美主义，无法理解团队分工结构、进度约束、人力成本等现实条件
- 无法在“高质量设计”与“有限时间线”之间平衡，需要人类基于实际工作量进行评估
- 决策涉及团队协作策略、教学目标、资源管理等超出纯技术范围的因素，超出了 AI 的能力范围
