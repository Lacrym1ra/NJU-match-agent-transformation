## 2. AI 助力分析（Q1）

AI 在本阶段最有帮助的地方是快速把零散材料组织成 P3 要求的交付结构。第一组的内容分散在 `API_SPEC.md`、`GROUP_RESPONSIBILITIES.md`、`MESSAGE_CENTER_DESIGN.md` 和后端路由文件中，如果完全人工整理，容易漏掉“已实现”和“设计已定”的状态差异。

AI 帮助我们完成了三类工作：

1. 把当前代码中的函数式模块翻译成课程要求的 UML 类图表达。
2. 把接口按认证、用户、问卷、匹配、消息中心重新分组。
3. 用 SOLID 的检查框架发现初稿中“用户匹配管理器”职责过重的问题。

但最终文档不能直接照搬 AI 初稿，必须人工对照真实仓库。比如 `/api/v1/notifications` 当前未注册，而 `/api/v1/user/notifications` 只是邮件提醒开关，这个差异如果不人工校准，会导致文档和联调不一致。

## 3. AI 误导分析（Q2）

SOLID 检查中发现的 AI 设计问题数量：8

最严重的设计问题是：AI 倾向于把认证、资料、问卷、匹配算法、通知、注销全部放到一个 `UserMatchManager` 中，形成 God Object。

具体误导：

| 问题 | 影响 | 修正 |
|---|---|---|
| 把邮件和站内消息都继承自 `Notification` | 邮件没有已读状态，继承关系不成立 | 拆成 `mail_logs` 和 `notifications` |
| 把匹配算法写死在 `MatchService` | 后续调整权重和算法困难 | 拆分为候选池、dealbreaker、评分、配对策略 |
| 把 `/user/notifications` 当站内消息 | 与当前代码不一致 | 明确其为邮件偏好，站内消息为 `/notifications` |
| 泛化课程“订单/评价”概念 | 与本项目第一组主线不贴合 | 用匹配双选结果和历史记录表达主流程闭环 |

## 4. Prompt 改进计划（Q3）

上阶段改进措施的验证结果：

本阶段在 Prompt 中加入“必须对照当前仓库代码和分组职责文档”，显著降低了 AI 乱造接口的比例。AI 初稿仍会补充一些标准化设计，但通过人工标注“已实现 / 设计已定”后，文档可用性更高。

本阶段新的改进措施：

1. 生成设计文档前，先要求 AI 列出它依据的文件和实现状态。
2. 对每个 API 强制标注 `已实现`、`设计已定` 或 `预留`。
3. 对类图要求说明“逻辑类图如何映射到当前函数式 TypeScript 实现”。
4. 对数据库要求从迁移 SQL 反推，不允许只凭业务想象建表。
5. 对跨组模块要求写清楚主责边界，避免把 g2/g3 的功能写进 g1。

## 5. 本阶段的核心工程判断

决策内容：

第一组 P3 文档不按传统“需求发布 / 接单 / 订单 / 评价”强行套模板，而是围绕本项目真实主线定义为“注册 - 建档 - 问卷 - 主匹配 - 揭晓 - 历史 - 通知”。其中站内消息中心作为设计已定能力纳入，但明确当前尚未注册路由。

为什么 AI 无法做这个决策：

AI 容易按照课程模板机械补齐通用校园互助平台接口，或者把其他组的论坛、圈子、治理能力合并进第一组。这个取舍需要理解项目真实分工、当前代码状态和答辩时的验收边界，属于团队层面的工程判断，而不是单纯文本生成。
