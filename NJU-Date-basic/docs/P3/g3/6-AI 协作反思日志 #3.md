## 2. AI 助力分析（Q1）

本阶段 AI 最大价值在于“快速结构化产出 + 与代码现状对齐迭代”。

具体体现：
- 能快速把分散要求（类图、SOLID、API、ER）组织成完整文档结构，明显降低文档拼装成本。
- 对“关系/约束/边界”类内容输出速度快，尤其在ER关系、API参数表、错误码表等模块化内容上效率高。
- 在明确“只写论坛与治理”后，AI 能较快收敛文档边界，减少圈子、组队、好友等非本组内容混入。
- 对已实现接口进行列表化整理时效率较高，便于后续人工逐项核对 `routes/forum.ts`、`routes/admin.ts`、`schema.ts`。

对团队效率的实际帮助：
- 让成员把更多时间用于“验边界、验事实、验可落地性”，而不是从零排版写文档。
- 提高了交付一致性：类图、API、数据库、整合文档之间术语和状态更统一。
- 对信用分、论坛举报、公告、留言板等新增能力，可以快速同步到多份文档中，减少遗漏。

## 3. AI 误导分析（Q2）

SOLID 检查中发现的 AI 设计问题数量：**5（S/O/L/I/D 各1项）**

最严重的设计问题是：
- **单一职责与依赖倒置同时失效**。AI初稿把论坛、举报、拉黑、审计、信用分、公告、留言板等全部塞进单个大类，并直接依赖 ORM 细节，导致扩展困难、测试困难、维护风险高。

本阶段出现的典型误导：
- 边界漂移：把组队主流程、圈子主流程等非本组内容带入API文档。
- 现实脱节：容易把早期接口状态当作当前事实。如果不核对 `index.ts`、`routes/forum.ts` 和 `admin.ts`，会保留不可联调之类过期判断。
- 实现夸大：设计稿中提到的 Repository、内容审核策略类并未完全独立落地，必须标注为演进方向，而不是已完成。
- 字段遗漏：旧版本只覆盖 `forum_posts`、`forum_comments`、`user_reports` 等基础表，遗漏当前已实现的论坛互动、论坛举报、信用分日志、公告与留言板表。

## 4. Prompt 改进计划（Q3）

上阶段改进措施的验证结果：
- “先声明边界再生成”有效，越界内容明显减少。
- “要求标注已实现/演进”有效，降低文档与代码不一致风险。
- “先证据后结论”有效，能及时发现 `/api/v1/forum` 已挂载、管理端论坛接口已开放等状态变化。

本阶段新的改进措施：
1. 在 Prompt 开头固定三段：`责任边界`、`当前代码基线`、`禁止扩展范围`。
2. 明确要求输出中加入“实现状态标签”：`已实现` / `演进方向` / `兼容字段`。
3. 对关键事实强制引用文件锚点（例如：`routes/*.ts`、`services/*.ts`、`index.ts`、`schema.ts`），先证据后结论。
4. 对“整合文档”任务增加一致性检查要求：术语、枚举、状态在 1~5 文档间保持一致。
5. 对涉及信用分、举报审核、软删除的内容增加事务和幂等检查，避免只写流程不写约束。

## 5. 本阶段的核心工程判断

决策内容：
- 详细设计文档采用“**双层表达**”：
  - 第一层：当前可联调能力（真实已实现）。
  - 第二层：架构演进能力（已设计但未完全独立抽象）。

为什么 AI 无法做这个决策：
- 该决策依赖团队对“课程验收”与“真实可交付风险”的平衡判断，不只是文本生成。
- AI可总结文档，但不能天然判断“老师验收关注点”与“当前工程真实状态”之间的权衡。
- 需要人来拍板：哪些内容必须写成“已实现”，哪些必须明确写“演进方向”，以避免交付误导。

本阶段落地判断：
- `/api/v1/forum` 已挂载，论坛基础链路与增强链路应写成已实现。
- 管理端 `/admin/forum/*` 已存在，帖子治理、论坛举报、信用用户、公告和留言板管理应写成已实现。
- Repository、独立 `CreditService`、独立 `ContentModerationService` 仍应写成演进方向。
- 圈子和组队主流程不属于本组范围；`circleId` 和 `squad` 仅作为兼容字段或普通标签说明。

---

## 本阶段总结

我们把 AI 当作“高效初稿与结构化助手”，而不是“事实来源本身”。

真正提升质量的关键是：
- 先定边界，再生成。
- 生成后必须回到代码做事实核对。
- 对高风险内容（接口可用性、信用分扣减、审核状态、软删除、审计）坚持人工最终裁决。
- 文档必须跟随当前项目文件更新，不能停留在早期设计状态。

## 7. 文档完善策略

本次文档完善不改变原有标题和主要内容，只在现有结构后追加补充说明：
- 类图文档追加类模型概览、详细类定义、关系总结与质量属性。
- SOLID 文档追加五项原则详细分析、违反统计、架构评价。
- API 文档追加端点总览、分页/幂等/权限/错误响应和流程串联。
- ER/SQL 文档追加设计决策、迁移说明、性能考虑和数据保留策略。
- 详细设计文档追加服务设计、关键业务流程、测试验收和质量路线。

追加原则：
- 只写 g3 的论坛与治理范围。
- 不把圈子主流程、组队主流程、好友/联系方式解锁迁入 g3 文档。
- 对设计抽象和当前代码实现做区分。
- 高风险事实以代码文件为依据。

## 8. 风险复盘

| 风险 | 表现 | 规避方式 |
|---|---|---|
| 范围越界 | 把 g2 的圈子、好友、联系方式、组队主流程写入 g3 | 只保留论坛与治理，`squad` 仅作为帖子标签 |
| 状态过期 | 保留早期接口状态 | 每次更新前核对 `index.ts` 和路由文件 |
| 实现夸大 | 把 Repository、独立 CreditService 写成已落地 | 标注为设计抽象或演进方向 |
| 表结构遗漏 | 漏写互动表、论坛举报表、信用日志表 | 以 `schema.ts` 为准补充 |
| 治理链路不闭环 | 只写举报，不写审核、扣分、审计 | 按“举报 -> 审核 -> 内容处置 -> 扣分 -> 审计”描述 |
