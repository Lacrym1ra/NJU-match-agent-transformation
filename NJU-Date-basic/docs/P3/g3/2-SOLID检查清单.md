# 关键实验：“AI 设计缺陷注入”

## AI 原始设计
AI 初稿把“论坛 + 举报 + 拉黑 + 审计 + 信用分 + 公告 + 留言板 + 组队同步”全部塞进 `ForumManager` 单类，并直接依赖 Drizzle 表对象。

补充观察：若继续把草稿、评论置顶、帖内投票、推荐排序和私信也塞入该单类，会进一步形成“内容 + 互动 + 推荐 + 社交沟通 + 治理”的超级对象。

## SOLID 检查清单

| SOLID 原则 | 检查问题 | AI 设计是否违反 | 违反说明 | 修正方案 |
|-----------|---------|--------------|---------|---------|
| S - 单一职责 | 有没有类承担了过多职责？ | 是 | `ForumManager` 同时处理发帖、评论、互动、举报、扣分、审计、公告、留言板 | 拆分为 `ForumService` / `ForumGovernanceService` / `GovernanceService` / `CreditService` / `AuditService` |
| O - 开闭原则 | 新增需求类型是否需要修改现有代码？ | 是 | 新增举报处置、信用规则、公告管理策略时需反复改同一个大类 | 抽象治理服务和信用服务，把易变规则从论坛主流程中分离 |
| L - 里氏替换 | 子类是否可以替换父类使用？ | 否（无继承抽象） | 初稿未抽象仓储接口，无法替换数据实现或 mock | 引入 `IPostRepository`、`ICommentRepository`、`IForumReportRepository` 等接口 |
| I - 接口隔离 | 有没有接口太“胖”，包含了不需要的方法？ | 是 | 一个服务接口暴露帖子、评论、点赞、举报、扣分、审计、公告等跨域方法 | 拆为论坛读写、互动、治理、信用、审计等细粒度接口 |
| D - 依赖倒转 | 高层模块是否直接依赖低层具体实现？ | 是 | Controller/Service 直接依赖 ORM 表查询细节，业务规则与 SQL 混杂 | 通过 Repository 抽象反转依赖，并将信用分与审计写入聚合到专门服务 |

新增能力复核：
- 草稿：属于前端编辑体验，不应进入 `ForumService` 后端状态机。
- 评论置顶与帖内投票：属于论坛互动扩展，可由 `ForumService` 编排，但数据访问应下沉到评论/投票仓储。
- 推荐排序：属于可替换算法策略，应抽象为推荐服务或内部策略函数，避免与基础列表查询强耦合。
- 私信：属于社交沟通域，应拆入 `SocialService`，不能并入论坛帖子服务。

## 记录
- AI 原始设计违反 SOLID：**4 处明显问题（S/O/I/D）+ 1 处抽象缺失（L）**。
- 主要修正：**服务职责拆分 + Repository 接口层 + 治理/信用独立服务 + 策略化内容审核点**。
- 补充修正：推荐排序和私信继续做边界隔离，避免论坛主服务变成新的大类。
- 当前代码已落地 `ForumService` 和 `ForumGovernanceService`，治理链路、信用分日志和审计链路已可在代码中定位；Repository 接口层仍属于后续演进方向。

## 设计模式应用

### 模式 1：Repository 模式
- 使用位置：`IPostRepository` / `ICommentRepository` / `IForumReportRepository` / `IUserReportRepository` / `ICreditLogRepository` / `IAuditRepository`。
- 使用原因：把业务逻辑从 Drizzle SQL 细节中解耦，方便单测与后续替换持久层。
- 不使用后果：Service 与 SQL 强耦合，重构成本高，难以做稳定的 mock 测试。

### 模式 2：策略模式
- 使用位置：`ContentModerationService.decide(hitTerms)` 与举报审核处置规则（通过/驳回、帖子/评论不同处置、1/3/5 扣分档）。
- 补充使用位置：推荐排序中的画像匹配、互动亲和、协同过滤、新鲜度和质量分可作为可替换评分策略；私信资格判断中的 `all/following/mutual/none` 也可作为隐私策略。
- 使用原因：敏感词处置、举报等级、信用分阈值等规则可扩展，后续新增风险级别不破坏主流程。
- 不使用后果：审核逻辑散落在发帖、评论、举报审核多个入口，规则分叉且难审计。

### 模式 3：门面模式
- 使用位置：`ForumGovernanceService` 作为论坛举报提交、审核、违规内容软删除、信用分扣减的统一门面；`GovernanceService` 作为用户举报和拉黑能力的统一入口。
- 补充使用位置：`SocialService` 作为关注、私信隐私、会话创建和消息发送的统一门面，避免 Controller 直接编排关注表、拉黑表和私信表。
- 使用原因：为 Controller 提供稳定入口，降低接口层认知负担，并保证“审核通过 -> 内容处置 -> 扣分 -> 日志”在同一事务语义中完成。
- 不使用后果：Controller 直接编排多个底层对象，重复逻辑增加，扣分和审计一致性难以保证。

## 3. 详细分析：5 项 SOLID 原则

### 3.1 单一职责原则（SRP）

原则定义：
- 一个类或模块只应有一个主要变化原因。

设计验证：
- `ForumService` 的变化原因是论坛内容与互动规则变化。
- `ForumRecommendationService` 的变化原因是推荐排序因子、权重和候选集策略变化。
- `SocialService` 的变化原因是关注关系、私信资格和会话读写规则变化。
- `ForumGovernanceService` 的变化原因是论坛举报审核与违规处置规则变化。
- `GovernanceService` 的变化原因是用户维度举报与拉黑规则变化。
- `CreditService` 的变化原因是信用分阈值、扣分、恢复策略变化。
- `AuditService` 的变化原因是审计记录格式与落库策略变化。

初始问题：
- `ForumManager` 同时处理内容、互动、治理、信用、审计，任一规则变化都要修改同一类。

修正结果：
- 将论坛主流程与治理流程拆开，使“发帖规则变化”和“审核扣分规则变化”不互相污染。
- 将推荐算法和私信能力视为独立变化方向，避免它们与发帖、评论、举报主流程互相污染。

结论：
- 设计层满足 SRP；当前代码中 `forumService.ts` 仍承担较多查询与互动编排，是后续可拆分点。

### 3.2 开闭原则（OCP）

原则定义：
- 对扩展开放，对修改关闭。

设计验证：
- 帖子类型通过 `ForumPostType` 扩展。
- 举报状态通过 `ForumReportStatus` 与审核动作扩展。
- 信用分扣分等级通过治理策略扩展。
- 内容审核策略通过 `ContentModerationService` 扩展。
- 推荐排序通过推荐评分策略扩展，不要求修改论坛基础列表接口。
- 私信隐私规则通过资格判断策略扩展，不要求修改论坛帖子或评论模型。
- 投票选项数量、投票权限和评论置顶权限可通过 `ForumPolicyService` 扩展。

初始问题：
- 举报原因、扣分等级、内容处置策略写死在单一大类中，新增规则会修改主流程。

修正结果：
- 将易变规则放入策略服务和治理门面，主流程只调用稳定入口。

结论：
- 设计上满足 OCP；当前实现中部分规则仍在服务函数内，后续可继续策略化。
- 补充结论：推荐权重、投票权限和私信隐私判断是后续优先策略化的扩展点。

### 3.3 里氏替换原则（LSP）

原则定义：
- 子类型或实现类应能替换其抽象接口使用。

设计验证：
- `DrizzlePostRepository` 可替换 `IPostRepository`。
- `DrizzleCommentRepository` 可替换 `ICommentRepository`。
- `DrizzleForumReportRepository` 可替换 `IForumReportRepository`。
- 审计、信用日志、通知仓储均可通过接口替换具体存储。
- 投票仓储、关注仓储、私信仓储可分别替换为 mock 或其他持久化实现。

初始问题：
- 初稿没有仓储抽象，服务层直接依赖 Drizzle 表对象，不存在可替换边界。

修正结果：
- 通过接口定义替换点，让测试 mock 和未来持久层替换有设计入口。

结论：
- 详细设计满足 LSP；实际代码中的 Repository 抽象尚未完全落地。

### 3.4 接口隔离原则（ISP）

原则定义：
- 客户端不应依赖它不使用的方法。

设计验证：
- 发帖列表依赖 `IPostRepository`，不需要依赖举报审核方法。
- 评论树依赖 `ICommentRepository`，不需要依赖信用分方法。
- 投票提交依赖 `IForumPollRepository`，不需要依赖公告、留言板或私信方法。
- 私信发送依赖 `IDirectMessageRepository` 和用户关系判断，不需要依赖帖子查询方法。
- 论坛举报依赖 `IForumReportRepository`，不需要依赖用户举报仓储。
- 信用分日志依赖 `ICreditLogRepository`，不需要依赖帖子查询。

初始问题：
- 单一 `ForumManager` 暴露帖子、评论、点赞、举报、扣分、审计、公告等方法，调用方被迫依赖过胖接口。

修正结果：
- 按职责拆分服务和仓储接口。

结论：
- 设计满足 ISP，并降低后续联调时的接口认知成本。

### 3.5 依赖倒置原则（DIP）

原则定义：
- 高层业务模块不应依赖低层实现细节，二者都应依赖抽象。

设计验证：
- Controller 依赖 Service 抽象职责。
- Service 设计上依赖 Repository、Audit、Credit 等抽象入口。
- Drizzle 查询细节被规划到 Repository 实现层。
- 推荐排序高层逻辑依赖评分策略和候选集抽象，不应直接散落在路由层。
- 私信资格判断依赖关注/拉黑/隐私仓储抽象，不应由 Controller 拼接 SQL。

初始问题：
- 初稿中业务流程直接写 SQL/ORM 查询，导致业务规则和持久化规则紧耦合。

修正结果：
- 引入 Repository 设计契约，并将审计与信用分写入抽象为独立服务。

结论：
- 设计满足 DIP；当前代码可按演进计划逐步减少 service 内直接查询。

## 4. 违反问题统计与修正

| 问题类别 | 初始违反点 | 影响 | 修正状态 |
|---|---|---|---|
| God Object | `ForumManager` 聚合所有职责 | 难维护、难测试 | 已拆分职责 |
| ORM 直连 | 业务层直接依赖 Drizzle 表 | 难替换、难 mock | 设计层引入 Repository |
| 接口过胖 | 单接口包含跨域方法 | 调用方依赖过多 | 拆分细粒度接口 |
| 策略硬编码 | 扣分与审核规则散落 | 新规则修改主流程 | 引入策略/门面 |
| 审计分散 | 审计由多个入口随意写 | 追溯不一致 | 统一审计抽象 |
| 推荐耦合 | 推荐权重写死在列表路由 | 调整排序影响基础列表 | 抽象推荐策略 |
| 社交越界 | 私信混入论坛服务 | 职责混淆、权限难测 | 拆出 `SocialService` |

- [x] 论坛主流程与治理流程拆分。
- [x] 用户举报与论坛内容举报区分。
- [x] 信用分变化独立为日志实体。
- [x] 审计日志作为治理关键动作的统一记录。
- [x] 类图中标注关联、聚合、组合和接口实现关系。
- [x] 评论置顶、帖内投票、推荐排序归入论坛扩展职责。
- [x] 关注与私信归入社交服务职责，不混入论坛聚合根。
- [ ] Repository 抽象在代码层完全落地。
- [ ] 内容审核策略类在代码层完全独立。
- [ ] 推荐排序策略在代码层完全独立。
- [ ] 私信反垃圾与敏感词策略在代码层完全独立。

## 5. 架构师评价

总体评价：
- 当前设计能覆盖 g3 的 P0 范围，并且把论坛内容流转和平台治理流转分开表达。

关键亮点：
- 论坛举报与用户举报分离，避免目标类型和审核规则混淆。
- 论坛举报审核通过后，内容处置、扣分、日志形成闭环。
- 信用分限制由后端执行，前端提示不作为安全边界。

改进方向：
- 将 `ForumService` 中互动、消息、公告相关函数继续按子服务拆分。
- 将推荐排序从 `ForumService` 中继续抽象为可测试的 `ForumRecommendationService`。
- 将私信限流、隐私策略和拉黑判断整理为 `SocialPolicyService`。
- 将信用分恢复、扣分、等级判断集中到独立 `CreditService`。
- 为举报审核事务补充更细的自动化回归测试。

## 6. 最佳实践总结

- 高风险治理逻辑必须有审计日志。
- 信用分变化必须有来源工单或来源动作。
- 论坛删除采用软删除，避免破坏审计追溯。
- 对用户可见的私密内容必须以服务端权限判断为准。
- 推荐流、热榜和私信入口都不能绕过服务端可见性、拉黑和隐私判断。
- 草稿只保存未发布编辑状态，不进入后端治理与审计范围。
- 设计文档中可以使用类图表达职责，但应说明当前 TypeScript 项目以函数式模块实现。
