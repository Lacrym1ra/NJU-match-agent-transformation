# Phase 1 交付物 04：需求规格说明书

## 1. 引言

### 1.1 目的

本文档定义 `NJU-Match` 的校园交友匹配主线需求，为后续设计、开发、测试和验收提供统一依据。

### 1.2 范围

本文档覆盖以下模块：

1. 校园邮箱注册、登录与密码重置
2. 用户档案建立与动态画像
3. 主问卷获取、提交与锁定管理
4. 每周匹配、揭晓、双向选择与历史记录
5. 用户侧的隐私边界与失败反馈

以下扩展能力不在本文档范围内：

1. 即时聊天
2. 公开内容社区
3. 校园互助接单与交易体系

### 1.3 术语

| 术语 | 含义 |
|------|------|
| 平台 | 本项目 `NJU-Match` |
| 用户 | 已注册的南京大学在校生 |

## 2. 总体描述

### 2.1 产品视角

本模块本质上是一个面向校内用户的低压力匹配流程：

1. 用户使用校园邮箱注册并登录。
2. 用户完成基础档案和主问卷。
3. 系统按周生成匹配结果。
4. 在揭晓时间后，用户查看结果并做出“愿见”或“止步”选择。
5. 只有在双向成功后，系统才展示联系方式。

### 2.2 用户特征

根据调研结果，目标用户具有以下特征：

1. 对认识新朋友和低压力社交有一定兴趣，但未必接受强恋爱导向。
2. 非常重视资料真实性、身份认证和隐私安全。
3. 更接受按周节奏的少量高质量推荐，而不是高频刷人。
4. 希望未匹配成功时得到清晰、温和且可执行的反馈。

### 2.3 约束

1. 平台仅面向南京大学在校生。
2. 联系方式不得在双向成功前暴露。
3. 本阶段需求需服从课程项目的时间与实现范围。

### 2.4 假设与依赖

1. 用户可以使用 `@smail.nju.edu.cn` 邮箱接收验证码。
2. 系统具备按周调度匹配任务的能力。
3. 用户愿意投入 5 至 10 分钟填写主问卷。
4. 动态画像上传为可选功能，不作为参与匹配的强制前置条件。

## 3. 功能需求

### 3.1 认证与账户

#### FR-01 发送邮箱验证码

- 描述：系统应支持向 `@smail.nju.edu.cn` 邮箱发送注册验证码和重置密码验证码。
- 来源：`[AI生成+人工修改]`
- 修改说明：人工补充了“仅限校内邮箱”的边界。
- 优先级：Must

#### FR-02 用户注册

- 描述：系统应支持用户使用邮箱、验证码和密码完成注册。
- 来源：`[AI生成+人工修改]`
- 修改说明：人工补充了验证码校验与账号创建的闭环要求。
- 优先级：Must

#### FR-03 用户登录

- 描述：系统应支持用户使用邮箱和密码登录，并返回后续请求所需的认证凭证。
- 来源：`[AI生成]`
- 优先级：Must

#### FR-04 重置密码

- 描述：系统应支持用户通过邮箱验证码重置密码。
- 来源：`[AI生成+人工修改]`
- 修改说明：人工补充了统一提示以避免邮箱枚举风险。
- 优先级：Should

### 3.2 用户档案与动态画像

#### FR-05 获取个人档案

- 描述：系统应支持登录用户获取自己的基础档案信息。
- 来源：`[AI生成]`
- 优先级：Must

#### FR-06 更新个人档案

- 描述：系统应支持用户更新昵称、性别、年级、院系、校区、匹配意向等基础资料。
- 来源：`[AI生成+人工修改]`
- 修改说明：人工将字段范围收敛为第一组匹配主线需要的信息。
- 优先级：Must

#### FR-07 Onboarding 草稿保存

- 描述：系统应支持用户在首次建档过程中分步保存草稿。
- 来源：`[人工补充]`
- 优先级：Must

#### FR-08 档案完成度校验

- 描述：系统应在用户提交 Onboarding 时校验必填项是否完整，并标记档案完成状态。
- 来源：`[AI生成+人工修改]`
- 修改说明：人工补充了“完成度”这一可测试状态。
- 优先级：Must

#### FR-09 动态画像上传

- 描述：系统应支持用户自愿上传生活事件，用于补充动态画像信息。
- 来源：`[人工补充]`
- 优先级：Could

#### FR-10 动态画像可控性

- 描述：系统应允许用户自主决定是否上传、修改或删除动态画像内容。
- 来源：`[人工补充]`
- 优先级：Should

### 3.3 主问卷

#### FR-11 获取主问卷

- 描述：系统应支持前端获取当前主问卷题目和问卷版本信息。
- 来源：`[AI生成]`
- 优先级：Must

#### FR-12 提交主问卷

- 描述：系统应支持登录用户提交主问卷答案，并保存与当前版本的关联关系。
- 来源：`[AI生成+人工修改]`
- 修改说明：人工补充了问卷版本关联要求。
- 优先级：Must

#### FR-13 读取已提交答案

- 描述：系统应支持用户查看当前已保存的主问卷答案。
- 来源：`[AI生成]`
- 优先级：Should

#### FR-14 匹配锁定期限制提交

- 描述：系统应在匹配锁定窗口内阻止用户修改主问卷。
- 来源：`[人工补充]`
- 优先级：Must

### 3.4 主匹配与揭晓

#### FR-15 参与资格校验

- 描述：系统应在执行匹配前校验用户是否已完成档案、完成主问卷并处于可参与状态。
- 来源：`[AI生成+人工修改]`
- 修改说明：人工补充了档案完成与状态校验条件。
- 优先级：Must

#### FR-16 本周暂停参与

- 描述：系统应支持用户暂停本周参与匹配，并在后续周期恢复可参与状态。
- 来源：`[人工补充]`
- 优先级：Should

#### FR-17 每周匹配计算

- 描述：系统应支持按周执行主匹配计算并生成本周匹配记录。
- 来源：`[AI生成+人工修改]`
- 修改说明：人工明确了“按周运行”的节奏约束。
- 优先级：Must

#### FR-18 当前状态查询

- 描述：系统应支持返回当前用户本周的匹配状态，如 `WAITING`、`REVEALED`、`NO_MATCH`、`EXPIRED` 等。
- 来源：`[人工补充]`
- 优先级：Must

#### FR-19 匹配结果揭晓

- 描述：系统应支持在揭晓时间后向用户展示本周匹配对象的脱敏信息与匹配解释。
- 来源：`[AI生成+人工修改]`
- 修改说明：人工补充了揭晓时间和脱敏展示要求。
- 优先级：Must

#### FR-20 提交愿见/止步

- 描述：系统应支持用户对本周匹配结果做出“愿见”或“止步”选择，且每期只能提交一次。
- 来源：`[AI生成+人工修改]`
- 修改说明：人工补充了“单次提交”这一约束。
- 优先级：Must

#### FR-21 双向成功后展示联系方式

- 描述：系统仅在双方都选择“愿见”后才展示联系方式。
- 来源：`[人工补充]`
- 优先级：Must

#### FR-22 匹配失败反馈

- 描述：系统应在未匹配成功时提供明确反馈，并可提示用户等待下周或完善资料。
- 来源：`[人工补充]`
- 优先级：Must

#### FR-23 历史匹配查询

- 描述：系统应支持用户分页查询历史匹配记录。
- 来源：`[AI生成]`
- 优先级：Should

### 3.5 隐私与安全边界

#### FR-24 默认脱敏展示

- 描述：系统在非双向成功场景下应只展示脱敏后的个人资料。
- 来源：`[人工补充]`
- 优先级：Must

#### FR-25 非法访问拦截

- 描述：系统应拒绝用户访问不属于自己的匹配结果或历史记录。
- 来源：`[AI生成+人工修改]`
- 修改说明：人工将访问控制明确为可测试规则。
- 优先级：Must

## 4. 非功能需求

### 4.1 安全性

1. 非登录状态不得访问用户档案、问卷答案和匹配结果。
2. 联系方式在双向成功前不得返回给任一用户。
3. 系统应对关键输入执行基础校验和错误处理。

### 4.2 可用性

1. 用户应能在较短流程内完成注册、建档和问卷填写。
2. 系统应明确展示当前状态，避免用户不知道下一步做什么。
3. 失败反馈应清晰、直接且可理解。

### 4.3 性能

1. 常规档案、问卷和状态查询接口应在课程项目规模下保持可接受响应时间。
2. 周期性匹配任务应能在一个批次中完成结果生成。

### 4.4 可维护性

1. 问卷版本应支持迭代。
2. 匹配状态应以统一状态字段维护。
3. 需求、用例和用户故事应能相互追踪。
