# 圈子与关系链模块 - 用户故事库

> 本文档包含校园社交与互助平台"第二组：圈子与关系链组"模块的完整用户故事库，共 31 条故事，使用 MoSCoW 优先级排序，每条故事均包含可测试的具体验收标准。

---

## 一、用户故事编写规范

### 1.1 故事格式

所有用户故事严格遵循以下格式：

```
作为 [角色]，我希望 [具体功能]，以便 [业务价值]

验收标准：
□ 条件1：[具体测试场景和预期结果]
□ 条件2：[具体测试场景和预期结果]
□ 条件3：[边缘情况或异常场景]
```

### 1.2 MoSCoW 优先级定义

| 优先级 | 含义 | 包含范围 |
|:---:|:---|:---|
| **Must** | 必须实现 | P0 核心功能，影响产品可用性 |
| **Should** | 应该实现 | P1 重要功能，提升用户体验 |
| **Could** | 可以实现 | P2 扩展功能，增加系统完整度 |
| **Won't** | 暂不实现 | 未来规划，放入产品路线图 |

### Story 1：用户浏览圈子发现页面 🔴

**用户故事：**
作为 **普通学生**，我希望 **在首页能看到系统推荐的圈子列表和搜索功能**，以便 **快速发现感兴趣的圈子并加入社交网络**。

**验收标准：**
- ✓ 首页展示推荐圈子列表，系统基于用户院系、年级和已选兴趣标签优先展示匹配度高的圈子，如果无匹配则按活跃度（成员数/发帖数）倒序推荐
- ✓ 圈子卡片展示圈子名称、简介摘要、成员数、圈主昵称及圈子标签
- ✓ 页面顶部提供搜索框，支持通过圈子名称或标签进行模糊匹配搜索
- ✓ 当搜索结果为空时，显示「未找到相关圈子，你可以尝试更换关键词，或者去创建属于自己的圈子」提示
- ✓ 分页加载：支持下拉加载更多推荐列表，每次最多加载 20 个圈子

### Story 2：圈主创建新圈子 🔴

**用户故事：**
作为 **普通学生（具有创建权限）**，我希望 **能创建属于自己的圈子，设置圈子信息和加入规则**，以便 **建立志同道合的用户社群**。

**验收标准：**
- ✓ 「创建圈子」表单包含必填字段：圈子名称（1-30字）、简介（1-200字）、圈子标签（至少1个，最多5个）、加入权限设置（公开/需审核/私密）
- ✓ 内容安全：提交时系统自动检测名称、简介和标签是否包含敏感/违规词汇，若包含则拦截并提示「包含敏感内容，请修改后提交」
- ✓ 唯一性限制：若创建同名圈子，系统阻止并提示「该圈子名称已被占用，请选择其他名称」
- ✓ 容量限制：单个用户最多只能创建 5 个圈子，超过则提示「已达到创建上限，不能创建更多圈子」
- ✓ 创建成功后自动在数据库生成唯一 ID，创建者成为圈主，页面跳转到管理页并显示「创建成功」的激励提示

### Story 3：圈主设置圈子加入权限 🔴

**用户故事：**
作为 **圈主**，我希望 **能灵活控制谁可以加入我的圈子，以及如何设置加入条件**，以便 **有效管理圈子成员质量和隐私保护**。

**验收标准：**
- ✓ 圈子权限设置页面显示三种选项：「完全公开」（任何人点击即可加入）、「需审核」（申请者需圈主批准）、「私密」（需圈主邀请）
- ✓ 修改权限后实时生效，已有成员不受影响，新的加入行为按新权限执行
- ✓ 若切换为「需审核」，系统自动将过期未处理的申请设为「已截断」，不再接收新申请
- ✓ 权限修改操作被记录在审计日志中，包含修改时间、修改内容、修改者信息

### Story 4：用户申请加入需审核的私密圈子 🔴

**用户故事：**
作为 **普通学生**，我希望 **能向私密圈子提出加入申请，并等待圈主的审核**，以便 **请求加入感兴趣但需要审批的圈子**。

**验收标准：**
- ✓ 在私密或需审核圈子详情页中，「加入」按钮替换为「申请加入」，点击弹出申请表单，包含必填字段「申请理由」（最多 300 字）
- ✓ 内容安全：提交时系统自动检测申请理由是否包含敏感违规词汇，若包含则拦截并提示修改
- ✓ 交叉权限异常：若申请用户已被圈主拉黑，点击「提交申请」时不发起真正请求，但界面统一提示「申请已满或暂不接受申请」，避免暴露拉黑事实
- ✓ 容量异常：若该圈子成员数已达到系统上限（如 500 人），点击“加入”或“申请加入”时提示「该圈子成员已满，暂不接受新申请」
- ✓ 状态限制：若用户对同圈子已有「待审核」申请，再次点击时系统提示「申请正在处理中，请勿重复提交」并禁用按钮
- ✓ 申请成功且审核状态合法持久化为「pending_review」，显示「申请已提交，请等待圈主审核」

### Story 5：圈主审批圈子加入申请 🔴

**用户故事：**
作为 **圈主**，我希望 **在圈子管理后台看到加入申请列表，能够逐一审核并同意/拒绝申请**，以便 **把控圈子成员构成**。

**验收标准：**
- ✓ 圈子管理后台展示「待审批申请」列表，显示申请时间、申请者昵称、申请理由、申请者的基本信息摘要
- ✓ 点击「同意」后，申请者自动加入圈子成员列表，该申请记录状态更新为「approved」
- ✓ 点击「拒绝」后，弹出可选框让圈主填写拒绝理由，拒绝理由（可选，最多 100 字）被记录，申请者收到拒绝通知
- ✓ 一周内未审批的申请自动标记为「expired」，不再在「待审批」列表中显示，但申请者与申请历史数据保留
- ✓ 审批操作实时同步到申请者的通知中心，显示「你的申请已通过/已拒绝」

### Story 6：用户浏览圈子成员列表 🔴

**用户故事：**
作为 **圈子成员**，我希望 **能看到圈子内的所有成员和他们的基本信息，了解圈子的人脉构成**，以便 **在圈子内寻找志同道合的人**。

**验收标准：**
- ✓ 圈子详情页中的「成员」选项卡显示成员列表，按加入时间倒序排列，每页显示 20 个成员
- ✓ 列表中显示每个成员的：头像、昵称、院系、共同圈子数，若是圈主则标记「👑 圈主」标签
- ✓ 点击成员名片可跳转到该成员的个人名片页，显示其公开或对我可见范围内的信息
- ✓ 若成员设置了某些字段为「完全私密」，列表中该字段显示为空或「-」

### Story 7：用户退出圈子 🟡

**用户故事：**
作为 **普通学生**，我希望 **能够随时退出已加入的圈子**，以便 **管理自己的圈子订阅和减少推送干扰**。

**验收标准：**
- ✓ 圈子详情页或成员列表中点击「退出圈子」，弹窗提示「确定要退出此圈子吗？你将失去对圈子内容的访问权限」
- ✓ 用户点击确认后，该用户从圈子成员表中删除，圈子成员数计数减 1
- ✓ 退出后用户无法再访问该圈子内容，若尝试进入则显示「你已退出此圈子，无法访问」
- ✓ 若用户是圈主，系统提示「圈主无法直接退出，请先转移圈主权限或删除圈子」，禁止退出操作

### Story 8：圈主移除违规成员 🟡

**用户故事：**
作为 **圈主**，我希望 **能将违反圈子规则或骚扰他人的成员从圈子移除**，以便 **维护圈子秩序和其他成员体验**。

**验收标准：**
- ✓ 圈子成员列表或成员详情页中，圈主可点击「更多」→「移除成员」
- ✓ 操作前弹窗提示「确定要移除该成员吗？」，圈主可选填移除理由（最多 100 字）
- ✓ 内容安全：录入移除理由时进行违规词检测，若有涉黄涉暴内容则提示圈主修改
- ✓ 确认后该成员立即从成员表删除，圈子成员计数减 1，被移除者收到包含理由的移除通知
- ✓ 被移除成员后续尝试重新加入时，提示「你已被该圈子限制，请联系圈主」，并将其列入圈子黑名单
- ✓ 移除及拉黑等管理操作详细记录于圈子审计日志中

---

### Story 9：圈主修改圈子基本信息 🟡

**用户故事：**
作为 **圈主**，我希望 **能修改圈子的名称、简介、标签等基本信息**，以便 **根据圈子发展调整其方向和吸引力**。

**验收标准：**
- ✓ 提供「编辑圈子信息」入口，显示圈子名称、简介（最多 200 字）、标签（最多 5 个）编辑表单
- ✓ 内容安全：修改并点击保存时，系统自动检测文本内容，包含敏感词时中断保存并提示需要修改
- ✓ 唯一交叉校验：若新输入的名称与已存在的其他圈子重名，提示「该名称已被占用」
- ✓ 保存后显示「更新成功」，且更新的圈子信息对所有成员和外部访客实时生效
- ✓ 任何圈子属性的变动均记录在审计日志中，以便追踪溯源和排查恶意改名等行为

### Story 10：系统响应全局封禁指令 🔴

**用户故事：**
作为 **平台系统服务**，我希望 **在接收到统一身份中心的违规/注销指令时，能自动处理该用户担任圈主或管理的圈子状态**，以便 **防止无主僵尸圈子驻留和越权管理等跨模块状态冲突**。

**验收标准：**
- ✓ 当接收到统一身份中心发送的用户注销或长期封禁（高于 30 天）指令时，检查该用户是否在任何圈子中担任唯一圈主。
- ✓ 若为唯一圈主，且圈子成员大于 1 人，系统则应按照成员活跃度或加入时间顺延，强制转移圈主权限给其他成员并后台发送提醒。
- ✓ 若为唯一圈主且圈子无人或不满足转移条件，系统自动冻结或解散该圈子。
- ✓ 用户以普通成员身份加入的圈子，系统自动触发等同于『被圈主移除』的操作，清理相关缓存。
- ✓ 处理全过程记录于跨模块事件响应审计日志中。

## 三、名片与隐私权限相关用户故事

### Story 11：用户设置名片隐私权限 🔴

**用户故事：**
作为 **普通学生**，我希望 **能细粒度地设置个人信息的可见范围，如微信号仅好友可见、手机号需申请解锁**，以便 **保护隐私同时允许恰当的社交接触**。

**验收标准：**
- ✓ 个人中心的「隐私设置」页面显示所有可配置的信息字段，分类如下：基础信息（昵称、性别）、联系方式（微信号、手机号、QQ）、位置信息（院系、宿舍区）
- ✓ 每个字段提供 5 个权限等级选项：🌐 完全公开 / 👥 仅好友 / 🏢 同圈子 / 🔒 需申请 / 🚫 完全私密
- ✓ 修改单个字段权限后页面即时反馈，显示新权限等级的标签
- ✓ 点击「保存」后，页面顶部显示绿色提示「隐私设置已保存✓」，权限规则实时生效于其他用户对我的访问
- ✓ 多次尝试修改并保存同一字段，系统只记录最后一次修改，不产生重复记录

---

### Story 12：用户查看公开名片信息 🔴

**用户故事：**
作为 **普通学生**，我希望 **能看到他人公开的名片信息，如昵称、院系、兴趣标签**，以便 **快速了解他人背景和寻找共同话题**。

**验收标准：**
- ✓ 进入他人名片页时，系统根据权限规则显示相应字段；权限为「完全公开」的字段直接显示，例如显示「院系：计算机学院」
- ✓ 若某字段权限为「完全私密」或「需申请」，该字段显示为「🔒 隐藏」或「申请解锁」
- ✓ 共同圈子、共同好友等关联信息也遵循权限规则显示，无权限看到的信息不显示数字，仅显示 「-」
- ✓ 名片页顶部显示该用户的好友状态（未添加/已申请/已是好友/已拉黑）和加好友入口

---

### Story 13：用户查看好友详细名片 🟡

**用户故事：**
作为 **普通学生**，我希望 **在与某人建立好友关系后，能看到他更多的信息**，以便 **更好地了解和联系朋友**。

**验收标准：**
- ✓ 已是好友的好友和普通用户看到的名片权限不同；好友能看到设置为「仅好友可见」的字段
- ✓ 若某字段权限设为「仅好友可见」，则非好友看到该字段为锁定状态，好友看到实际内容（如微信号、电话）
- ✓ 在好友列表中长按或右键点击某好友，可快速查看其名片预览，无需跳转详情页

---

### Story 14：用户查询指定可见范围内的名片 🟢

**用户故事：**
作为 **普通学生**，我希望 **能筛选和查看圈子内其他成员的名片信息，只看我有权限看到的内容**，以便 **在圈子内有针对性地寻找合作对象**。

**验收标准：**
- ✓ 圈子成员列表中提供「筛选」功能，可按院系、年级、标签等维度筛选成员
- ✓ 点击筛选后的成员，系统自动将该成员的名片展示限制为「同圈子可见」的权限范围
- ✓ 若某字段权限设为「需申请解锁」，则显示为「🔒 需申请解锁」，用户可点击申请

## 四、好友关系相关用户故事

### Story 15：用户发送好友申请 🟡

**用户故事：**
作为 **普通学生**，我希望 **能向其他用户发送好友申请，建立双向关系**，以便 **扩展自己的社交网络和获得更多交互权限**。

**验收标准：**
- ✓ 他人名片页提供「加好友」按钮，点击弹出填写验证信息的对话框
- ✓ 内容安全：用户填写的申请理由需经过系统违规词检测，若有不当内容则阻止发送并要求修改
- ✓ 容量极限校验：分别检查双方好友数，若发起方好友数已满，提示「你的好友数已达上限」；若接收方好友数已满，提示「对方好友数已达上限」
- ✓ 交叉状态拦截：若接收方已将发起方拉黑，点击发送后统一提示「发送失败，对方暂不接受你的申请」，确保不会借由报错提示暴露被拉黑的状态
- ✓ 防刷重校验：若对同一对象已有未处理的好友申请，按钮变为禁用状态并提示「你已发送过申请，请等待回复」
- ✓ 合法申请建立后，接收方收到通知，状态变更为「pending_approval」

---

### Story 16：用户处理好友申请（同意/拒绝） 🟡

**用户故事：**
作为 **普通学生**，我希望 **能在收到好友申请后选择同意或拒绝，并查看所有申请历史**，以便 **主动管理自己的好友列表**。

**验收标准：**
- ✓ 个人中心的「好友申请」页显示所有待处理的好友申请列表，申请者的基本信息和申请时间清楚显示
- ✓ 点击「同意」后，双方建立好友关系，被申请者立即出现在申请者的好友列表中，双方可见性权限同时更新
- ✓ 点击「拒绝」后，该申请标记为「rejected」，申请者收到「对方拒绝了你的好友申请」的通知，拒绝后双方无法再直接看到对方的好友状态为「申请中」
- ✓ 申请表单中显示一周内的申请，超过一周的申请自动标记为「expired」，允许重新申请

---

### Story 17：用户删除好友关系 🟡

**用户故事：**
作为 **普通学生**，我希望 **能随时删除已建立的好友关系**，以便 **管理自己的社交圈子并移除不适合的关系**。

**验收标准：**
- ✓ 在好友列表中，长按或右键点击某好友，选择「删除好友」
- ✓ 删除前弹窗确认「确定删除该好友吗？删除后你将看不到对方的隐私内容」
- ✓ 删除后，双方的好友关系立即解除，对方在你的好友列表中消失，你在对方的好友列表中也消失
- ✓ 删除后重新看到对方名片时，对方设置为「仅好友可见」的字段重新变为隐藏状态
- ✓ 删除操作不产生通知，即只删除而不告知对方已被删除

---

### Story 18：用户撤销未处理的好友申请 🟢

**用户故事：**
作为 **普通学生**，我希望 **能撤销那些已发送但还未被对方处理的好友申请**，以便 **改变主意或清理积压的申请**。

**验收标准：**
- ✓ 个人中心的「已发送申请」列表中，显示所有状态为「pending_response」的好友申请
- ✓ 在「已发送申请」列表中右键或点击「撤销」，确认后该申请被删除
- ✓ 被申请者收到「XXX 撤销了好友申请」的通知（或者简单清除该申请），其待处理列表中该申请消失
- ✓ 撤销后如需重新申请，需间隔至少 24 小时

---

### Story 19：用户拉黑或取消拉黑 🟢

**用户故事：**
作为 **普通学生**，我希望 **能拉黑骚扰我的用户，防止他们向我发送申请或查看我的信息**，以便 **保护自己的隐私和避免骚扰**。

**验收标准：**
- ✓ 在他人名片页或好友列表中，点击「更多」→「拉黑该用户」
- ✓ 拉黑后该用户无法向我发送好友申请，若尝试则系统提示「该用户已将你拉黑」
- ✓ 被拉黑用户看我的名片时，所有信息显示为「该用户不接受陌生人查看」或类似提示
- ✓ 我可在「被拉黑列表」中查看所有被拉黑的用户，并选择「取消拉黑」恢复正常状态

### Story 20：用户申请解锁他人联系方式 🔴

**用户故事：**

**验收标准：**

- ✓ 交叉状态防御：若当前申请者已被被解锁方拉黑，不显示「申请解锁」入口，仅显示常规隐私保护锁定提示
- ✓ 防刷和频次限制：30 天内对同一对象同一字段的失败申请超过 2 次，限制操作并提示「频繁操作，请 7 天后重试」

## 十一、AI 辅助实验分析 (响应任务 3.3)

通过对初代 AI 生成的 `用户故事库_圈子与关系链.md` 文件内容分析，可以得出以下判断：

### 11.1 AI 生成的内容是否遗漏了异常流？
**结论：部分轻度异常流有考虑到，但遗漏了大量深层业务异常流和系统级异常流。**

*   **已考虑的异常流（AI表现较好的地方）：**
    *   **排重校验：** 同名圈子拦截（Story 2）、重复发送入圈申请（Story 4）、重复发送好友申请（Story 15）。
    *   **防刷机制：** 频繁申请解锁的限制（Story 20 提到 30天内2次被拒需等7天）、撤销后重申的限制（Story 18 提到 24小时）。
*   **严重遗漏的异常流（AI的盲区，人工已补充）：**
    *   **文件生成结构性错误（明显失误）：** Story 1（用户浏览圈子发现页面）不仅和 Story 2 混在了一起，而且完全没有生成 Story 1 对应的验收标准（人工已修复）。
    *   **内容安全与审核异常：** 用户创建圈子、填写加入理由、拒绝理由时，输入的文字是否包含敏感词/违规信息？这部分异常拦截完全归零（人工已补充，增加系统敏感词拦截）。
    *   **边界与容量异常：** 圈子是否有人数上限？当圈子满员时，普通用户点击申请、圈主点击“同意”时应该触发什么异常提示？个人加入圈子是否有上限？（人工已补充容量与上限校验）。
    *   **并发与冲突操作：** 两个副圈主/管理员同时审批同一个用户的申请会发生什么？
    *   **交叉权限异常：** 如果一个用户被圈主拉黑（Story 19），此时该用户去申请加入该圈主创建的“需审核”圈子（Story 4），到底是直接拦截还是正常提交？AI 没有考虑模块之间的连带异常流（人工已补充静默拦截等处理机制）。

### 11.2 验收标准是否具体可测试？
**结论：大部分验收标准是具体且可测试的，包含明确的阈值和预期结果，但缺少前置条件（Given）的严谨定义。**

*   **具备高可测试性的表现：**
    *   **明确的文字/数值边界：** 如圈子名称“1-30字”、简介“1-200字”、分页“每页显示 20 个成员”、理由“最多 100 字”。这些可以直接写进测试用例。
    *   **明确的 UI 状态跳转与文案提示：** 如“按钮变为禁用状态，显示灰色”、“弹出『确定要退出此圈子吗？…』”、“标记为『已截断』”，这些 UI 交互有明确的预期目标值。
    *   **后台数据状态的明确变更：** 如“状态更新为 `approved`”、“状态为 `pending_review`”、“记录在审计日志中”。这些对后端开发和接口测试非常友好。
*   **不可测试/模糊的表现：**
    *   **未定义明确的前置测试数据：** 条目普遍使用描述性语言，而没有采用更为严密可测试的 `Given-When-Then`（假设-当-那么）句式结构，导致测试的前置环境不够清晰。
    *   **缺乏具体的排序/规则定义：** 如 Story 6 中的列表只提了“按加入时间倒序”，但如果加入时间精确到毫秒都一致的情况没有定义兜底排序（如按用户ID）。
    *   **隐式需求的遗漏：** Story 1 提到的“系统推荐的圈子列表”，默认版完全没有定义“推荐”的标准是什么（按热度？按同院系？），测试工程师无法对“推荐是否准确”进行验证（人工已修补这部分具体的匹配度规则）。
