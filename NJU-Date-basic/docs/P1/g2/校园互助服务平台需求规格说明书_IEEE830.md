# 圈子与关系链子系统需求规格说明书（SRS）

版本：v1.1
编写日期：2026-04-17
子系统：圈子与关系链（社交建立模块）

---

## 1. 引言

### 1.1 目的
本文档依据 IEEE 830 规范，定义“校园社交与互助服务平台”中“圈子与关系链（社交建立模块）”的需求边界、功能需求、非功能需求及追踪关系。
文档面向产品经理、开发工程师、测试工程师和项目评审人员，用于指导实现、测试验收与跨组协作。

### 1.2 范围
本子系统聚焦“大学生校园弱关系向强关系转化”路径，覆盖以下功能：
1. 圈子管理：圈子发现、加入/退出、成员列表、圈内频道页。
2. 名片与隐私体系：公开名片/好友名片差异化展示与字段级权限控制。
3. 好友与关系链管理：好友申请、通过、拒绝、删除与关系维护。
4. 权限解锁流：联系方式解锁申请、审批、撤销与展示控制。
5. 圈内专属互动：圈内问卷、同好推荐、活动组队与群组互动。

明确不在本子系统范围内：
1. 用户注册、登录、找回密码、统一身份认证。
2. 全站公共论坛发帖、举报审核、封禁处置、运营后台治理。
3. 交易支付、订单履约、校园跑腿等其他业务域。

### 1.3 术语、缩略语与定义
- SRS：Software Requirements Specification，需求规格说明书。
- 圈子：由共同兴趣、课程或活动主题形成的半封闭社交空间。
- 弱关系：基于共同标签/圈子而建立的低信任初始连接。
- 强关系：建立好友关系并可进行深层沟通与协作的连接状态。
- 公开名片：陌生人可见的信息集合。
- 好友名片：建立好友关系后可见的增强信息集合。
- 解锁字段：默认隐藏、需申请审批后才可见的联系方式字段。
- 圈内频道：圈子内部按主题划分的互动页（如“组队”“问答”“活动”）。

## 2. 总体描述

### 2.1 产品视角
本子系统是平台中的“社交建立域”，承接统一认证后的用户身份信息，并向上支撑“圈子互动、关系沉淀、协作组队”能力。其核心业务链路为：

发现圈子 -> 加入圈子 -> 识别同好 -> 名片互看 -> 好友建立 -> 联系方式解锁 -> 组队协作

该链路用于将校园内一次性、低信任连接逐步升级为持续、可协作的强关系连接。

### 2.2 大学生用户特征分析
1. 时间碎片化：日常高频短时使用，要求关键动作路径短、反馈快。
2. 信任建立渐进：更倾向先看共同圈子和共同兴趣，再决定是否加好友。
3. 隐私敏感度高：联系方式不愿直接公开，偏好“先申请、后授权”的披露机制。
4. 场景驱动明显：关系升级多发生在“活动组队、课程协作、兴趣交流”等具体场景。
5. 社交风险顾虑：对骚扰、频繁申请、越权查看等行为容忍度低。

### 2.3 技术约束
1. 本子系统必须复用统一用户身份服务，不可重复实现注册登录逻辑。
2. 所有客户端与服务端通信必须使用 HTTPS。
3. 权限判断需支持字段级策略（按信息字段、关系类型、圈子上下文进行授权）。
4. 关键状态变更（入圈审批、好友关系、隐私解锁）必须具备审计记录。
5. 移动端与 Web 端行为规则一致，保证跨端状态同步。

### 2.4 假设与前提
1. 用户已通过平台基础身份认证并处于“可使用”状态。
2. 圈子、用户、关系数据可由同一主数据库或可事务协调的数据层提供。
3. 站内通知能力可用，用于申请与审批消息触达。
4. 推荐能力可调用规则引擎或推荐服务，但本子系统仅定义业务输入输出，不限定算法实现。

## 3. 功能需求

说明：
- 编号规则：FR-CC（圈子管理）、FR-PC（名片隐私）、FR-FR（好友关系）、FR-UL（权限解锁）、FR-CI（圈内互动）。
- 业务优先级分为：高/中/低。
- 每条需求均标注来源：`[AI生成]`、`[人工补充]`、`[AI生成+人工修改]`。

### 3.1 模块一：圈子管理

- 【需求编号】FR-CC-001
  【需求描述】系统应提供“圈子发现广场”，支持按兴趣标签、院系、年级、活跃度检索圈子，帮助用户快速识别潜在弱关系社交入口。
  【业务优先级】高
  【来源】[AI生成+人工修改]
  【人工修改说明】补充“院系、年级”检索维度，以贴合问卷对同频筛选诉求。

- 【需求编号】FR-CC-002
  【需求描述】圈子详情页应展示圈子基础信息（名称、简介、标签、成员数、活跃度、加入规则），并展示圈规摘要与公告置顶区域。
  【业务优先级】高
  【来源】[AI生成+人工修改]
  【人工修改说明】新增“圈规摘要与公告置顶”，对应访谈中对进圈前信息透明的需求。

- 【需求编号】FR-CC-003
  【需求描述】系统应支持三类加入机制：公开加入、申请审核加入、仅邀请加入；并根据机制展示不同交互按钮与提示。
  【业务优先级】高
  【来源】[AI生成]

- 【需求编号】FR-CC-004
  【需求描述】当用户申请加入需审核圈子时，系统应保存申请理由、申请时间和状态（待审核/通过/拒绝/过期），并向圈主发送待办通知。
  【业务优先级】高
  【来源】[AI生成]

- 【需求编号】FR-CC-005
  【需求描述】圈主应可在审批列表中对入圈申请执行通过或拒绝操作；通过后自动建立成员关系并开放圈内资源访问权限。
  【业务优先级】高
  【来源】[AI生成]

- 【需求编号】FR-CC-006
  【需求描述】系统应提供圈子成员列表，支持按匹配度、同专业/同年级、活跃度排序，并展示对当前访问者可见的成员摘要信息。
  【业务优先级】高
  【来源】[AI生成+人工修改]
  【人工修改说明】新增排序策略，吸收问卷中对“可解释筛选排序”的明确偏好。

- 【需求编号】FR-CC-007
  【需求描述】成员应可主动退出圈子；退出时系统应提供“是否清空本人在该圈历史足迹”的可选项，退出后立即失去圈内访问权限。
  【业务优先级】中
  【来源】[AI生成+人工修改]
  【人工修改说明】新增“退圈清痕”可选项，来自问卷中高比例隐私诉求。

- 【需求编号】FR-CC-008
  【需求描述】系统应提供圈内频道页，并支持“实时群聊频道 + 话题帖子频道”双形态并存，按成员身份控制可见范围。
  【业务优先级】高
  【来源】[AI生成+人工修改]
  【人工修改说明】将“频道页”细化为双通道互动，解决访谈中反复提出的双形态需求。

- 【需求编号】FR-CC-009
  【需求描述】圈主应可配置入圈问答（问题、答案或审核条件）与关键词过滤规则，以降低广告与低质量入圈。
  【业务优先级】中
  【来源】[人工补充]

- 【需求编号】FR-CC-010
  【需求描述】系统全局事件响应：当接收到统一身份中心发送的用户注销或封禁指令时，本系统应自动解散该用户为唯一圈主的圈子，或请求系统强制转让圈主权限。
  【业务优先级】高
  【来源】[人工补充]

### 3.2 模块二：名片与隐私体系

- 【需求编号】FR-PC-001
  【需求描述】系统应提供用户专属名片，名片字段分为“基础公开信息（昵称、兴趣标签等）”与“敏感身份信息（真实姓名、学号、联系方式等）”。
  【业务优先级】高
  【来源】[AI生成+人工修改]
  【人工修改说明】将“基础身份信息”改为分层字段定义，消除是否公开真实身份的歧义。

- 【需求编号】FR-PC-002
  【需求描述】名片展示必须区分访问关系：陌生人视图（公开名片）与好友视图（好友名片），并依据关系类型动态渲染字段。
  【业务优先级】高
  【来源】[AI生成]

- 【需求编号】FR-PC-003
  【需求描述】用户应可对每个名片字段配置可见级别：公开、同圈可见、好友可见、需申请解锁、仅自己可见。
  【业务优先级】高
  【来源】[AI生成]

- 【需求编号】FR-PC-004
  【需求描述】当访问者无权限查看字段时，系统应返回统一“已隐藏/可申请解锁”状态，不暴露隐私策略细节。
  【业务优先级】高
  【来源】[AI生成]

- 【需求编号】FR-PC-005
  【需求描述】用户更新名片隐私配置后，权限规则应实时生效，后续名片访问请求需按新规则鉴权。
  【业务优先级】中
  【来源】[AI生成]

- 【需求编号】FR-PC-006
  【需求描述】系统应记录隐私配置变更审计日志（变更字段、前后值摘要、操作者、时间），用于追踪越权争议。
  【业务优先级】中
  【来源】[AI生成]

- 【需求编号】FR-PC-007
  【需求描述】系统应支持“一张通用名片”与“按圈子定制名片模板”两种模式，用户可自行选择，以平衡个性化与配置成本。
  【业务优先级】中
  【来源】[人工补充]

### 3.3 模块三：好友与关系链管理

- 【需求编号】FR-FR-001
  【需求描述】访问他人名片时，系统应提供“添加好友”入口，并允许填写申请说明以增强建立连接的上下文。
  【业务优先级】高
  【来源】[AI生成]

- 【需求编号】FR-FR-002
  【需求描述】系统应保存好友申请状态（待处理/通过/拒绝/过期），并向被申请方发送通知。
  【业务优先级】高
  【来源】[AI生成]

- 【需求编号】FR-FR-003
  【需求描述】被申请方应可在申请列表中执行通过或拒绝；通过后系统建立双向好友关系并更新名片可见权限。
  【业务优先级】高
  【来源】[AI生成]

- 【需求编号】FR-FR-004
  【需求描述】系统应支持删除好友；删除后双方恢复为非好友状态，好友专属字段自动隐藏。
  【业务优先级】高
  【来源】[AI生成]

- 【需求编号】FR-FR-005
  【需求描述】系统应提供“关系链管理视图”，展示用户的一度关系（好友）与圈内共同关系提示（共同圈子/共同好友数）。
  【业务优先级】中
  【来源】[AI生成]

- 【需求编号】FR-FR-006
  【需求描述】对频繁重复申请、短期骚扰行为应触发频率限制策略，保护用户免受关系链滥用。
  【业务优先级】高
  【来源】[AI生成]

- 【需求编号】FR-FR-007
  【需求描述】好友申请通过后，系统应展示“共同兴趣/共同圈子/建议开场话题”破冰提示，降低关系建立后的沉默率。
  【业务优先级】中
  【来源】[人工补充]

- 【需求编号】FR-FR-008
  【需求描述】系统应支持“静默拒绝申请”和“静默删除好友”策略选项，避免对方收到明确拒绝/删除通知，降低社交尴尬。
  【业务优先级】中
  【来源】[人工补充]

- 【需求编号】FR-FR-009
  【需求描述】系统应支持关系降级（仅保持关注不可互动）模式，作为直接删除之外的柔性关系管理手段。
  【业务优先级】低
  【来源】[人工补充]

### 3.4 模块四：权限解锁流

- 【需求编号】FR-UL-001
  【需求描述】当目标字段被设置为“需申请解锁”时，系统应在名片中展示解锁入口并要求填写申请理由。
  【业务优先级】高
  【来源】[AI生成]

- 【需求编号】FR-UL-002
  【需求描述】系统应支持按“用户-字段”维度创建解锁申请，并记录状态（待处理/通过/拒绝/过期/撤销）。
  【业务优先级】高
  【来源】[AI生成]

- 【需求编号】FR-UL-003
  【需求描述】被申请方应可逐条审批解锁请求；批准后申请方仅可查看获批字段，不可越权访问其他隐私字段。
  【业务优先级】高
  【来源】[AI生成]

- 【需求编号】FR-UL-004
  【需求描述】被申请方应可撤销既有解锁授权；撤销后字段访问权限立即失效并回到隐藏状态。
  【业务优先级】中
  【来源】[AI生成]

- 【需求编号】FR-UL-005
  【需求描述】系统应提供解锁申请历史查询，支持用户查看申请理由、审批结果与时间线。
  【业务优先级】中
  【来源】[AI生成]

- 【需求编号】FR-UL-006
  【需求描述】系统应对同一申请方在限定周期内的失败解锁次数进行阈值控制，超过阈值后限制再次申请。
  【业务优先级】高
  【来源】[AI生成]

- 【需求编号】FR-UL-007
  【需求描述】在活动组队场景中，系统可提供“临时联系方式解锁”机制，活动结束后自动回收可见权限。
  【业务优先级】低
  【来源】[人工补充]

### 3.5 模块五：圈内专属互动

  【业务优先级】高

  【业务优先级】中

- 【需求编号】FR-CI-006

  【业务优先级】中
  【来源】[AI生成]

## 4. 非功能需求

- 【需求编号】NFR-P-001
  【需求描述】圈子发现广场列表接口在 95% 请求下响应时间应不超过 800ms。

  【来源】[AI生成]

- 【需求编号】NFR-P-002
  【需求描述】成员列表、好友列表、申请列表分页查询在单页 20 条数据下响应时间应不超过 500ms。
  【业务优先级】中
  【来源】[AI生成]

- 【需求编号】NFR-P-003
  【需求描述】申请与审批类写操作（入圈、好友、解锁）在正常负载下应在 1s 内完成并返回状态。
  【业务优先级】中
  【来源】[AI生成]

- 【需求编号】NFR-P-004
  【需求描述】圈内推荐结果刷新周期不超过 15 分钟，确保推荐可用且具时效性。
  【业务优先级】低
  【来源】[AI生成]

### 4.2 安全性与隐私边界需求
- 【需求编号】NFR-S-001
  【需求描述】名片隐私字段在存储层必须加密或脱敏存储，禁止明文落库。
  【业务优先级】高

## 5. 需求追踪矩阵

### 5.1 核心用户场景定义
- S1：新生在发现广场找到兴趣圈并成功加入，完成第一次弱关系接触。
- S2：圈内成员浏览名片并发起好友申请，建立稳定双向关系。
- S3：用户对好友或潜在合作对象申请解锁联系方式，进入强关系沟通。
- S4：用户通过圈内问卷与同好推荐找到协作对象，并参与活动组队。
- S5：用户在不适场景下可收回授权、删除好友、退出圈子，保持社交边界可控。

### 5.2 模块到场景映射

| 功能模块 | 关键需求编号 | 对应核心场景 | 场景价值说明 |
|---|---|---|---|
| 圈子管理 | FR-CC-001~FR-CC-0010 | S1、S5 | 提供弱关系入口、圈规约束与可退出机制，保证关系建立与退出都可控 |
| 名片与隐私体系 | FR-PC-001~FR-PC-007 | S2、S3、S5 | 在可见性分层下逐步披露信息，兼顾隐私安全与个性化展示 |
| 好友与关系链管理 | FR-FR-001~FR-FR-009 | S2、S5 | 将临时互动沉淀为可维护关系网络，并通过破冰与静默策略降低摩擦 |
| 权限解锁流 | FR-UL-001~FR-UL-007 | S3、S5 | 通过申请审批与可撤回授权完成联系方式安全交换 |
| 圈内专属互动 | FR-CI-001~FR-CI-006 | S4 | 用问卷、推荐与组队场景驱动深度合作和持续互动 |

### 5.3 验收口径（场景级）
1. 若用户可在一次会话内完成“发现圈子 -> 加入 -> 浏览成员”，则 S1 验收通过。
2. 若用户可完成“名片查看 -> 好友申请 -> 通过后信息升级展示”，则 S2 验收通过。
3. 若用户可完成“联系方式申请 -> 对方审批 -> 字段级可见”，则 S3 验收通过。
4. 若圈内可完成“问卷填写 -> 同好推荐 -> 活动组队报名”，则 S4 验收通过。
5. 若用户可执行“撤销授权/删除好友/退出圈子”并即时生效，则 S5 验收通过。
