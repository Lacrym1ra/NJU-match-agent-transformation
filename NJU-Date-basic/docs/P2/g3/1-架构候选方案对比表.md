# 架构候选方案对比表

> 南苏三折叠：诚园闪击苏教 | 负责论坛与治理子系统

## 1. 对比方案与选取理由

我们组负责整个项目的论坛模块实现以及全链路的举报和拉黑设计实现，由于是在已有项目上做工作，已有的项目框架和内容将在很大程度上影响决策，当然，开发需求和小组整体设想仍旧是架构不变的服务对象。

- **方案 A：分层模块化单体（Modular Monolith）**
  - 保持现有 `Express + TypeScript + PostgreSQL + React` 主体结构
  - 在单体内按模块分层（route/service/db/model）
  - 论坛与治理作为新模块挂到现有应用中
- **方案 B：微服务拆分（Microservices）**
  - 将论坛、治理、用户、圈子拆为独立服务
  - 引入服务间通信、网关、链路治理

选这两种方案的原因：  
它们分别代表“**沿现有代码演进**”和“**重做为服务化架构**”两条典型路线，便于结合课程周期和团队经验做决策。

## 2. 对比图

### 2.1 方案 A：分层模块化单体

```text
React 前端
   │ REST (/api/v1/*)
   ▼
Express 单体应用
 ├─ auth/user/survey/match/admin/circles/card/friends/contacts（已实现）
 └─ forum（待接入待开发）
   │
   ▼
PostgreSQL（共享库）
```

### 2.2 方案 B：微服务拆分

```text
React 前端
   │
API Gateway
 ├─ User Service
 ├─ Forum Service
 ├─ Governance Service
 └─ Circle Service
   │
   ├─ 各服务独立数据库 / 或共享数据库
   └─ 服务间通信（HTTP/MQ）
```

## 3. 核心维度对比

| 对比维度 | 方案 A：分层模块化单体 | 方案 B：微服务 |
|---------|-------------------------|----------------|
| 开发复杂度 | 低。沿用现有代码结构与部署方式，在现有后端新增 forum 路由和 service 即可。 | 高。需补网关、服务拆分、通信协议、配置与运维体系。 |
| 可维护性 | 中高。模块边界清晰时可维护性好，代码集中便于调试。 | 中。长期可维护性高，但早期服务边界不稳时维护成本大。 |
| 可扩展性 | 中。可按模块继续拆分，后续有演进空间。 | 高。天然支持按服务独立扩展。 |
| 性能 | 中高。校内项目规模下足够；少网络跳转，链路短。 | 中高。高并发时潜力更大，但存在服务间通信开销。 |
| 团队学习成本 | 低。团队已在使用 Express/React/PostgreSQL。 | 高。需掌握分布式治理、服务发现、容错等。 |
| 10 周内可行性 | **高**。与当前仓库高度一致，可快速交付可演示版本。 | **低**。重构体量大，容易挤压业务功能落地时间。 |

## 4. 结论

结合当前真实实现状态（后端已是单体多模块；论坛表已建但论坛路由未注册；治理接口部分已上线），**优先选择方案 A：分层模块化单体**。  
该方案能在 10 周内稳定完成论坛与治理能力，同时为后续微服务演进保留接口和模块边界，不做过早架构复杂化。
