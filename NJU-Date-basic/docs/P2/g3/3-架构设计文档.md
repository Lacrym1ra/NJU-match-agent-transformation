# 论坛与治理子系统架构设计文档

> 南苏三折叠：诚园闪击苏教 v2.0  | 举报与拉黑&论坛主体已实现 2026.5.4 by XYH

## 1. 架构目标与边界

### 1.1 架构风格
采用分层模块化单体，在当前仓库结构下优先保证论坛功能快速落地，并保留后续按论坛/治理拆分的边界。

### 1.2 前提
- 举报与拉黑能力在写文档的过程中已经被架构同学实现，已可用（`POST /api/v1/user/report/:targetId`、`POST /api/v1/user/block/:targetId`、`DELETE /api/v1/user/block/:targetId`，以及管理端举报处理接口）。
- g2（圈子小组）对于组队和信用分模块提出两个联调接口需求。

### 1.3 设计目标
- 完成论坛主链路：列表、发帖、详情、评论、软删除、管理置顶/删帖。
- 在发帖链路中补充本地草稿保存能力，降低编辑中断导致的内容丢失风险。
- 支持圈子维度论坛（`circleId`）与组队贴（`type=squad`）统一建模。
- 支持评论置顶、帖内投票、点赞/收藏/浏览计数与热度榜，丰富帖子互动形态。
- 支持基于用户画像、问卷兴趣、互动行为和内容质量的推荐排序。
- 支持关注关系与私信沟通，并通过隐私设置控制私信入口。
- 新增“组队同步到论坛”专用 API。
- 在信用分中新增两个接口：截止自动扣分、活动结束后同组举报。

### 1.4 当前代码现状校准（2026-05-04）
基于当前仓库代码与文档核对，论坛治理相关能力分为两层：
- 已落地能力（可联调）：
  - 用户举报：`POST /api/v1/user/report/:targetId`
  - 用户拉黑：`POST /api/v1/user/block/:targetId`、`DELETE /api/v1/user/block/:targetId`
  - 管理端举报审核：`GET /api/v1/admin/reports`、`PATCH /api/v1/admin/reports/:id`
  - 审计日志：举报审核行为写入 `audit_logs`
- 已有数据基础但接口未完整落地：
  - `forum_posts`、`forum_comments` 已在迁移与 schema 中定义；
  - `/api/v1/forum/*` 与 `/api/v1/admin/forum/*` 仍以“设计先行”为主，需在后续迭代注册路由与服务。

说明：本文后续出现“建议新增”或“演进接口”均表示架构基线，不等于当前版本已全部实现。

## 2. 总体架构

```text
前端层（React）
  用户侧：Forum / ForumPost / PostEditor / CircleDetail入口 / Messages
  管理侧：Admin 举报处理 + ForumModeration
      │
接口层（Express）
  /api/v1/forum/*        论坛主接口 + 组队同步接口 + 信用分接口 + 投票/评论置顶/推荐排序
  /api/v1/social/*       关注关系 + 私信 + 私信隐私设置
  /api/v1/admin/forum/*  管理端帖子治理
  /api/v1/admin/reports  举报审核（已可用）
  /api/v1/user/*         举报/拉黑（已可用）
      │
服务层
  ForumService / ForumRecommendationService / SocialService / TeamupSyncService / CreditService / ForumAdminService
      │
数据层（PostgreSQL + Drizzle）
  forum_posts / forum_comments / forum_poll_options / forum_poll_votes / direct_messages / audit_logs / user_reports / user_blocks
  （新增建议）forum_teamup_bindings / forum_credit_events
```

关键说明：
- 前端不做最终权限判断，圈子成员校验、发帖资格、信用分扣减均以后端为准。
- 论坛页与圈子页复用同一论坛接口，圈子页只透传 `circleId`。
- 举报/拉黑作为可用治理能力接入论坛，但不作为论坛主流程前置依赖。

## 3. 模块职责

### 3.1 前端模块
- `Forum.tsx`：全站/圈子列表、类型筛选、分页、最新/热门/推荐排序。
- `ForumPost.tsx`：帖子详情、评论树、评论置顶、帖内投票、组队贴行动按钮。
- `PostEditor.tsx`：发帖输入，支持 `type=squad` 默认值、图片、投票选项与本地草稿。
- `ForumRanking.tsx` / `HotRankingSidebar.tsx`：热度榜与侧边榜单入口。
- `Messages.tsx`：私信会话列表、会话详情与消息发送。
- `Admin.tsx`：举报处理分区 + 帖子管理分区。

### 3.2 后端模块
- `routes/forum`：论坛主接口、组队同步接口、信用分接口、评论置顶、帖内投票、热度榜与推荐排序。
- `routes/social`：关注关系、私信会话、私信发送与隐私设置。
- `routes/admin/forum`：管理查帖、删帖、置顶。
- `ForumPolicyService`：圈子成员校验、可见性校验、发帖资格校验。
- `ForumService`：帖子、评论、点赞、收藏、投票、评论置顶、热度分更新与推荐查询。
- `SocialService`：关注关系、私信资格判断、会话幂等创建、消息读取与未读状态。
- `TeamupSyncService`：接收组队数据并自动生成/更新组队帖。
- `CreditService`：扣分事件落库、成员举报触发信用分流程。
- `ContentModerationService`：发帖内容规范化、敏感词匹配、命中分级处理与审核日志。

### 3.3 数据模型（核心）
- `forum_posts`：帖子主表（`type`、`circle_id`、`is_pinned`、`pinned_comment_id`、`visibility`、`hot_score`、`has_poll`、`deleted_at`、计数字段）。
- `forum_comments`：评论与二级回复（软删除），支持文本/语音评论、转写状态与评论点赞计数。
- `forum_poll_options`：帖内投票选项（`post_id`、`option_text`、`display_order`、`vote_count`）。
- `forum_poll_votes`：帖内投票记录（`post_id`、`option_id`、`user_id`），通过唯一约束保证同一用户每帖一票。
- `forum_post_likes`、`forum_post_favorites`、`forum_comment_likes`：互动关系表，用于计数、个人列表和推荐信号。
- `user_follows`：关注关系，支撑私信权限中的 `following|mutual` 判断。
- `user_message_settings`：私信隐私设置（`all|following|mutual|none`）。
- `direct_message_conversations`、`direct_messages`：私信会话与消息明细，按用户对唯一会话聚合。
- `audit_logs`：管理操作与关键治理动作审计。
- `user_reports`、`user_blocks`：已可用治理能力的持久化。
- `forum_teamup_bindings`（建议新增）：
  - `teamup_id`（唯一）
  - `post_id`
  - `circle_id`
  - `leader_id`
  - `sync_status`（`active|closed|canceled`）
  - `last_synced_at`
- `forum_credit_events`（建议新增）：
  - `event_id`
  - `teamup_id`
  - `user_id`
  - `event_type`（`deadline_penalty|member_report`）
  - `score_delta`
  - `reason`
  - `created_at`
- `sensitive_words`（建议新增）：
  - `id`
  - `term`
  - `level`（`block|replace|review`）
  - `is_active`
  - `updated_at`
- `content_moderation_logs`（建议新增）：
  - `id`
  - `target_type`（`post|comment`）
  - `target_id`
  - `hit_terms`
  - `decision`（`pass|replaced|blocked|pending_review`）
  - `created_at`

## 4. 论坛业务规则

### 4.1 帖子类型
- 当前数据库约束（已落地）：
  - `post`：普通交流（历史兼容值）
  - `squad`：组队贴
- 目标业务类型（后续演进）：
  - `general`、`help`、`trade`、`activity`（需先完成 migration 与前后端枚举同步）

规则：
- `squad` 可放宽门槛，但不绕过登录与圈子成员规则。
- 在未完成类型迁移前，`post` 仍作为线上兼容主值；文档中的 `general` 视为目标语义别名。
- 发帖草稿不进入后端帖子状态机，当前以前端 `localStorage` 保存标题、正文、类型、匿名/可见性、图片 URL 与投票选项；发布成功或用户放弃后清理。
- 帖内投票随帖子创建写入，选项数量保持在 2-4 个范围内；投票提交后只允许同一用户在同一帖子下保留一条投票记录。
- 评论置顶只允许帖子作者或具备治理权限的用户操作，且仅置顶未删除的一级评论；置顶评论在评论列表中优先展示。

### 4.2 圈子可见性
- `circleId = null`：全站可见。
- `circleId != null`：圈子帖子，仅圈子成员可访问与互动。
- 圈子校验必须后端执行，不依赖前端隐藏按钮。
- 推荐排序、热度榜默认只面向全站公开且未删除帖子，避免私密帖和圈内帖被跨上下文曝光。

### 4.3 软删除与审计
- 帖子/评论均软删除。
- 管理端删帖、置顶、举报处理、信用分关键事件统一写 `audit_logs`。
- 帖子被删除时，前台列表、推荐流、热度榜和投票入口均不可见；已存在投票、评论与私信引用不做物理删除，保留治理回溯能力。
- 用户侧评论置顶、投票、点赞、收藏属于普通互动操作，主要通过业务表与计数字段追踪；管理端置顶/下线等治理操作必须写审计。

### 4.4 内容安全与敏感词屏蔽
采用“规范化 + 词库匹配 + 分级处置 + 人工复核”的策略（与 ADR-007 对齐）：
- 规范化：大小写归一、空白折叠、常见符号归一，降低规避写法影响。
- 词库匹配：命中 `sensitive_words` 后按等级执行：
  - `block`：直接拦截发布并返回错误提示；
  - `replace`：自动替换敏感片段后发布；
  - `review`：进入待审核状态，不立即公开。
- 人工复核：高风险命中进入管理端审核队列，结果可反哺词库与规则。

约束：
- 发帖与评论均走同一 `ContentModerationService`，避免策略分叉。
- 敏感词命中与处置动作写 `content_moderation_logs`，保证可追踪。
- 私信内容同样需要复用文本长度校验、频率限制和拉黑/隐私权限判断；若后续接入敏感词服务，应与论坛内容审核共用规则来源。
- 推荐排序不得绕过内容安全结果：被删除、私密、圈内不可见或待审核内容不能进入公开推荐候选池。

## 5. 接口设计

### 5.1 通用约定
- 协议：HTTPS + JSON
- 用户鉴权：`Authorization: Bearer <token>`
- 管理鉴权：`x-admin-key`
- 组队同步建议使用服务间鉴权：`x-internal-key`（或网关内网鉴权）

### 5.2 论坛主接口
- `GET /api/v1/forum/posts`（支持 `sort=latest|hot|recommended`、`type`、`keyword`、`authorScope`、分页）
- `POST /api/v1/forum/posts`（支持正文、图片、匿名/可见性、投票选项）
- `GET /api/v1/forum/posts/:postId`
- `POST /api/v1/forum/posts/:postId/comments`
- `DELETE /api/v1/forum/posts/:postId`
- `DELETE /api/v1/forum/comments/:commentId`
- `PUT /api/v1/forum/posts/:postId/pinned-comment`
- `DELETE /api/v1/forum/posts/:postId/pinned-comment`
- `POST /api/v1/forum/posts/:postId/poll/vote`
- `POST /api/v1/forum/posts/:postId/like`、`DELETE /api/v1/forum/posts/:postId/like`
- `POST /api/v1/forum/posts/:postId/favorite`、`DELETE /api/v1/forum/posts/:postId/favorite`
- `GET /api/v1/forum/ranking/hot`
- `GET /api/v1/admin/forum/posts`
- `DELETE /api/v1/admin/forum/posts/:postId`
- `PUT /api/v1/admin/forum/posts/:postId/pin`

发帖草稿说明：
- 当前草稿为前端本地能力，不新增后端草稿接口；草稿键按论坛发帖入口统一维护，避免未发布内容进入审计与推荐链路。
- 保存草稿时若仍有图片上传中，应提示用户稍后再保存，避免草稿引用临时或不可访问资源。

推荐排序说明：
- `sort=recommended` 由后端基于用户 MBTI、问卷兴趣、点赞/收藏行为、相似用户互动、帖子新鲜度与互动质量综合排序。
- 推荐候选池限定为公开、未删除、全站帖子，并保留置顶帖优先级。
- 当用户互动数据不足时，推荐算法降低行为权重，更多依赖画像与内容新鲜度。

帖内投票说明：
- `POST /api/v1/forum/posts` 的 `pollOptions` 创建投票选项，选项文本长度与数量在接口层校验。
- `POST /api/v1/forum/posts/:postId/poll/vote` 使用 `optionId` 投票；同一 `postId + userId` 只能成功写入一次。
- 投票后同步更新选项 `vote_count`，详情页返回用户已投选项与最新计数。

评论置顶说明：
- `PUT /api/v1/forum/posts/:postId/pinned-comment` 将指定一级评论写入帖子 `pinned_comment_id`。
- `DELETE /api/v1/forum/posts/:postId/pinned-comment` 清空当前置顶评论。
- 被置顶评论删除后，详情展示层必须忽略该置顶状态，避免已删除内容被顶置曝光。

私信与关注接口：
- `GET /api/v1/social/follows/:userId`
- `GET /api/v1/social/follows`
- `POST /api/v1/social/follows/:userId`
- `DELETE /api/v1/social/follows/:userId`
- `GET /api/v1/social/messages/privacy`
- `PUT /api/v1/social/messages/privacy`
- `GET /api/v1/social/messages`
- `GET /api/v1/social/messages/eligibility/:userId`
- `GET /api/v1/social/messages/:userId`
- `POST /api/v1/social/messages/:userId`

私信规则说明：
- 会话按用户对唯一化，避免双方重复创建多个会话。
- 发送前校验拉黑关系、目标用户私信隐私设置和发送频率。
- 私信列表按 `last_message_at` 倒序，消息明细支持基于 `before` 的分页读取。

### 5.3 组队同步到论坛
`POST /api/v1/forum/teamups/sync`

用途：圈子组队侧在组队创建/状态变化时同步到论坛，系统使用 `leaderId` 作为帖子作者创建或更新 `squad` 帖。

请求体（按当前圈子组建议；后续如字段有变动，以圈子正式契约为准）：

```json
{
  "id": "teamup-uuid",
  "circleId": "circle-uuid",
  "leaderId": "user-uuid",
  "title": "周末仙林羽毛球双打",
  "descriptionPreview": "周六下午，水平不限，场地 AA。",
  "maxMembers": 4,
  "currentMemberCount": 2,
  "deadlineAt": "2026-05-02T12:00:00Z",
  "endAt": "2026-05-02T15:00:00Z",
  "joinMode": "approval",
  "isPublic": true,
  "status": "recruiting",
  "effectiveStatus": "recruiting",
  "joinable": true,
  "leader": {
    "userId": "user-uuid",
    "nickname": "小南",
    "avatarUrl": null
  }
}
```

落库与映射规则：
- 幂等键：`teamup.id`（重复调用执行更新，不重复创建帖子）。
- 帖子类型固定 `type=squad`，`circle_id=teamup.circleId`，`user_id=teamup.leaderId`。
- 帖子正文由 `descriptionPreview + 结构化组队信息` 组成（成员数、截止时间、加入方式、可加入状态）。
- `status/effectiveStatus/joinable` 变化时，同步更新帖子展示标签。

示例响应：

```json
{
  "message": "teamup synced",
  "teamupId": "teamup-uuid",
  "postId": "forum-post-uuid",
  "action": "created"
}
```

### 5.4 组队帖点击后的导航规则
- 打开组队帖详情时，后端返回行动元信息：
  - `needJoinCircle: boolean`
  - `joinable: boolean`
  - `teamupId`
  - `circleId`
- 前端处理：
  1. `needJoinCircle=true`：先跳圈子加入流程（join 成功后回跳帖子详情或直接进组队加入页）。
  2. `needJoinCircle=false && joinable=true`：可直接发起加入组队。
  3. `joinable=false`：展示截止/已满员/已结束状态，不显示加入按钮。

### 5.5 信用分接口

#### 5.5.1 组队截止后自动扣分
`POST /api/v1/forum/credit/teamups/:teamupId/deadline-penalty`

用途：由定时任务或组队状态机在截止后触发，对命中的成员执行信用分扣减。

请求体示例：

```json
{
  "triggerAt": "2026-05-02T12:05:00Z",
  "policyCode": "TEAMUP_DEADLINE_NO_SHOW_V1",
  "targets": [
    { "userId": "u1", "scoreDelta": -5, "reason": "报名后未按规则确认" }
  ]
}
```

关键规则：
- 同一 `teamupId + policyCode + userId` 必须幂等。
- 记录 `forum_credit_events` 与 `audit_logs`。

#### 5.5.2 活动结束后同组成员举报
`POST /api/v1/forum/credit/teamups/:teamupId/member-reports`

用途：活动结束后，同组成员可对同组对象提交行为举报，进入治理审核并联动信用分处理。

请求体示例：

```json
{
  "reportedUserId": "u2",
  "reason": "no_show",
  "detail": "活动开始后失联",
  "evidences": ["https://.../proof1.png"]
}
```

关键规则：
- 仅允许同组成员且活动结束后提交。
- 先写举报工单（`pending`），审核后再决定是否扣分。
- 举报结果通过既有治理通知链路回传。

### 5.6 敏感词治理接口
- `POST /api/v1/forum/posts`、`POST /api/v1/forum/posts/:postId/comments`：
  - 在创建前执行内容审核；
  - 返回可区分结果：`published`、`published_with_replacement`、`pending_review`、`blocked`。
- `GET /api/v1/admin/forum/moderation/queue`：
  - 管理端查看待审核内容列表。
- `PATCH /api/v1/admin/forum/moderation/:id`：
  - 管理员执行 `approve|reject|replace` 审核动作。

说明：
- 若本迭代不新增管理端审核接口，至少保留 `content_moderation_logs` 与 `blocked/pending_review` 状态，后续可平滑接入。

## 7. 关键流程

### 7.1 普通发帖流程（含内容审核）
1. 前端提交帖子数据。
2. 后端校验登录态、参数、圈子成员权限。
3. `ContentModerationService` 执行规范化与敏感词匹配。
4. 命中后按等级处置（拦截 / 替换发布 / 待审核）。
5. 通过后创建帖子、图片、投票选项与计数初始化。
6. 发布成功后前端清理本地草稿；若用户关闭编辑器，可选择把当前输入保存到本机草稿。

### 7.2 组队同步流程
1. 圈子组队服务调用 `/forum/teamups/sync`。
2. 论坛侧按 `teamupId` 查绑定关系并创建或更新 `squad` 帖。
3. 返回 `postId`，供圈子侧跳转或关联。

### 7.3 组队信用分流程
1. 截止触发自动扣分接口，落账本和审计。
2. 活动结束后同组成员可提交举报。
3. 管理端审核举报后执行最终扣分/驳回。

### 7.4 组队帖导航流程
1. 用户进入组队帖详情。
2. 后端返回 `needJoinCircle` 与 `joinable`。
3. 前端按“先入圈再入队”规则分流，确保权限与体验一致。

互动与推荐补充流程：
1. 用户点赞、收藏、评论、投票或浏览帖子后，后端更新对应业务表与帖子计数字段。
2. 热度分随互动更新，并用于 `sort=hot` 与热度榜。
3. 推荐流请求 `sort=recommended` 时，后端读取用户画像、问卷兴趣和历史互动，计算候选帖推荐分。
4. 推荐结果仍经过删除状态、可见性、圈子边界与置顶优先级过滤。

私信补充流程：
1. 用户从个人资料、关注列表或论坛作者入口进入私信前，先请求私信资格。
2. 后端根据拉黑关系、关注关系和目标用户隐私设置返回是否可发送。
3. 发送消息时按用户对创建或复用会话，写入 `direct_messages` 并更新会话 `last_message_at`。
4. 接收方读取会话后更新 `read_at`，用于未读状态统计。

## 8. 开发落地建议

1. 先落论坛主接口与页面（列表、详情、评论、软删除）。
2. 接入管理端帖子治理（删帖、置顶、审计）。
3. 补齐发帖草稿、评论置顶、帖内投票、点赞/收藏/热度榜与推荐排序。
4. 实现关注/私信接口与隐私设置，确保拉黑、关注关系和私信资格判断一致。
5. 实现组队同步接口与 `forum_teamup_bindings`。
6. 实现信用分两个接口与 `forum_credit_events`。
7. 联调圈子入口：`/forum?circleId=...` 与 `/forum/new?circleId=...&type=squad`。

联调重点：
- `circleId` 解释一致。
- `teamupId` 同步幂等。
- 组队帖点击导航与入圈流程打通。
- 举报/拉黑保持可用，不抢论坛主线篇幅。
- 推荐流、热度榜、管理置顶、评论置顶之间的排序优先级一致。
- 投票、点赞、收藏等互动必须幂等，刷新页面后状态不丢失。
- 私信必须尊重拉黑、关注关系和目标用户隐私设置。

## 9. 演进说明

- 当前阶段保持单体实现，优先功能闭环。
- 当组队同步与信用分事件规模增大时，可将 `TeamupSyncService` 与 `CreditService` 内部服务化。
- 当敏感词命中规模增大时，可将 `ContentModerationService` 独立为内容安全子服务，并接入缓存与异步审核队列。
- 当推荐请求量增大时，可将推荐候选集和热度分更新拆成异步任务或缓存层，避免列表查询承担过多实时计算。
- 当私信规模增大时，可引入消息推送、会话未读数缓存和更细粒度的反垃圾策略。

## 10. 实施优先级与验收口径（新增）

### 10.1 P2 阶段建议优先级
1. 先完成论坛主链路最小闭环：帖子列表/发帖/详情/评论/软删除。
2. 接入管理端帖子治理：删帖、置顶、治理审计记录。
3. 再落组队同步与信用分扩展接口，避免主链路被扩展需求阻塞。

### 10.2 验收口径（与当前项目匹配）
- 功能口径：
  - 圈子与全站论坛可通过 `circleId` 正确区分；
  - 软删除后前台不可见，管理端可审计回溯；
  - 草稿保存与恢复不影响后端发布状态，发布成功后草稿被清理；
  - 评论置顶只展示未删除的一级评论，投票保持一人一票；
  - 推荐流、热度榜和普通列表均不泄露私密帖、圈内帖或已删除帖子；
  - 私信发送符合对方隐私设置、关注关系与拉黑关系约束；
  - 举报与拉黑能力不回归、不破坏现有联调链路。
- 工程口径：
  - 路由边界保持在 `/api/v1/forum/*`、`/api/v1/admin/forum/*`、`/api/v1/admin/reports/*`、`/api/v1/user/report|block/*`；
  - 关注与私信路由保持在 `/api/v1/social/*`，不混入论坛帖子治理接口；
  - 新增治理动作必须写 `audit_logs`；
  - 普通互动动作通过唯一约束和事务保证幂等与计数一致；
  - 论坛规则校验以后端为准，不依赖前端按钮隐藏。
