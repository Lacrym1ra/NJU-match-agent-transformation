# 2-架构辩论赛记录

## 一、成员 A（直接提问：推荐什么架构）

### Prompt A
开发一个校园社交互助平台的“论坛与治理子系统”（包含富文本发帖、多级评论、前台匿名马甲机制、闭环举报流程、阳光值信用分管理、阶梯式账号封禁以及行为审计日志等功能），推荐采用什么架构？

### AI 回答摘要
- 给出三类方案：分层单体、微服务、事件驱动（辅助）。
- 结论建议为：**模块化单体 + 异步事件驱动**。
- 主要理由：
  - 小团队直接上微服务风险高、复杂度高；
  - 论坛主链路（发帖/评论/浏览）保持同步，治理链路（阳光值、审计、举报处理）异步解耦；
  - 通过逻辑分层和数据隔离（核心业务库 vs 安全审计库）兼顾效率与安全。

## 二、成员 B（提供详细约束后提问）

### Prompt B
- 先要求 AI 从 SRS 中提取硬约束：性能、匿名隐私、合规留存、治理时效。
- 再让 AI 输出“后端开发红线清单”：接口脱敏、状态机一致性、防篡改、封禁令牌失效、审计日志不可删改。
- 最后要求面向测试/运营整理“阳光值与举报闭环”业务约束。

### AI 回答摘要
- 明确了可执行的硬指标：
  - Feed 首屏 < 1.0s，发帖 QPS > 500；
  - 前台匿名、后台实名，真实 ID 独立加密存储并严格权限控制；
  - 软删除数据保留 180 天，敏感管理操作必须审计。
- 对后端实现给出红线：
  - DAO/Service 层统一脱敏；
  - 举报触发时生成原始快照，防二次编辑篡改证据；
  - 封禁时强制使当前 Token 失效；
  - 审计日志 append-only，不允许单点人工删除。
- 对治理流程给出可测规则：
  - 举报 24h 必须闭环；
  - 必须站内信反馈举报人；
  - 阳光值阶梯惩罚阈值清晰（<60、<30）。

## 三、成员 C（要求对比多方案优劣）

### Prompt C
要求 AI 以“系统架构师”视角，对比：
1. 单体 + 集中式数据库  
2. 微服务（论坛、隐私溯源、治理审计拆分）  
3. Serverless/FaaS  
并按数据安全、性能扩展、交付效率、运维复杂度四维评估，给最终推荐和缺点应对。

### AI 回答摘要
- 对比结果：
  - **隐私隔离与审计可靠性**：微服务更优；
  - **开发效率**：单体更优；
  - **Serverless**：冷启动与本地调试复杂，不适合本项目当前阶段。
- 最终推荐：**模块化单体（当前）+ 微服务演进（中后期）**。
- 配套建议：
  - 先做严格模块边界和数据边界；
  - 预留 Forum / Vest / Audit 拆分路径；
  - 引入 RBAC 与服务间认证，降低后期改造成本。

## 四、成员 D（角色扮演：让 AI 输出“可落地决策过程”）

### Prompt D
- 要求 AI 扮演“首席架构师”，不能只给结论，必须给出完整决策路径。
- 明确四类刚性约束：
  - Feed 高并发（QPS > 500，首屏 < 1s）；
  - 前台匿名/后台实名，真实身份映射高敏隔离；
  - 举报闭环、阳光值惩戒、封禁与审计不可篡改；
  - 学生团队、交付周期紧、Docker 本地联调可控。
- 强制输出六部分：
  - 目标优先级；
  - 模块边界（内容域/身份域/治理域/审计域）；
  - 数据与权限隔离；
  - 同步与异步链路划分；
  - 三阶段演进路线；
  - 当前“做什么/不做什么”及风险缓解。

### AI 回答摘要
- 给出明确架构决策：**模块化单体 + 事件驱动治理链路 + 敏感数据独立库**。
- 形成“优先级驱动”的取舍顺序：
  - P0 隐私与审计合规；
  - P1 主链路性能；
  - P2 交付效率；
  - P3 演进弹性。
- 在单体内按微服务思路先固化边界：
  - Content（帖子/评论/Feed）；
  - Vest/Identity（马甲映射）；
  - Governance（举报/阳光值/处罚状态机）；
  - Audit（管理动作与治理日志）。
- 落地约束强调“先防事故”而非“先堆技术”：
  - 模块间仅允许经 Service 接口调用，禁止跨域直连表；
  - `vest_mapping` 高权限隔离，前台 DTO 全链路脱敏；
  - 审计日志 append-only，数据库权限层禁改删；
  - 主流程同步、治理流程异步，兼顾体验和闭环。
- 给出可执行演进路线：
  - 阶段1：模块化单体上线并补齐治理闭环；
  - 阶段2：优先拆治理/审计消费端；
  - 阶段3：按流量与安全压力拆 Vest/Forum 服务并统一鉴权。
- 明确阶段性“不做清单”：
  - 暂不引入服务网格、复杂分布式事务、全量 Serverless、多地域部署。
- 明确风险与缓解：
  - 拆分困难 -> 先定义领域接口和事件契约；
  - 异步可观测性不足 -> 事件 ID、重试、死信队列；
  - 审计越权风险 -> 最小权限 + 独立审计账号。

### D 视角增量价值
- 相比 A/B/C，D 的价值不在“再给一个架构名词”，而在于补齐了：
  - **决策顺序**（先解决什么）；
  - **阶段边界**（现在做与不做）；
  - **风险前置**（已知风险对应可执行缓解动作）。
- 这使团队在实现时更容易避免“过度设计”与“后期推倒重来”。

## 五、团队辩论结论（30 分钟）

### 1）最终选择
团队投票后选择：**模块化单体 + 局部事件驱动 + 敏感数据隔离设计（并预留微服务演进路径）**。

### 2）选择原因
- 兼顾当前交付效率与后续扩展能力；
- 能直接满足 SRS 的核心硬约束：匿名隔离、治理闭环、审计留痕、性能目标；
- 与团队能力匹配，本地 Docker 联调和排障成本可控；
- 为后续拆分治理/审计/身份模块保留了技术路径，避免重构推倒重来。

### 3）为什么不选其他方案
- **不选“纯单体（无模块边界）”**：短期快，但后续扩展与安全隔离代价高，容易形成耦合泥团。
- **不选“一步到位全微服务”**：服务治理、分布式一致性、联调复杂度对当前团队过重。
- **不选“全量 Serverless”**：冷启动、调试与可观测性成本较高，且对稳定低延迟主链路不友好。

### 4）Prompt 策略差异复盘
- A（直接问）给出方向快，但约束细节不足；
- B（带约束）输出最“可执行”，便于研发与测试落地；
- C（多方案对比）最适合做架构选型辩论；
- D（角色扮演）最适合沉淀“分阶段实施路线”和“现在不做什么”的决策边界。
