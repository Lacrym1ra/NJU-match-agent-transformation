## 2. AI 助力分析（Q1）
本阶段 AI 最大的贡献是：把“架构争论”快速收敛成可执行产物，包括统一术语、约束清单、分阶段路线和 ADR 初稿，显著降低了团队在文档组织与选型表达上的时间成本。
不同 Prompt 策略下 AI 回答质量的差异：直接提问（A）适合快速定方向；约束驱动（B）产出最可执行，能直接转为开发与测试条目；方案对比（C）最适合辩论和评审；角色扮演（D）最适合沉淀“决策过程、风险与边界”。

## 3. AI 误导分析（Q2）
AI 在架构建议中的典型问题：
- 问题1：AI 容易把“设计方案”说成“已实现功能”。如何发现：对照仓库路由与文档时，发现 `/api/v1/forum/*` 在设计稿中完整存在，但代码里尚未注册同等接口。如何修正：在架构文档中新增“当前代码现状校准”段，明确“已落地 / 设计先行”边界，所有接口标注实现状态。
- 问题2：AI 倾向过早引入复杂架构（微服务、消息队列、服务网格）。如何发现：建议中包含与当前学生团队交付周期不匹配的运维组件，且仓库部署仍以 Docker Compose 单体为主。如何修正：把决策改为“模块化单体优先 + 演进预留”，并在文档写明“当前不做项”和触发升级条件。
- 问题3：AI 会混淆治理对象边界（举报用户 vs 举报帖子/评论）。如何发现：现有实现是 `user_reports`（用户举报），但建议里多次默认成内容举报工单。如何修正：按现有 schema 与 API 先固化用户举报闭环；内容级举报作为后续扩展单列，不与当前接口混写。

## 4. Prompt 改进计划（Q3）
上阶段（P1）提出的改进措施，验证结果：有效。将“先给约束、再要结论”作为默认提问方式后，AI 输出的可落地性明显提升，返工主要从“推翻结论”转为“细化实现”。
本阶段新的改进措施：  
1. 统一采用“三段式 Prompt”：`项目现状（已实现）+ 硬约束 + 期望输出格式`。  
2. 在 Prompt 中强制 AI 标注“已实现 / 设计建议 / 暂不做”，避免状态混淆。  
3. 要求 AI 给出“反例与不推荐项”，防止只给理想方案。  
4. 输出后固定执行一次“代码对照复核”（路由、schema、迁移、部署方式）。  
5. ADR 生成时强制补“负面后果与监控点”，避免只有正面叙事。

## 5. 本阶段的核心工程判断
决策内容：论坛与治理子系统在 P2 采用“模块化单体 + 局部事件驱动 + 敏感数据隔离”，并把论坛主链路闭环（帖子/评论/治理）放在优先级第一位，组队同步与信用分扩展放在第二阶段。
为什么 AI 无法做这个决策：该决策依赖本项目真实约束（当前代码完成度、团队实现能力、联调窗口、课程周期、已有接口兼容成本），这些上下文和取舍责任只有团队自己能最终承担；AI 可以提供备选方案与风险清单，但不能替代项目责任人做最终 trade-off。
