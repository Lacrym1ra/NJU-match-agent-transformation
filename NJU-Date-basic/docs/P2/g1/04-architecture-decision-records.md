# ADR 记录

## ADR-001：采用前后端分离的模块化分层单体架构

### 状态

已接受

### 背景

第一组负责的功能覆盖认证、用户资料、问卷、匹配、揭晓、历史、匿名心意、双向确认、站内消息、举报/拉黑和通知提醒。业务链路相互依赖较强，尤其是用户资料、问卷答案和匹配结果之间需要一致的数据视图。项目周期为课程 10 周左右，团队需要优先保证可运行系统交付。

### 决策

我们决定采用：**前后端分离 + 后端模块化分层单体架构**。

后端内部按 Routes / Controllers / Zod Schema / Services / Repositories / Infrastructure Providers 分层组织。

### 理由

1. 与 Node.js 20+、Express.js、TypeScript、PostgreSQL、Drizzle 的技术栈匹配。
2. 单体内部调用可以降低模块通信成本，利于短周期交付。
3. Service 层能承载匹配算法、问卷版本、消息通知等复杂业务规则。
4. Repository 层统一封装数据库访问，避免 SQL 和业务规则散落在 Controller。
5. 模块边界清晰，未来可按 Match、Notification、AI Provider 等方向拆分服务。

### 后果

- 正面影响：实现成本可控，数据一致性更容易保证，团队学习成本低。
- 负面影响：所有模块部署在一个后端服务中，单服务故障可能影响整体 API。
- 需要关注的风险：随着代码规模增大，必须严格防止 Controller 过厚和跨模块随意访问 Repository。

### AI 辅助记录

#### AI 初稿内容摘要

AI 初稿建议“使用分层架构，Controller 处理请求，Service 处理业务，Repository 处理数据库；未来可以演进为微服务”。

#### 人工修订内容

```diff
- 采用普通分层架构即可，后续可以考虑微服务。
+ 采用前后端分离的模块化分层单体架构。
+ 明确后端内部层次为 Routes / Controllers / Zod Schema / Services / Repositories / Infrastructure Providers。
+ 明确不在当前阶段采用微服务，因为认证、问卷、匹配和通知共享强一致数据边界。
+ 明确 Jobs 只能调用 Service，不能直接访问 Repository。
```

#### 修订理由

AI 初稿方向正确，但没有充分强调课程周期、数据一致性和模块依赖边界。人工修订后，架构决策更贴近第一组实际交付范围。

## ADR-002：采用 PostgreSQL 16 + Drizzle ORM 作为核心数据访问方案

### 状态

已接受

### 背景

系统需要维护用户账号、个人资料、参与状态、问卷版本、问卷答案、匹配批次、匹配结果、历史记录、匿名心意、双向确认、站内消息、举报和拉黑等结构化数据。匹配生成、结果锁定和消息创建之间存在事务一致性要求。

### 决策

我们决定采用 **PostgreSQL 16** 作为唯一核心业务数据库，采用 **Drizzle ORM** 作为 TypeScript 数据访问层。

### 理由

1. PostgreSQL 支持事务、索引、约束和复杂查询，适合匹配类系统的数据模型。
2. 问卷答案、匹配结果和通知记录之间可以通过事务保持一致。
3. Drizzle ORM 类型安全、轻量、原生 SQL 友好，适合 TypeScript 项目。
4. 单数据库方案降低开发、部署和调试复杂度。
5. 当前没有必须引入 NoSQL 或缓存数据库的强需求。

### 后果

- 正面影响：数据模型统一，事务清晰，便于迁移和测试。
- 负面影响：复杂统计或高并发读场景可能对 PostgreSQL 形成压力。
- 需要关注的风险：需要合理设计索引，例如 user_id、match_run_id、notification user_id/read_at、survey_version_id 等字段。

### AI 辅助记录

#### AI 初稿内容摘要

AI 初稿建议“使用 PostgreSQL 或 MySQL，ORM 可以选择 Prisma 或 Drizzle；如果需要缓存可以加 Redis”。

#### 人工修订内容

```diff
- 数据库可以选择 PostgreSQL 或 MySQL，ORM 可以选择 Prisma 或 Drizzle。
- 后续可以加 Redis 缓存提升性能。
+ 数据库确定采用 PostgreSQL 16，ORM 确定采用 Drizzle ORM。
+ 当前阶段不引入 Redis，优先用 PostgreSQL 事务和索引满足业务需求。
+ 将问卷答案、匹配结果、站内消息、举报拉黑等数据统一放在 PostgreSQL 中。
+ 在 MatchService 生成匹配结果和 NotificationService 创建站内消息时关注事务边界。
```

#### 修订理由

AI 初稿给了多个可选项，但项目已经有明确技术选型。人工修订将“候选建议”收敛为“最终决策”，并补充了事务一致性和索引风险。

## ADR-003：采用 JWT 进行无状态认证

### 状态

已接受

### 背景

系统需要支持注册、登录、找回密码、身份认证和前端页面访问控制。前端通过 API 调用后端，后端需要识别当前用户并保护 `/user/*`、`/survey/*`、`/match/*`、`/notifications/*` 等接口。

### 决策

我们决定采用 **JWT（jsonwebtoken）** 进行无状态认证。登录成功后后端签发 JWT，前端在请求头中携带：

```http
Authorization: Bearer <token>
```

### 理由

1. JWT 与前后端分离架构匹配，不依赖服务端 Session 存储。
2. Express 中间件可以统一解析 token 并注入 userId。
3. 对课程项目而言，实现简单、学习成本低。
4. TypeScript 中可定义统一的 AuthContext 类型，减少接口层重复逻辑。

### 后果

- 正面影响：后端无状态，接口鉴权实现简单，前端集成成本低。
- 负面影响：token 一旦签发，在过期前默认难以强制失效。
- 需要关注的风险：需要设置合理过期时间；密码找回、封禁、敏感操作后可选引入 tokenVersion 或 token blacklist。

### AI 辅助记录

#### AI 初稿内容摘要

AI 初稿建议“用 JWT 做登录态，保存 token 到 localStorage，所有接口带上 Bearer token”。

#### 人工修订内容

```diff
- 前端可以把 JWT 存到 localStorage。
+ 本 ADR 只决策后端认证方案为 JWT，不强制规定前端存储位置。
+ 后端必须设置 token 过期时间，并在中间件统一验证。
+ 对找回密码、封禁或高风险场景，预留 tokenVersion / blacklist 机制。
+ 所有 /user/*、/survey/*、/match/*、/notifications/* 默认需要鉴权。
```

#### 修订理由

AI 初稿忽略了 token 存储安全与失效风险。人工修订将重点放在后端架构决策，并补充安全风险和未来增强方案。

## ADR-004：采用站内消息中心为主、邮件 Provider 为辅的通知架构

### 状态

已接受

### 背景

第一组负责站内消息中心，包括消息列表、未读/已读、红点/角标，并负责与主线相关的通知提醒。同时已有 `PATCH /user/notifications` 表示邮件提醒开关，但它不等同于站内消息中心。系统还需要发送 OTP 验证码及匹配通知邮件。

### 决策

我们决定将通知拆分为两个层次：

1. **站内消息中心**：由 Notifications 模块维护，数据持久化到 PostgreSQL，提供 `/notifications/*` 接口。
2. **邮件发送能力**：由 MailProvider 封装 Nodemailer SMTP 与阿里云 DirectMail，仅作为外部通知渠道。

### 理由

1. 站内消息是产品功能，邮件是通知渠道，两者职责不同。
2. 未读数、已读状态、红点/角标必须依赖数据库持久化。
3. 邮件发送可能失败，不应影响站内消息落库。
4. 双 Provider 邮件方案可以降低 SMTP 或 DirectMail 单点不可用风险。

### 后果

- 正面影响：消息中心边界清晰，前端可以稳定获取消息列表和未读数。
- 负面影响：同一业务事件可能同时涉及站内消息和邮件发送，需要处理部分成功情况。
- 需要关注的风险：邮件重试、发送日志和幂等机制需要逐步完善。

### AI 辅助记录

#### AI 初稿内容摘要

AI 初稿建议“建立 NotificationService，发送站内通知和邮件通知；用户可以开启或关闭通知”。

#### 人工修订内容

```diff
- NotificationService 同时负责站内通知和邮件通知，用户可以开启/关闭通知。
+ NotificationService 负责站内消息中心，包括消息列表、已读/未读、红点/角标。
+ MailProvider 只负责邮件发送，不直接代表站内消息。
+ PATCH /user/notifications 只表示邮件提醒开关，不等同于 /notifications/*。
+ 邮件失败不回滚站内消息落库；必要时记录发送失败状态。
```

#### 修订理由

AI 初稿混淆了“产品内消息”和“邮件提醒渠道”。人工修订明确了接口边界，避免后续实现时把邮件开关误当作消息中心。

## ADR-005：采用 node-cron 承担短周期定时任务

### 状态

已接受

### 背景

系统需要在固定时间触发主线流程，例如周二提醒、周三匹配与解锁、周五过期等。当前技术选型中已确定使用 node-cron。项目部署方式为 Docker Compose，短期内没有复杂分布式调度需求。

### 决策

我们决定采用 **node-cron** 在后端服务内执行轻量定时任务。定时任务只负责触发流程，具体业务逻辑放在 MatchService、NotificationService 和 MailProvider 中。

### 理由

1. node-cron 实现简单，符合课程项目交付节奏。
2. 当前只有少量固定周期任务，不需要引入独立调度平台。
3. 与 Express 后端同进程部署，Docker Compose 配置简单。
4. 通过调用 Service 可以复用业务逻辑，避免任务脚本与 API 逻辑不一致。

### 后果

- 正面影响：实现成本低，易于本地开发和联调。
- 负面影响：如果后端多实例部署，可能重复执行任务。
- 需要关注的风险：需要增加任务幂等设计，例如按 match_run 的周期唯一键避免重复匹配。

### AI 辅助记录

#### AI 初稿内容摘要

AI 初稿建议“用 node-cron 设置周二、周三、周五任务，分别发送提醒、生成匹配、处理过期”。

#### 人工修订内容

```diff
- node-cron 定时执行提醒、匹配和过期处理即可。
+ node-cron 只作为触发器，业务逻辑必须放入 Service。
+ 周期性匹配必须设计幂等键，避免重复生成同一周期 match_run。
+ 后续如果多实例部署，需要改为单独调度器、数据库锁或队列方案。
+ 任务执行需要记录日志，便于排查匹配或通知失败。
```

#### 修订理由

AI 初稿只覆盖实现方式，遗漏了重复执行、幂等和多实例部署风险。人工修订补充了工程质量属性权衡。
