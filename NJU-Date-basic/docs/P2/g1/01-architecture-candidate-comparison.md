# 架构候选方案对比表

## 1. 项目功能与约束

第一组负责的业务范围包括：

- 账号与身份：注册、登录、找回密码、身份认证。
- 用户主线：个人资料、参与状态、建档流程。
- 问卷主线：灵魂问卷、答案保存、问卷版本管理。
- 匹配主线：主匹配算法、结果生成、锁定与揭晓、历史记录、未成功提示。
- 互动主线：匿名心意表达、双向意向确认。
- 通知与安全：站内消息中心、主线通知提醒、举报与拉黑入口。

由此可以得到几个架构约束：

1. **业务链路连续性强**：用户资料、问卷答案、匹配结果、揭晓与通知之间存在明显的顺序依赖。
2. **数据一致性要求较高**：匹配结果生成、锁定、历史记录和通知创建需要避免状态不一致。
3. **团队周期有限**：课程项目需要在 10 周内完成可运行交付，人均工时也有限。
4. **模块边界需要清楚**：认证、用户、问卷、匹配、通知等职责需要分开，避免后期功能堆叠。
5. **未来需要可扩展**：当前优先交付，但匹配算法、通知机制、AI 文案等能力后续可能演进。

## 2. 候选架构方案

本次比较三种候选架构风格：

- **方案 A：前后端分离 + 后端模块化分层单体架构**  
  前端负责页面和交互，后端作为 API 服务；后端内部按模块划分，并在每个模块内区分接口层、业务层、数据访问层和基础设施适配层。

- **方案 B：传统 MVC 架构**  
  系统以 Model、View、Controller 为核心组织。Controller 处理请求，Model 处理数据，View 处理页面展示或页面模型。

- **方案 C：微服务 / 事件驱动架构**  
  将认证、用户、问卷、匹配、通知等拆为独立服务，通过同步 API 或异步事件协作；通知、匹配等流程可通过事件驱动串联。

## 3. 多维度对比表

| 对比维度 | 方案 A：模块化分层单体 | 方案 B：传统 MVC | 方案 C：微服务 / 事件驱动 |
|---|---|---|---|
| 开发复杂度 | 中等。需要先定义模块边界和层次职责，但实现路径清晰。 | 较低。适合快速开发小型应用，但复杂业务容易写进 Controller。 | 高。需要服务拆分、服务通信、事件投递、部署编排和故障处理。 |
| 可维护性 | 高。认证、用户、问卷、匹配、通知可分别维护，业务规则沉淀在业务层。 | 中。早期简单，但匹配算法、问卷版本、通知状态增加后，控制层容易膨胀。 | 理论上高，但需要成熟的服务治理能力，否则维护成本反而上升。 |
| 可扩展性 | 中高。先保持单体部署，内部边界清楚，后续可按模块拆分。 | 中。模块边界较弱，后续拆分成本较高。 | 高。服务可独立扩展，事件链路适合通知、匹配等异步流程。 |
| 性能 | 较好。单体内部调用成本低，适合当前业务规模。 | 较好。实现简单，运行开销低。 | 不确定。可横向扩展，但网络调用、消息投递和一致性处理会增加延迟。 |
| 团队学习成本 | 低到中。分层和模块化概念容易理解，适合课程团队协作。 | 低。概念熟悉，但对前后端分离 API 服务的表达不够精确。 | 高。需要掌握服务治理、消息机制、幂等、最终一致性和监控。 |
| 数据一致性 | 较易保证。关键业务可在同一数据库事务边界内完成。 | 较易保证，但数据访问和业务规则可能分散。 | 较难。跨服务数据一致性需要事件补偿或最终一致性设计。 |
| 与功能范围匹配度 | 高。认证、用户、问卷、匹配、通知天然可以形成模块。 | 中。适合页面驱动，但本项目更偏 API 与业务流程驱动。 | 中。通知和匹配适合事件化，但整体拆分过早。 |
| 测试便利性 | 高。可分别测试校验、业务规则、数据访问和定时流程。 | 中。若 Controller 过厚，单元测试不够聚焦。 | 中。单服务测试方便，但跨服务联调和端到端测试复杂。 |
| 部署难度 | 低。可以一个后端服务配合数据库部署。 | 低。部署方式简单。 | 高。多服务、多进程、消息队列和监控链路增加部署成本。 |
| 10 周内可行性 | 高。能兼顾边界清晰和交付效率。 | 中高。能完成基础功能，但复杂业务沉淀风险较高。 | 低。架构复杂度超过当前课程项目收益。 |

## 4. 结论

最终选择：**方案 A：前后端分离 + 后端模块化分层单体架构**。

该方案不是因为某个具体技术栈已经确定才被选择，而是由项目功能范围、工期、团队学习成本、数据一致性和可维护性要求共同推导得到。后续的技术选型需要服务于这一架构选择：应优先选择轻量、类型安全、易部署、便于模块化组织和事务处理的技术组合。
