# “架构辩论赛”记录

## 1. 实验目标

通过 4 位成员使用不同 Prompt 策略向 AI 咨询架构建议，观察 AI 回答质量差异，并结合项目真实约束完成架构风格选择。

本实验只讨论架构风格，不提前确定具体技术栈。技术栈应在架构风格确定后，再作为架构设计文档中的落地结果说明。

项目约束摘要：

- 第一组负责认证、用户资料、问卷、匹配、揭晓、历史、匿名心意、双向确认、站内消息、举报/拉黑入口和主线通知。
- 项目需要在课程周期内完成可运行系统，团队总工时有限。
- 匹配、问卷、用户资料、通知之间存在较强主线依赖，需要关注数据一致性、模块边界和可维护性。
- 候选架构主要包括 MVC、分层架构、微服务和事件驱动架构。

## 2. 成员 A：直接询问推荐架构

### 2.1 Prompt

```text
我们要做一个包含登录、用户资料、问卷、匹配、通知消息的 Web 系统。推荐什么软件架构？
```

### 2.2 AI 回答摘要

AI 推荐可以使用 MVC 或分层架构，并提到如果未来规模扩大可以考虑微服务。回答强调：

- MVC 容易理解，上手快。
- 分层架构适合业务逻辑较清晰的系统。
- 微服务适合复杂系统，但当前可能过度。
- 建议先使用单体架构，后续再拆分。

### 2.3 质量评价

| 维度 | 评价 |
|---|---|
| 优点 | 给出了常见架构选项，方向基本正确。 |
| 不足 | 没有结合课程周期、团队学习成本、匹配业务复杂度和数据一致性要求。 |
| AI 输出质量 | 3/5 |
| 人工修改幅度 | 45% |

## 3. 成员 B：提供详细项目约束后询问

### 3.1 Prompt

```text
我们是课程项目第一组，10 周内要完成一个 Web 系统。第一组负责注册登录、找回、身份认证、用户资料、参与状态、灵魂问卷、答案保存、问卷版本管理、主匹配算法、匹配结果生成、锁定与揭晓、历史记录、匿名心意表达、双向意向确认、站内消息中心、用户举报/拉黑入口和通知提醒。请推荐适合的架构风格。
```

### 3.2 AI 回答摘要

AI 推荐模块化分层单体架构。理由包括：

- 认证、用户、问卷、匹配和通知属于同一业务主线，适合在单体内保持统一边界。
- 分层可以把输入处理、业务规则和数据访问分开，降低后续维护成本。
- 微服务和事件驱动会增加服务通信、部署和一致性复杂度。
- MVC 虽然简单，但复杂业务增长后容易出现控制层职责过重。

### 3.3 质量评价

| 维度 | 评价 |
|---|---|
| 优点 | 明确结合业务范围和课程周期，能解释为什么分层架构更适合当前阶段。 |
| 不足 | 对站内消息、邮件提醒、系统通知之间的边界仍然较粗，需要人工补充。 |
| AI 输出质量 | 4/5 |
| 人工修改幅度 | 25% |

## 4. 成员 C：要求对比多种方案优劣

### 4.1 Prompt

```text
请对比 MVC、分层架构、微服务架构、事件驱动架构在一个包含认证、用户资料、问卷、匹配算法、通知消息和举报拉黑模块的 Web 系统中的优劣。请从开发复杂度、可维护性、可扩展性、性能、团队学习成本、10 周内可行性和数据一致性角度做表格，并给出推荐方案。
```

### 4.2 AI 回答摘要

AI 生成了架构对比表，并给出结论：推荐分层架构。核心观点：

- MVC 简单但容易出现控制器过厚。
- 分层架构在业务复杂度和实现成本之间平衡最好。
- 微服务可扩展但不适合短周期项目。
- 事件驱动适合通知、匹配完成后的异步操作，但不建议作为整体主架构。

### 4.3 质量评价

| 维度 | 评价 |
|---|---|
| 优点 | 表格结构清晰，便于团队辩论和投票。 |
| 不足 | AI 倾向泛化描述，未自动识别“匹配结果锁定与揭晓”对事务一致性的要求。 |
| AI 输出质量 | 4/5 |
| 人工修改幅度 | 30% |

## 5. 成员 D：让 AI 扮演架构师角色

### 5.1 Prompt

```text
请你扮演一个有交付经验的软件架构师。我们要在 10 周内完成一个匹配类 Web 系统。第一组负责认证、资料、问卷、匹配、揭晓、历史、心意表达、双向确认、站内消息、举报拉黑和通知提醒。请从架构风险、模块边界、数据一致性、未来扩展和团队执行角度给出架构建议。
```

### 5.2 AI 回答摘要

AI 从架构师视角建议采用模块化分层单体：

- 表现层负责接收请求、鉴权、参数校验和响应封装。
- 业务层承载认证、问卷、匹配、通知等核心业务规则。
- 数据访问层集中处理持久化逻辑，避免业务代码直接散落到多个入口。
- 基础设施层接入邮件、AI、定时任务等外部能力。
- 明确提醒不要为了“架构高级感”过早引入微服务和消息队列。

AI 还指出：

- 匹配生成和通知创建最好在同一可靠边界中完成。
- 邮件发送失败不应影响站内消息落库。
- AI 生成内容应设置超时、失败降级和人工可控边界。

### 5.3 质量评价

| 维度 | 评价 |
|---|---|
| 优点 | 最贴近交付，能主动识别风险并给出工程边界。 |
| 不足 | 仍需人工根据第一组实际页面和职责范围校准模块边界。 |
| AI 输出质量 | 5/5 |
| 人工修改幅度 | 20% |

## 6. 辩论会议记录

### 6.1 会议基本信息

| 项目 | 内容 |
|---|---|
| 会议主题 | Phase 2 架构辩论赛 |
| 会议形式 | 线上讨论 |
| 会议时长 | 约 30 分钟 |
| 参与成员 | 成员 A、成员 B、成员 C、成员 D |
| 讨论目标 | 在 MVC、分层架构、微服务、事件驱动中选择最终架构风格 |

### 6.2 主要争议点

| 争议点 | 讨论内容 | 结论 |
|---|---|---|
| 是否选择 MVC | MVC 上手快，但本项目的业务规则比简单页面 CRUD 更复杂。 | 不作为主架构，只吸收控制入口概念。 |
| 是否选择微服务 | 微服务扩展性好，但会带来部署、服务通信、认证共享、数据一致性成本。 | 当前不采用。 |
| 是否选择事件驱动 | 匹配完成后通知可以异步，但当前没有必要把整体系统设计为事件驱动。 | 可作为未来演进方向，当前不作为主架构。 |
| 是否需要复杂中间件 | 当前首要目标是功能闭环、模块边界和数据一致性。 | 不把中间件作为架构选择的前提。 |
| 匹配算法放在哪里 | 匹配逻辑需要读取用户资料、问卷答案、参与状态，并生成结果和通知。 | 应作为独立业务模块处理，而不是散落在页面或控制入口中。 |
| 站内消息和外部提醒的关系 | 站内消息是系统内业务对象，外部提醒只是触达渠道。 | 二者边界应分开，避免把通知渠道等同于消息中心。 |

### 6.3 投票结果

| 方案 | 票数 | 结论 |
|---|---:|---|
| MVC | 0 | 不采用 |
| 分层架构 | 4 | 采用 |
| 微服务 | 0 | 不采用 |
| 事件驱动 | 0 | 不作为主架构 |

### 6.4 最终结论

最终选择：**前后端分离 + 后端模块化分层单体架构**。

核心理由：

1. 满足 10 周交付要求，复杂度可控。
2. 对认证、用户、问卷、匹配、通知等模块有清晰边界。
3. 能更好地维护匹配、锁定、揭晓、通知创建等核心流程的数据一致性。
4. 不把复杂中间件、服务拆分或事件链路作为短周期项目的必要前提。
5. 保留未来演进空间，后续可将匹配、通知或 AI 相关能力拆出独立服务。

## 7. Prompt 策略效果差异总结

| Prompt 策略 | 回答质量 | 差异说明 |
|---|---:|---|
| 直接询问 | 3/5 | 得到通用建议，但缺少项目约束。 |
| 提供详细业务约束 | 4/5 | 输出更贴合业务范围和周期限制。 |
| 要求多方案对比 | 4/5 | 表格清晰，适合决策讨论。 |
| 架构师角色扮演 | 5/5 | 最能暴露风险和工程取舍。 |

结论：Prompt 中包含业务范围、时间限制、团队能力和期望输出格式时，AI 回答明显更可用；角色扮演能提升风险识别质量，但仍需要人工检查与项目真实边界是否一致。技术栈不应在架构辩论阶段被当作既定约束，而应在架构方案确定后再作为落地选择进入架构设计文档。
