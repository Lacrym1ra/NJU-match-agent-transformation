# 架构候选方案对比表

> 只记录当前仓库中已有事实与可追溯结论。

## 最终采用的架构风格

统一仓库下的模块化分层单体架构（Modular Layered Monolith）。

一句话落地方式：一个 React 前端、一个 Express 后端、一个 PostgreSQL 数据库，后端按业务域拆模块而不拆微服务。

## 候选方案对比

| 对比维度 | 方案 A：模块化分层单体 | 方案 B：微服务拆分 |
|---------|----------------------|-------------------|
| 开发复杂度 | 低，单仓协作 | 高，需要服务拆分与治理 |
| 可维护性 | 中高，依赖模块边界治理 | 中高，但需成熟分布式治理 |
| 可扩展性 | 中，可按业务继续拆模块 | 高，但当前阶段过度设计 |
| 性能 | 对当前规模足够，链路短 | 理论上更强，网络开销更高 |
| 团队学习成本 | 低，技术栈统一 | 高，需要分布式与运维能力 |
| 10 周内可行性 | 高，贴合现有代码现实 | 低，不符合当前节奏 |
| 结论 | 采用 | 不采用 |

## 为什么不选微服务

1. 当前代码现实是单前端、单后端、单数据库；拆分会引入额外耦合成本。
2. 业务域共享统一用户、认证与圈子上下文，拆分后需要复杂的数据与身份同步。
3. 课程周期有限，先把模块边界清晰化更可行。
