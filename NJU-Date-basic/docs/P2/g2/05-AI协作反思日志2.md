## 2. AI 助力分析（Q1）

**本阶段 AI 最大的贡献是：**
快速生成了符合 P2 要求的标准文档结构和模板框架（如 ADR、架构辩论赛记录格式）；在“架构辩论赛”中，通过引入场景与约束，AI 能快速产出逻辑严密的技术选型对比（如NestJS+PostgreSQL），并敏锐指出了并行开发不同模块下的数据一致性风险，为人工决策提供了优质参考。

**不同 Prompt 策略下 AI 回答质量的差异：**
- **无约束开放提问**：AI 给出的回答非常泛化（如仅建议“模块化单体”），套话多，缺少落地细节。
- **详尽背景约束提问**：提供“4人团队/工时限制/业务难点”后，AI 能够收敛建议，直接输出契合中小规模团队短平快交付目标的具体技术栈和状态机选型。
- **高阶角色扮演提问**：赋予“资深架构师”角色后，AI 能够跳出技术选型的底层细节，从微服务解耦与限界上下文的高维视角，指出多个业务闭环间跨域权限判定不一致的风险。

## 3. AI 误导分析（Q2）

**AI 在架构建议中的典型问题：**

- **问题1：单纯照搬现有参考材料，缺乏针对局部的深入推演分析。**
  - **如何发现**：在要求基于《当前项目真实架构设计》补充特定的“兴趣圈组”架构内容时，用户审阅后发现生成文本仅是对整体架构材料的简单复述与搬运，完全没有结合具体的兴趣圈代码表现出新的思考。
  - **如何修正**：用户通过明确的 Prompt 纠正（“我感觉你完全是那边搬过来的...你的交互物需要侧重于兴趣圈”），并要求 AI 停止输出无关的证据代码块，聚焦分析圈子隐私分层和可见性的特定决策。
  
- **问题2：过度解读指令或破坏固有排版格式。**
  - **如何发现**：AI 在重构架构辩论文档时，私自加上了原本 P2 要求之外的内容（如多余的高亮或不存在的评测标准）；而在填补信息时将标题、背景内容与引用混合，导致文档排版混乱。
  - **如何修正**：通过确切的指令让 AI 精简输出（“把 prompt 和 ai 的回答放在灰色引用框里”，“去除 AI 初稿与人工修订 diff 区块”），且最终再由人工校对微调版式。

- **问题3：顾此失彼，过度聚焦局部需求导致遗漏全局设计规范。**
  - **如何发现**：在核对 P2 考核要求与 AI 最初生成的《架构设计文档》时，发现 AI 虽然根据人工指令详细输出了“兴趣圈”局部业务的架构细节，但却完全遗漏了 P2 模板中处于顶层的硬性要求——“全局模块职责边界、依赖拓扑与通信接口”，导致文档结构不完整。
  - **如何修正**：用户不得不人工查验 P2 规范，并通过严厉的 Prompt 追问和补救（“为什么你原来生成的时候没有加上这一部分呢，p2文件里面有明确要求啊”）。这也迫使后续交互中明确要求 AI 平衡“全局骨架完整性”与“局部模块细化”的主次关系。

## 4. Prompt 改进计划（Q3）

**上阶段（P1）提出的改进措施，验证结果：**
通过前期探索得知，直接抛出大问题会导致回答假大空。在此次架构辩论赛中得到了验证，即提供详细项目资源约束并附加角色扮演的 Prompt，显著提升了输出内容的深度和项目贴合度。

**本阶段新的改进措施：**
1. **内容生成与排版指令分离**：生成长文本或复杂表格体系时，不再将“生成内容”与“排版对齐”合在一个 prompt 中。先要求 AI 生成具体模块的核心决策点，再用单独指令（如“将上述内容填入给定 markdown 模板的框内”）约束其排版。
2. **上下文隔离**：避免让 AI 自行在所有文件中寻找焦点。由人来圈定范围（比如“现在只看 06-圈子组模块与接口详述，然后总结 ADR”），以避免它照搬通用的全局架构设计。

## 5. 本阶段的核心工程判断

**决策内容：**
最终确定选用何种整体技术栈（如放弃过度设计的全微服务，采用模块化单体），决定在文档中主要聚焦哪几项 ADR（如圈子隐私分层、兴趣圈组交互物索引等），以及评定项目中各业务闭环边界该如何划分（如何隔离认证服务与业务主线）。

**为什么 AI 无法做决策：**
AI 无法感知项目真实开发者的研发能力瓶颈、团队偏好、以及当前课程作业评价体系的侧重点。AI 倾向于推荐工业界成熟且大而全的通用方案，或者由于缺乏业务直觉，无法判定项目中如“兴趣圈”这样的特定模块才是团队产出的亮点。因此，需要人类架构师根据团队实际情况（时效、人力、作业要求）来做出最终的裁剪和拍板。
