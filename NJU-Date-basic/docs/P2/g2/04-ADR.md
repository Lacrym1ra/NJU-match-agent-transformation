# ADR 集合

# ADR-001：采用统一仓库下的模块化分层单体架构

## 状态
已接受

## 背景

当前项目需要同时承载主匹配、兴趣圈、社交关系、组队、后台治理等能力；不同模块共享统一用户、认证、数据库与部署资源。

## 决策

我们决定采用统一仓库下的模块化分层单体架构，而不是把三组拆成三个独立系统或微服务。

## 理由

- 当前代码已经稳定组织成单前端、单后端、单数据库。
- 共享用户体系和圈子上下文决定了模块之间会频繁协作。
- 以课程项目规模与周期来看，先做清晰模块边界更合理。

## 后果

- 正面影响：开发、部署和联调成本低，协作效率高。
- 负面影响：模块增多后，边界维护成本上升。
- 需要关注的风险：服务层容易膨胀，需要持续按业务域治理。

## AI 辅助记录
- **AI 初稿内容摘要**：推荐采用微服务架构（Microservices），将三大业务域完全拆分。
- **人工修订内容**：否决微服务，落地为“基于单 Node 进程的模块化单体架构（Modular Monolith）”。
- **修订理由**：10周、4人的资源高度受限。跨域事务如果走网络调用难度极高。
- **差异对照 (Diff 标记)**：
```diff
- 总体架构建议采用微服务架构（Microservices），通过 API 网关和 gRPC 通信进行三大业务域隔离。
+ 总体架构建议采用基于 Express 的模块化单体架构（Modular Monolith），仅在 src 层将 routes 和 services 进行按业务域划分。
```



# ADR-002：统一使用 PostgreSQL + Drizzle 作为主数据层

## 状态
已接受

## 背景

项目包含大量关联关系：用户、问卷、匹配、圈子、好友、组队、举报、后台治理等，需要一致性较高的数据模型。

## 决策

我们决定统一使用 PostgreSQL 作为运行时数据库，并使用 Drizzle ORM 管理 schema 与查询访问。

## 理由

- 当前代码中数据库连接、schema 和迁移都围绕 PostgreSQL + Drizzle 实现。
- 关系型数据更适合当前项目的多表关联与事务控制。
- 单一数据源便于三组协作，减少跨库同步复杂度。

## 后果

- 正面影响：数据一致性强，结构清晰，便于维护和统计。
- 负面影响：若出现高频缓存场景，还需补充缓存层。
- 需要关注的风险：表规模增长后需持续优化索引与查询性能。

## AI 辅助记录
- **AI 初稿内容摘要**：推荐使用 MongoDB 或 Prisma 作为核心存储栈。
- **人工修订内容**：决定采用 PostgreSQL + Drizzle ORM，并用 `jsonb` 支持扩展。
- **修订理由**：深层关系结构（圈内身份->好友->审批）下 NoSQL 难以应对复杂 Join。Drizzle 更轻量且贴近 SQL 表达。
- **差异对照 (Diff 标记)**：
```diff
- 建议采用 MongoDB 处理灵活的名片数据，或使用 Prisma 作为 ORM。
+ 决定采用 PostgreSQL (支持 jsonb) + Drizzle ORM，以兼顾事务强一致性与字段扩展性。
```



# ADR-003：圈子社交的隐私分层与可见性控制

## 状态
已接受

## 背景

圈子社交涉及公开名片、好友名片与联系方式等敏感信息，需要在圈子内实现逐级授权与分层展示，同时保证频道成员展示不泄露隐私字段。

## 决策

我们决定采用“公开层 / 好友层 / 解锁层”的隐私分层，并通过名片模块可见性与解锁审批控制信息展示。

## 理由

- 圈子频道需要公开展示成员标签，但不能暴露联系方式或好友级信息。
- 名片模块已支持 `public/hidden/deleted` 分层，便于实现“先公开、后好友”的展示递进。
- 联系方式属于高敏信息，需要显式解锁与审批流程隔离。

## 后果

- 正面影响：频道展示安全边界清晰，私密信息不会在未授权场景泄露。
- 负面影响：交互链路更长，部分用户会感知“解锁门槛”。
- 需要关注的风险：前端错误使用接口或缓存导致信息越权展示。

## AI 辅助记录
- **AI 初稿内容摘要**：推荐传统的两层权限模式（公开与私密）进行粗粒度拦截。
- **人工修订内容**：构建细粒度数据隔离：组件级 `public/hidden/deleted` 叠加通道级 `isChannelTag`，配以独立的锁审核表。
- **修订理由**：社交场域需双向同意。简单 Role 字段无法满足防止抓包拉取大名片及恶意枚举的业务合规要求。
- **差异对照 (Diff 标记)**：
```diff
- 隐私控制基于“圈子是否私有”进行判断，非私有圈子可以直接拉取用户档案。
+ 隐私控制采用“公开层/好友层/解锁层”三层递进。采用白名单 isChannelTag 控制频道产出，使用独立表 contact_unlock_requests 阻拦联系方式。
```



# ADR-004：加入圈子时自动初始化 A/B 区名片

## 状态
已接受

## 背景

圈子加入后需要尽快进入频道与名片流程，但如果必须先手动创建名片，会导致链路断裂与转化下降。

## 决策

我们决定在用户加入圈子时自动初始化 A 区基础名片与该圈 B 区名片实例。

## 理由

- 用户加入后即可进入频道，不需要额外步骤才能看到/编辑名片。
- A 区可从用户资料与问卷映射预填，降低首次编辑成本。
- B 区默认空值与删除状态，避免误展示未填写信息。

## 后果

- 正面影响：入圈后流程连续，减少空页面与阻塞。
- 负面影响：初始化逻辑更复杂，需要处理幂等与重复加入场景。
- 需要关注的风险：默认数据与真实用户意图可能存在偏差，需要提示用户编辑。

## AI 辅助记录
- **AI 初稿内容摘要**：推荐“懒加载”（Lazy Evaluation）策略，在查询空时插入名片。
- **人工修订内容**：采用“强初始化”，在圈子 join 的同一数据库事务中创建 A 区与 B 区名片行。
- **修订理由**：被动查看时的临时插入会导致多并发下的竞争重入，明确动作+事务包裹能彻底杜绝外键悬空脏数据。
- **差异对照 (Diff 标记)**：
```diff
- 优化读取性能：在用户首次查询自己的名片数据时检测并动态插入名片行。
+ 强化数据完整性：在用户触发 POST /circles/:circleId/join 的同时开启 DB 事务，连同圈内身份一并初始化并落盘 A/B 名片基础配置。
```
