## 2. AI 助力分析（Q1）

### AI 在编码中最有价值的场景

**场景：算法/公式实现。** 热度排序公式 `hot_score = (like*3 + favorite*4 + comment*5 + view*0.2) / (1 + hours/24)` 的 Drizzle ORM 实现涉及复杂的 SQL 表达式。AI 能正确地在 TypeScript 中用 `sql` 模板构建该表达式，并处理了除零保护和空值兜底。人工只需确认业务参数（权重值）。

**具体案例：** `forumService.ts` 中 `hotScoreExpr()` 函数的实现，AI 在一轮内给出了完整的 `sql<>` 表达式，人工仅微调了分母系数。

### AI 在测试生成中最有价值的场景

**场景：边界条件用例生成。** 为论坛服务的工具函数（`maskAuthor`、`toAuthorDTO`、`mapNotificationType`、`toContentSnippet`）生成测试时，AI 自动覆盖了：
- 正常输入
- null/undefined 输入
- 空字符串输入
- 超长字符串截断
- 未知类型的默认回退

人工补充了少数与业务强相关的测试（如匿名mask的 `isOwn` 判断场景），修改幅度约 20%。

### AI 在调试中最有价值的场景

**场景：权限遗漏检测。** 私密帖越权漏洞的调试中，AI 在 3 分钟内识别出 `getPostDetail` 缺少 `visibility` 检查，并进一步指出 `likePost`、`favoritePost`、`createComment` 等函数也存在相同的权限缺口，建议提取公共函数 `requirePostAccess`。这比人工排查快 8 倍（3min vs 25min）。

## 3. AI 误导分析（Q2）

### "AI 代码信任度实验"数据摘要

- **AI 直出的测试通过率：** 70%（7/10 用例）
- **人工审查修复后的测试通过率：** 100%（10/10 用例）
- **发现的主要问题类型：**
  1. **安全防护缺失**（40%）：参数无上限保护、无效类型未拦截、私密帖权限遗漏
  2. **边界条件遗漏**（30%）：负值 page、无 debounce 搜索、超长 keyword
  3. **业务规则偏差**（20%）：热度公式缺少 view 权重、热榜未排除私密帖
  4. **代码质量问题**（10%）：匿名帖 `isAnonymous` 布尔返回逻辑不清晰

### "AI 调试对决"实验总结

- **AI 擅长调试的 Bug 类型：**
  - 逻辑遗漏类（缺少权限检查、缺少条件分支）
  - 跨平台兼容类（路径分隔符、环境变量）
  - 代码片段级别的模式匹配（SQL 语法、类型不一致）

- **AI 不擅长调试的 Bug 类型：**
  - 需要全局业务上下文的问题（AI 不了解完整业务流程）
  - 并发/竞态条件（需要运行时调试，静态分析难以发现）
  - 前后端联调中的接口契约问题（字段名/类型不一致）

- **AI 修复方案的典型问题：**
  - **过度工程化**（如 Bug #2）：AI 建议将所有通知类型改为枚举常量，引入了 50+ 行的重构改动，而问题本身只需要改一个字符串
  - **缺少副作用评估**：AI 的方案有时没有考虑对其他模块的影响，需要人工 review

## 4. Prompt 改进计划（Q3）

### 上阶段改进措施的验证结果

- **"先给接口定义再写实现"** — 有效。在开发论坛 API 时，先让 AI 生成接口契约（入参、返回值），确认无误后再写实现，大幅减少返工。
- **"明确列出安全要求"** — 有效但需要人工提醒。AI 不会主动考虑安全问题，但在 Prompt 中明确要求"检查权限/参数校验/输入清洗"后，输出质量明显提升。
- **"分步骤生成大型模块"** — 有效但效率较低。拆分为 5+ 个子任务后，每个子任务质量更高，但整体耗时增加。

### 编码阶段的 Prompt 最佳实践

1. **先定义数据模型，再写业务逻辑。** 提供完整的 TypeScript interface 或 DTO 定义，让 AI 在"类型约束"下工作，减少类型错误。
2. **明确列出禁止事项。** 例如"不返回已删除的帖子""不泄露匿名作者信息""不暴露私密帖内容"——负面约束比正面描述更有效。
3. **提供已有代码片段作为上下文。** 让 AI 看到项目中的编码风格、命名约定、错误处理模式，生成的代码更一致。
4. **要求 AI 声明"未处理的情况"。** 例如"请列出你认为还需要人工处理的地方"——有助于发现 AI 忽视的问题。

### 调试阶段的 Prompt 最佳实践

1. **提供完整的错误上下文，而非只是错误消息。** 包括：堆栈跟踪、相关代码文件路径、请求参数、环境信息。
2. **描述"预期行为"和"实际行为"的差异。** 清晰的两列对比让 AI 快速理解问题。
3. **说明已尝试的排查步骤。** 避免 AI 重复你不成功的方法。
4. **要求 AI 同时列出根因和影响范围。** 例如"除了这个函数，还有哪些地方可能存在相同问题？"

### 下阶段计划改进

1. 为 AI 建立项目级的"安全审查清单"，每次代码生成后自动对照检查
2. 探索用 AI 做端到端的集成测试生成（而非仅单元测试）
3. 制定团队统一的 Prompt 模板库，减少个人风格导致的输出差异

## 5. 本阶段的核心工程判断

### 决策内容

**将匿名帖的"mask"逻辑统一在服务端实现，前端只消费脱敏后的数据。**

### 为什么 AI 无法单独做这个决策

AI 在最初生成匿名帖代码时，将 mask 逻辑同时放在了前端和服务端，导致两处不一致（前端可能因为网络请求拦截等原因泄露 author 信息）。AI 能实现"掩码"这个技术动作，但无法判断"掩码应该放在服务端还是前端"这个架构决策——这需要理解安全边界、数据流向和最小权限原则。

### 团队最终如何判断和取舍

团队决定：
- **服务端作为唯一的权限边界**：所有匿名/隐私判断在服务端完成，前端收到的数据已经是脱敏后的结果
- **前端不可信任**：即使前端有显示判断，也必须以服务端返回为准——因为前端代码对用户可见、可被篡改
- **性能 trade-off**：选择在服务端 JOIN 用户表时直接携带 author 信息，在一个查询中完成"数据加载+权限判断+匿名脱敏"，避免 N+1 问题

这个决策确保了即使未来添加新的客户端（如移动端 App），匿名/隐私保护也会在服务端统一生效。
