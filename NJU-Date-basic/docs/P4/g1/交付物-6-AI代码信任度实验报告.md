# P4 AI 代码信任度实验报告

## 1. 实验对象

- 实验功能点：登录校验与密码找回相关认证逻辑
- 选题原因：
  - 该功能属于 P0 核心链路，直接影响注册、登录和后续所有受保护接口。
  - 该模块同时覆盖接口校验、错误处理、安全约束和异常路径，适合作为代码信任度实验对象。

## 2. 已观察事实

### 2.1 代码与文档证据

- `backend/src/routes/auth.ts`
  - 已实现 `/auth/send-code`、`/auth/register`、`/auth/login`、`/auth/forgot-password/send-code`、`/auth/forgot-password/reset`。
  - 登录接口对 `email` 使用 `@smail.nju.edu.cn` 正则校验，对 `password` 使用 `6-72` 长度限制。
- `backend/src/services/authService.ts`
  - 已实现 OTP 发送、OTP 消费、密码注册、密码登录、忘记密码重置。
  - OTP 校验存在失败计数与封锁逻辑。
  - `loginWithPassword` 对“未注册邮箱”和“密码错误”返回不同提示。
- `backend/docs/API_REFERENCE.md`
  - `POST /auth/login` 的错误说明写的是统一的“邮箱或密码错误”。
  - `POST /auth/forgot-password/send-code` 明确写了“为避免账号枚举，该接口对邮箱是否存在返回统一提示”。
- `backend/src/services/authService.test.ts`
  - 已写出对 OTP 失败封锁、JWT payload、输入校验、邮箱枚举风险的测试性检查。
  - 其中多条断言直接指出当前登录逻辑存在账号枚举风险。
- `backend/src/concurrency.test.ts`
  - 已写出对 `sendOtp` 冷却窗口竞态、OTP 二次消费、并发注册等并发风险的测试性检查。

## 3. 实验 Prompt

本次实验采用如下 Prompt：

```text
请为一个 Express + TypeScript + PostgreSQL 项目的认证模块实现登录与密码找回相关逻辑。

要求：
1. 仅允许 @smail.nju.edu.cn 邮箱。
2. 支持：
   - POST /auth/login：邮箱 + 密码登录
   - POST /auth/forgot-password/send-code：发送重置验证码
   - POST /auth/forgot-password/reset：验证码重置密码
3. 使用 JWT 返回登录态。
4. 对输入进行 Zod 校验。
5. 登录、找回密码、OTP 逻辑要考虑安全性，包括错误提示、限流、验证码过期与异常处理。
6. 输出路由层和核心 service 层代码，保持结构清晰，可直接接入现有 Express 项目。
```

## 4. AI 直出结果摘要

从生成结果来看，AI 直出代码基本完成了以下内容：

- 能较快生成 `auth.ts` 路由骨架和 `authService.ts` 的主流程。
- 能补出 JWT 生成、密码哈希、OTP 基础校验、Zod 请求体验证。
- 能给出“未注册邮箱”和“密码错误”的分支处理。
- 能实现忘记密码发送验证码与重置密码的基本 CRUD 流程。

但进一步检查后也能看到一些明显不足：

- 跨接口的一致安全语义。
  - `forgot-password/send-code` 已采用统一提示防止账号枚举。
  - `login` 当前实现却仍暴露“该邮箱尚未注册，请先注册账号”。
- 并发与竞态风险。
  - `sendOtp` 的冷却标记在异步数据库/邮件操作之后才写入。
  - OTP 消费与注册流程存在先查后改的竞态窗口。
- 输入校验边界。
  - OTP `code` 仅校验长度为 6，没有在 schema 层限制为纯数字。

## 5. 人工检查与修复点

### 5.1 人工检查关注点

- 是否符合项目既有接口文档与安全约束。
- 是否处理异常路径和边界输入。
- 是否存在只看单接口正确、但跨接口语义不一致的问题。
- 是否存在竞态和高并发下的错误行为。

### 5.2 人工检查发现的主要问题

#### 问题 1：登录接口存在账号枚举风险

- 观察依据：
  - `backend/src/services/authService.ts` 中，未注册邮箱返回 `该邮箱尚未注册，请先注册账号`，并附加 `USER_NOT_REGISTERED` 区分码。
  - `backend/docs/API_REFERENCE.md` 中，`POST /auth/login` 的 401 错误说明为统一的“邮箱或密码错误”。
  - `backend/src/services/authService.test.ts` 明确将此识别为不安全行为。
- 风险：
  - 攻击者可以根据错误提示和错误码批量探测哪些邮箱已注册。
- 人工检查后的处理意见：
  - 登录失败应统一返回同一错误消息。
  - 应删除暴露邮箱存在性的区分性错误码。

#### 问题 2：OTP 输入校验不够严格

- 观察依据：
  - `backend/src/routes/auth.ts` 中，`code` 使用 `z.string().length(6)`。
  - `backend/src/services/authService.test.ts` 明确指出 `"abcdef"` 这类 6 字符字符串可通过 schema，只会在数据库匹配阶段失败。
- 风险：
  - 输入校验边界后移到业务/数据库层，不利于尽早拒绝非法输入，也会增加错误定位成本。
- 人工检查后的处理意见：
  - 可将 OTP 校验升级为 `.regex(/^\\d{6}$/)`。

#### 问题 3：OTP 冷却与消费逻辑存在并发竞态

- 观察依据：
  - `backend/src/concurrency.test.ts` 已针对 `sendOtp`、`consumeOtp`、`registerWithOtp` 写出并发风险检查。
  - `backend/src/services/authService.ts` 中，冷却标记写入发生在异步操作之后。
- 风险：
  - 并发请求下可能出现重复发码、同一 OTP 被重复消费或并发注册错误。
- 人工检查后的处理意见：
  - 冷却标记应在通过校验后立即占位。
  - OTP 消费和注册过程应增加更强的原子性保护或事务控制。

## 7. 实验结论

### 7.1 可以信任 AI 的部分

- 认证路由、基础 service 流程、Zod schema、JWT 生成这类样板型工作，AI 能明显提速。
- 测试样例和安全检查清单，AI 也适合先给出初稿。

### 7.2 不能直接信任 AI 的部分

- 安全语义是否跨接口一致。
- 并发下是否仍然满足业务约束。
- 边界条件是否在正确层次被拦截。
- 错误信息是否泄露了不应暴露的系统状态。

### 7.3 本项目中的工程判断

本次实验最关键的判断不是“登录功能能否跑通”，而是“认证模块是否在系统层面保持一致的安全语义”。这一判断依赖项目 API 文档、服务实现、测试意图和后续前端交互，不能只凭 AI 生成的一段局部代码作结论。

### 7.4 结论摘要

- AI 在认证模块上适合先产出“可运行初稿”。
- 人工审查的价值主要体现在安全一致性、边界校验和并发约束上。
- 对登录、鉴权、状态流转这类 P0 主链路，不能把“能跑”当成“可直接信任”。

### 7.5 本次实验的保守结论

- 这次实验说明，AI 在生成认证模块初稿时效率较高，尤其适合完成路由骨架、基础校验和常规业务流程。
- 但在涉及系统级安全语义、边界输入和并发约束时，人工检查仍然不可替代。
- 团队后续若继续使用 AI 参与编码，应把重点放在“先生成、再验证、后合并”，而不是直接信任生成结果。
