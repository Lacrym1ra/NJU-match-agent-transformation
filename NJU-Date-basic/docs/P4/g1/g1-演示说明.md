## 一、运行方式

### 1.1 前置要求

| 工具 | 版本 | 说明 |
|---|---|---|
| Node.js | 20+ | 前后端统一运行环境 |
| npm | 10+ | 用于安装依赖和启动开发服务 |
| PostgreSQL | 14+ | 也可使用项目根目录的 Docker Compose 启动 |

### 1.2 本地启动

后端：

```bash
cd backend
cp .env.example .env
# 编辑 .env：填写 DATABASE_URL、JWT_SECRET、ADMIN_KEY
npm install
npm run dev
```

前端：

```bashgit
cd frontend
npm install
npm run dev
```

访问地址：`http://localhost:3001`

### 1.3 Docker 启动

```bash
docker compose up -d --build
```

访问地址：

- 前端：`http://localhost:3001`
- 后端 API：`http://localhost:3000`

开发模式下如未配置真实 SMTP，OTP 验证码会打印在后端终端，格式类似：

```text
[DEV] OTP for demo-a@smail.nju.edu.cn: 123456
```

### 1.4 健康检查

```bash
curl http://localhost:3000/health
```

预期返回：

```json
{ "status": "ok", "timestamp": "..." }
```

## 二、演示环境配置

### 2.1 必填环境变量

`backend/.env` 至少需要：

```env
DATABASE_URL=postgres://postgres:postgres@localhost:5432/nju_date
JWT_SECRET=任意随机字符串（建议 32 字节以上）
ADMIN_KEY=任意随机字符串（用于匹配触发等管理接口）
FRONTEND_URL=http://localhost:3001
```

`SMTP_*`、`OPENAI_API_KEY`、`ALIYUN_*` 等字段留空不影响主线演示。若未配置邮件服务，验证码从后端终端读取。

### 2.2 演示数据准备

为了演示主匹配与 Heartbox，建议准备两个测试用户：

| 账号 | 邮箱 | 性别 | 用途 |
|---|---|---|---|
| 演示用户 A | `demo-a@smail.nju.edu.cn` | 男 | 主流程演示 |
| 演示用户 B | `demo-b@smail.nju.edu.cn` | 女 | 匹配对象 / Heartbox 对象 |

两个用户均需完成：

- 注册和密码设置
- Onboarding 建档
- 灵魂问卷提交
- `isParticipating = true`
- Heartbox 演示时还需完成学号绑定

### 2.3 手动触发匹配

正常匹配每周三自动运行。为了演示，可以通过管理接口手动触发。

推荐使用管理面板：

```text
http://localhost:3001/admin
```

输入 `ADMIN_KEY` 后，先执行“匹配池预检”，确认至少有一男一女且问卷已完成，再点击“立即匹配”。

也可以通过接口触发：

```bash
curl -X POST \
  -H "x-admin-key: ${ADMIN_KEY}" \
  http://localhost:3000/api/v1/admin/trigger-matching
```

注意：后端管理员鉴权使用 `x-admin-key` 请求头，不是 `Authorization: Bearer`。

## 三、核心演示路径

建议完整演示时间控制在 8-12 分钟。

### 路径 1：注册与建档（1-2 分钟）

入口：`http://localhost:3001/login`

步骤：

1. 点击“注册账号”，输入 `demo-a@smail.nju.edu.cn`。
2. 点击获取验证码，从后端终端读取 OTP。
3. 填写验证码并设置密码。
4. 首次登录后进入 Onboarding 页面。
5. 填写昵称、性别、校区、院系、MBTI、联系方式等资料。

验证点：

- 非 `@smail.nju.edu.cn` 邮箱会被拦截。
- 登录失败不会区分“未注册”和“密码错误”，避免邮箱枚举。
- profile/auth 响应不会返回 `passwordHash`、`studentIdHash` 等敏感字段。

### 路径 2：灵魂问卷填写（2 分钟）

入口：登录后从 Dashboard 进入问卷页。

步骤：

1. 展示问卷分区和多题型：单选、多选、排序、Likert、开放题。
2. 演示重要度权值滑块。
3. 提交问卷。

验证点：

- 提交后 Dashboard 显示问卷已完成。
- 问卷答案和权值写入后端，用户进入匹配池。

### 路径 3：Dashboard 与参与状态（1 分钟）

入口：`http://localhost:3001/dashboard`

步骤：

1. 展示当前匹配状态。
2. 展示参与匹配、暂停本周、长期停止等状态。
3. 如果信用分低于等于 90，恢复参与会被限制。

验证点：

- 匹配计算窗口内按钮置灰。
- 问卷未完成时不能参与匹配。
- 低信用分用户不能恢复参与。

### 路径 4：匹配揭晓与双选（2-3 分钟）

入口：`http://localhost:3001/reveal`

前置条件：两个演示用户已完成资料和问卷，管理员已触发匹配。

步骤：

1. 展示揭晓页信封动画。
2. 拆信后展示匹配对象资料、标签、AI 寄语和契合度信息。
3. 点击“心动”或“婉拒”。
4. 双方均心动后进入 MUTUAL 状态，展示联系方式。
5. 展示举报/拉黑入口。

验证点：

- MUTUAL 前不展示联系方式。
- LOCKED、MISSED、EXPIRED 等状态不能错误操作。
- 举报/拉黑入口已接入用户侧流程。

### 路径 5：Heartbox 双向心动（2 分钟）

入口：`http://localhost:3001/heartbox`

前置条件：两个演示用户均已绑定学号。

步骤：

1. 用户 A 输入用户 B 的学号并投递心动信号。
2. 切换到用户 B，输入用户 A 的学号并投递。
3. 双向投递后跳转到 Heartbox Reveal。
4. 展示定向心动对象资料和联系方式。

验证点：

- 学号明文不入库，只存储哈希和末四位。
- 不能向自己投递，不能重复投递。
- Heartbox 是定向心动，不经过每周主匹配算法。

### 路径 6：历史与设置（1-2 分钟）

入口：

- 历史：`/dashboard` 下方历史区域
- 设置：`/settings`
- 账号：`/account`

步骤：

1. 查看历史匹配记录。
2. 在设置页修改资料、标签、联系方式、参与状态。
3. 展示名片编辑器入口。
4. 可说明账号注销会清空 PII，但演示时不建议真实执行。

验证点：

- 资料修改后同步到 Dashboard 和 Reveal。
- 账号注销会匿名化用户信息，匹配记录保留。

## 四、快捷演示路线

时间紧张时可以使用 5 分钟路线：

1. 登录已有账号。
2. Dashboard 展示当前匹配状态。

4. Heartbox 展示学号绑定状态和双向心动流程。
5. Settings 展示资料维护、参与状态、举报/拉黑/注销说明。

## 五、已知限制与注意事项

| 限制 | 说明 | 对演示影响 |
|---|---|---|
| 匹配周期固定 | 默认每周三自动运行 | 演示前通过 admin 面板手动触发匹配 |
| 匹配池人数要求 | 至少 2 人且建议一男一女，均需完成问卷并参与匹配 | 演示前准备两个账号 |
| Heartbox 需要学号绑定 | 未绑定学号无法投递心动信号 | 演示前完成学号绑定 |
| 站内消息中心独立列表页未落地 | 后端接口已就绪，Dashboard 已有聚合消息入口；独立 `/messages` 页面延期至 P5 | 不影响 g1 主匹配演示 |
| 用户分层管理属于 P2 | 已写入 Sprint 看板作为管理后台能力预研，本期不纳入演示 | 不影响 P0/P1 验收 |
| 邮件服务可能未配置真实 SMTP | 开发环境 OTP 从后端终端读取 | 注册/绑定时切换查看终端即可 |
| 全量后端测试仍有并发类失败 | 最近一次 `npm test` 为 189 项中 174 项通过，15 项失败集中在 `concurrency.test.ts` | 本次安全修复对应测试已通过；演示使用正常主流程 |
