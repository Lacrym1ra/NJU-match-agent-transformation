## 2. AI 助力分析（Q1）

- **AI 在编码中最有价值的场景：**
  - **快速生成状态类型扩展框架和 UI 状态映射 helper：** 如扩展 `friends.ts/contacts.ts` 状态枚举和 Dashboard `switch(status)` 文案输出，节省了大量 boilerplate 代码编写时间。
  - **大规模代码重构的依赖追踪：** 在后端大 Service 拆分为 `modules/<domain>/` 的过程中，AI 自动追踪了路由、service 互引、realtime、类型引用、测试等全量依赖路径，采用"两层结构"——新模块入口 + 旧 service 兼容 re-export——降低了迁移风险，人工只需审查关键边界。
  - **交付物缺口分析与验证：** AI 对照 P4 验收标准自动运行 `npm test`、`npm run build` 等命令验证现状，输出了精确到条目的缺口清单（如缺少 `docs/P4/` 目录、CI/CD 未自动跑测试、缺少覆盖率脚本等），帮助团队快速定位最紧急的补齐项。
  - **并发 Bug 测试框架搭建：** 团队成员主动设计了"故障复现 + 回归测试"的双层测试架构，将 `concurrency.test.ts`（修复前模型，预期失败）和 `concurrency.fixed.test.ts`（修复后模型，预期通过）分离，并在 GitLab CI 中配置 `allow_failure` 策略。AI 协助生成了具体的测试代码，但整体架构设计和证据链思路来自团队成员的工程判断，既保留了修复前的失败证据又不阻塞主流水线。

- **AI 在测试生成中最有价值的场景：**
  - **对照需求规格生成测试候选：** AI 读取 P4 要求后，按"边界条件、异常输入、权限校验、状态转换"四类自动梳理测试候选，如学号/邮箱绑定策略（发现 `studentIdPolicy.ts` 只取邮箱 local-part 未校验域名的真实问题）、联系方式加密/解密、好友请求冷却边界等。
  - **发现潜在 Bug：** 在分析测试候选时，AI 发现 `SettingsPrivacyTab` 的 UI 同时展示"撤回/忽略/拉黑"但数据源只取收到的 pending 申请，前端判断过宽——这一发现后来确实成为一个需要修复的 Bug。
  - **并发测试策略设计：** 团队成员明确指出并发问题必须在真实数据库环境中验证，要求 AI 生成基于 PostgreSQL 真实连接的集成测试而非 Mock 测试。AI 在此基础上生成了包含 advisory lock、`SELECT ... FOR UPDATE` 和唯一索引约束的测试用例框架，覆盖了 5 个高风险并发场景（双向好友申请、双击接受、退圈死锁、删除原子性、并发审批）。团队成员还特别强调测试必须使用 `Promise.all` 并行触发多个异步操作，才能准确模拟真实的并发竞争环境。

- **AI 在调试中最有价值的场景：**
  - **快速定位状态枚举遗漏类 Bug：** 如旧二分判断 `status !== 'rejected'` 未覆盖新增状态，AI 约 5 分钟定位到根因。
  - **环境与工具链问题排查：** 在 `git add` 超时问题中，AI 快速定位到根因是 iCloud Drive 对 `.git/index.lock` 写入的干扰，而非项目本身损坏，并给出了"不要把 Git 仓库放同步目录"的实用建议。
  - **合并冲突诊断：** AI 能区分"真实 merge 冲突"与"未提交改动导致的 merge 拒绝"，避免团队在错误方向上浪费时间。
  - **并发 Bug 根因分析：** 识别出 5 个高风险并发场景，并能深入分析事务隔离级别、行锁顺序、唯一约束等数据库机制。例如在"退圈死锁"问题中，AI指出不同事务以不同顺序锁定 teamup 行会形成循环等待，AI 随后提供了在 `SELECT ... FOR UPDATE` 后增加 `ORDER BY id` 的具体实现方案。这种"人工识别风险 + AI 提供技术细节"的协作模式显著提升了调试效率。

## 3. AI 误导分析（Q2）

**"AI 代码信任度实验"数据摘要：**
- AI 直出的测试通过率：100%（`npm run lint` 和 `npm run build` 均通过，无编译/构建错误）
- 人工审查修复后的测试通过率：100%（业务逻辑正确性人工验证通过）
- 发现的主要问题类型：权限边界判断错误（撤销授权按钮放错视角）、收发方申请列表混用导致动作权限错误、通知跳转未优先消费后端已提供的 `actionUrl` 字段

**"AI 调试对决"实验总结：**
- AI 擅长调试的 Bug 类型：状态枚举扩展遗漏类 Bug、幂等/并发类 Bug（如聊天重复发送），AI 能快速扫描类型定义和代码逻辑找到根因。
- AI 不擅长调试的 Bug 类型：涉及业务角色权限边界的 Bug（如撤销授权按钮应放在哪个视角）、需要持久化约束的并发问题（AI 初始建议内存 Map 去重，忽略服务重启失效）。
- AI 修复方案的典型问题：倾向于在应用层做拦截（如内存去重），忽略持久化约束（数据库唯一索引）；对业务角色权限边界的判断不够准确，需要人工校正。

**AI 在代码审计中的局限性：**
- 在设计承诺与实现差异审计中，AI 输出了 12 条主要差距，但部分差距实际上是产品设计演进后的有意变更（如圈子频道从"群聊+私信"收敛为"成员展示"），AI 无法区分"未完成"和"有意简化"，需要人工逐条判断。
- AI 在审计时倾向于"宁多勿漏"，把一些后续产品设计已经改变的旧承诺也列为差距，增加了人工筛选的工作量。

**AI 在测试生成中的典型偏差：**
- **过度依赖 Mock 测试：** 如果没有明确要求"真实 DB 集成测试"，AI 默认生成的测试代码更倾向于使用 Jest Mock 或内存数据结构，而非连接真实 PostgreSQL 数据库。这种测试虽然执行速度快，但无法验证真实的事务隔离、行锁竞争、唯一约束等并发场景下的行为。团队成员在多次迭代中发现这一问题后，开始在 Prompt 中明确强调"使用真实数据库连接，不要 Mock `pool.query`"，并要求测试用例必须包含 `BEGIN`/`COMMIT` 事务包裹、`FOR UPDATE` 行锁、并发 Promise.all 调用等要素，才能生成有效的并发测试。
- **缺乏证据链意识：** AI 初始只生成修复后的回归测试，不理解 P4 交付物中"修复前/修复后对比截图"的重要性。团队成员指导 AI 同时生成"修复前复现测试"（预期失败）和"修复后回归测试"（预期通过），并将两者分离到不同文件中，形成了完整的证据链。

## 4. Prompt 改进计划（Q3）

- **上阶段改进措施的验证结果：** 上阶段要求在 Prompt 中明确指定框架版本和接口定义，本阶段验证该措施有效减少了 AI 生成代码的 API 不兼容问题；要求 AI 输出解释也减少了直接复制错误代码的概率。
- **编码阶段的 Prompt 最佳实践：**
  - 提供完整的接口定义、上下文类结构和业务规则说明；
  - 明确要求"只改前端时不得改后端"等约束条件；
  - 分批实现功能，避免一次性生成过多代码导致质量下降；
  - 大规模重构时，要求 AI "先保行为、再拆边界"，旧入口保留兼容 re-export，降低一次性迁移风险。
- **调试阶段的 Prompt 最佳实践：**
  - 同时提供报错信息、相关代码片段、数据库表结构和预期的行为描述；
  - 提供复现步骤和请求体，帮助 AI 准确定位问题；
  - 环境类问题（如 git 超时、构建卡住）提供完整报错原文和环境路径，AI 能快速定位到文件系统/工具链层面。
- **测试生成阶段的 Prompt 最佳实践（新增）：**
  - **明确测试类型：** 如果目标是验证并发安全、事务原子性或数据库约束，必须在 Prompt 中强调"使用真实 PostgreSQL 数据库连接，禁止 Mock `pool.query` 或任何数据库方法"。团队成员在实践中发现，如果不明确这一点，AI 会自动选择更快的 Mock 方案，导致测试无法暴露真实的并发问题。
  - **指定测试框架：** 对于并发测试，要求使用 `Promise.all` 并行触发多个异步操作，并在测试中显式声明 `BEGIN`/`COMMIT` 事务。这是团队成员根据实际并发 Bug 复现经验总结的关键要点。
  - **要求双重证据：** 对于 Bug 修复类测试，要求 AI 同时生成"修复前复现测试"（预期失败）和"修复后回归测试"（预期通过），并将两者分离到不同文件中。这种策略是团队成员为满足 P4 交付物要求而主动设计的。
  - **人工审核点：** AI 生成的并发测试必须经过人工审核以下要点：
    1. 是否使用了真实的数据库连接池而非 Mock；
    2. 是否正确包裹了事务（`BEGIN`/`COMMIT`）；
    3. 是否模拟了并发场景（`Promise.all` 并行调用）；
    4. 断言是否覆盖了期望的业务行为（如"只插入 1 条记录"而非"不报错"）。
    这些审核点是团队成员在多次 AI 协作中积累的实战经验。
- **下阶段计划改进：**
  - 在 Prompt 中强制要求 AI 进行自我审查，检查权限边界和持久化约束；
  - 尝试让 AI 生成更复杂的集成测试场景；
  - 对 AI 生成的并发处理方案，人工必须确认是否需要数据库层约束；
  - 审计类任务中，在 Prompt 中明确标注"哪些设计承诺已被后续设计变更覆盖"，减少 AI 输出无效差距项；
  - **测试生成任务中，建立"Mock vs 真实 DB"的决策矩阵：** 对于纯逻辑验证（如数据格式转换、状态机流转）可使用 Mock，对于涉及事务、锁、约束的场景必须使用真实 DB。这是团队成员在本阶段实践中形成的方法论。

## 5. 本阶段的核心工程判断

- **决策内容：**
  1. 决定将实时聊天 WebSocket 鉴权从长期 JWT 改为一次性 ticket 机制，并将联系方式存储从明文 JSON 改为加密密文，这两项改动增加了开发复杂度但保障了安全性。
  2. 决定将后端大 Service 文件拆分为 `modules/<domain>/` 独立模块，虽然增加了迁移工作量，但使核心业务逻辑可被单独测试，支撑了第二组后端自有模块形成可复核的单元测试覆盖：聊天风控与关系策略 Line 100%，名片快照 99.26%，入圈策略 89.64%，联系方式字段 89.13%，组队策略 88.08%。前端页面级权限门控则采用 `src/pages/*.test.ts` 的用例数口径纳入 `test:g2:unit`，例如 `TeamUpDetail.test.ts` 新增组队结束后同行者举报按钮门控测试，而不把页面渲染壳层强行并入核心模块 Line 覆盖率百分比。
  3. 在 AI 审计出的 12 条设计承诺差距中，团队判断部分差距是产品设计演进的有意变更（如圈子频道收敛），不需要全部补齐，只对影响核心业务流程的项（如入圈审批、字段级联系方式授权、候补补位）进行了实现。
  4. **成员关系生命周期语义审计：** 在为历史组队增加同行者举报入口时，团队发现此前使用 AI 开发圈子与组队模块时，没有在 Prompt 和设计文档中明确规定"成员关系删除语义"：圈成员 `circle_members` 采用物理删除，组队成员 `teamup_members` 采用软删除，导致两个相近业务实体产生了不同的历史保留结果。团队审计后确认，当前举报路径通过历史组队成员保留的 `userId` 行权，聊天/帖子作者字段和信用分扣减也不依赖当前圈成员关系。反事实评估后，若立即统一为软删除，需要改动 `leaveCircle` 主链路和多处"是否退圈"判定语义，且这些路径已被 G2 E2E 与集成测试覆盖；而不改的代价已被 `teamup_members` 软删除、内容表 `author_id` 冗余和通用举报的 `userId` 行权机制消解。因此团队判断在本阶段交付窗口内回归风险高于收益，决定保留现状，并将"成员生命周期语义统一"记录为后续重构候选。
  5. **并发 Bug 修复策略选择：** 面对 5 个高风险并发 Bug（双向好友申请、双击接受、退圈死锁、删除原子性、并发审批），团队成员主动评估了每个问题的触发难度、影响范围和修复成本，决定采用"数据库层约束 + 应用层条件更新"的双重防护机制。具体包括：
     - 方向无关的唯一索引（防止双向并发好友申请）
     - `WHERE status='pending'` 条件更新（防止重复处理）
     - `ORDER BY id FOR UPDATE` 固定锁顺序（防止死锁）
     - 事务包裹 + 行数统计返回（保证原子性可验证）
     这一策略是团队成员在分析 AI 初始建议（仅应用层锁）后，结合多实例部署和服务重启场景做出的工程判断。
  6. **测试证据链设计：** 团队成员为满足 P4 交付物中"修复前/修复后对比截图"的要求，主动设计了双层测试架构——保留"修复前复现测试"作为预期失败的证据，同时新增"修复后回归测试"作为通过的证据。两者在 GitLab CI 中分离（复现测试设置 `allow_failure`），既满足了交付要求又避免了阻塞主流水线。这一设计思路完全来自团队成员的工程经验，AI 仅负责生成具体的测试代码。

- **为什么 AI 无法单独做这个决策：**
  - AI 倾向于选择最简单的实现方式（如直接使用 JWT 连接 WebSocket、明文存储联系方式），无法主动权衡安全性与开发复杂度之间的取舍；
  - AI 无法判断哪些设计承诺差距是"有意简化"还是"遗漏实现"，因为它不了解产品设计演进的历史上下文；
  - 模块拆分的粒度和迁移策略需要结合团队实际开发节奏和测试需求来决定，AI 只能提供技术方案，不能判断"什么时候拆"和"拆到什么程度够用"；
  - **实体生命周期语义的一致性：** 如果 Prompt 没有明确规定相近实体的删除语义和历史保留要求，AI 会倾向于沿用当前文件或局部模块中最顺手的实现模式，结果可能在 `circle_members` 和 `teamup_members` 这类相近概念上生成两种不同策略。是否必须立刻统一，不能只看代码风格一致性，还要结合举报、信用分、历史展示、作者追责等下游链路审计后决定。
  - **并发 Bug 修复的权衡：** AI 初始建议仅在应用层增加标志位或内存锁来防止重复处理，但团队成员判断认为这不足以应对数据库层面的并发竞争和多实例部署场景，必须引入数据库唯一索引和条件更新等持久化约束。这一判断基于团队成员对分布式系统一致性的深入理解。
  - **测试类型的选择：** AI 默认生成 Mock 测试以追求执行速度，但团队成员判断认为并发问题的本质就是数据库层面的竞争，只有真实环境才能准确复现。因此团队成员明确要求使用真实 DB 集成测试，并在 Prompt 中反复强调这一点。
  - **证据链的设计：** AI 无法理解 P4 交付物中"修复前/修复后对比截图"的重要性，因此需要团队成员指导其生成双层测试架构。这是团队成员基于对交付要求的深入解读而做出的主动设计。

- **团队最终如何判断和取舍：**
  - 安全性决策：团队评估了系统涉及用户隐私数据（联系方式、学号等），安全性是底线，因此决定投入额外工时实现一次性 ticket 鉴权和联系方式加密存储，虽然增加了约 4 小时工时，但有效防止了 URL 泄露和隐私数据明文暴露的风险。
  - 模块拆分决策：团队在 AI 建议的"全量拆分"和"最小迁移"之间选择了折中方案——核心策略逻辑（如聊天内容审核、组队状态判定、联系方式加密）抽为独立可测模块，而数据库集成入口仍保留在原 service 文件中通过 re-export 兼容，既满足了测试覆盖率要求，又避免了全量迁移带来的风险。
  - 设计差距取舍：团队逐条审查了 AI 输出的 12 条差距，将其中 5 条标记为"产品设计演进已覆盖"，只对影响 P0/P1 核心业务流程的 7 条进行了实现，避免了在已废弃的设计方向上浪费时间。
  - 成员关系语义取舍：团队在组队举报需求中发现圈成员与组队成员的删除语义并不统一。经过人工审计，当前通用举报、信用分扣减和历史组队展示都可以基于 `userId` 与软删除的组队成员记录闭环，未发现需要在 P4 交付窗口内立即改动的数据安全边界；因此团队选择保留现状，只补足历史组队的举报入口，并把"圈成员/组队成员生命周期统一"作为未来重构候选。这一判断来自团队对业务链路的人工审计，AI 负责辅助定位代码路径和验证影响面。
  - **并发 Bug 修复取舍：** 团队成员对 5 个并发 Bug 进行了风险评估，将"双向好友申请"、"双击接受"、"并发审批"标记为高优先级（直接影响数据一致性），将"退圈死锁"标记为中优先级（极端场景才触发），将"删除原子性"标记为低风险（已有事务保护）。修复顺序按风险从高到低执行，每个修复都配套了复现测试和回归测试。这一优先级排序完全来自团队成员的工程判断，AI 仅提供技术支持。
  - **测试策略取舍：** 团队在"快速 Mock 测试"和"慢速真实 DB 测试"之间选择了后者，因为并发问题的本质就是数据库层面的竞争，只有真实环境才能准确复现。为了平衡执行速度，团队成员将并发测试集中到 `test:g2:fixed-issues` 和 `test:g2:known-issues` 两个独立命令中，日常开发时可跳过，CI 中则必须执行。这一策略是团队成员基于实际开发效率和交付要求的权衡结果。对于纯前端展示/权限门控（如历史组队同行者举报按钮），团队选择抽取纯 helper 并用轻量 Node 单元测试覆盖，避免为单个按钮引入重型 DOM 测试，同时仍纳入 `test:g2:unit` 和 `test:g2` 的主测试链路。
