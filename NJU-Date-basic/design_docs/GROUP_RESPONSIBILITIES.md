# 三组职责与模块总表

> 版本：v1.1 | 日期：2026-04-21

## 1. 文档目的

本文专门回答三类问题：

1. 三组分别负责哪条产品主线
2. 每组具体负责哪些模块、页面、接口和业务规则
3. 像“信用分机制”这种跨模块能力，到底归谁主责、谁消费

使用规则：

- 想看“产品和模块归谁做”，先看本文
- 想看“接口长什么样”，再看各组 API 文档
- 想看“当前后端到底有没有这条接口”，最后以后端代码为准

## 2. 三组产品线一句话定义

| 组别 | 产品线定义 | 关键词 |
|---|---|---|
| 第一组 | 恋爱交友匹配主线 | 注册、问卷、匹配、揭晓、历史、互动表达、消息中心 |
| 第二组 | 圈子与关系链主线 | 圈子、频道、名片、好友、联系方式解锁 |
| 第三组 | 论坛、治理与信用主线 | 论坛、举报、拉黑、后台、审计、信用分 |

一句话理解：

- 第一组负责“怎么认识人、怎么被匹配、怎么看到结果和提醒”
- 第二组负责“匹配之后和圈子里的关系怎么持续发展”
- 第三组负责“大家怎么发内容、平台怎么治理、信用怎么约束”

## 4. 第一组职责

### 4.1 组别定位

第一组就是“恋爱交友匹配主线组”。

它负责的平台主线是：

`注册 -> 建档 -> 问卷 -> 主匹配 -> 揭晓 -> 历史 -> 互动反馈`

### 4.2 第一组具体功能

第一组负责的具体模块：

1. 注册、登录、找回、身份认证
2. 个人资料、参与状态、建档流程
3. 灵魂问卷、答案保存、问卷版本管理
4. 主匹配算法、结果生成、锁定与揭晓
5. 揭晓页、历史记录页、未成功提示
6. 匿名心意表达、双向意向确认
7. 站内消息中心（消息列表、未读 / 已读、红点 / 角标）
8. 用户侧举报 / 拉黑入口接入
9. 与主线相关的通知提醒

### 4.3 第一组主要页面

- 登录页
- 个人资料页
- 问卷页
- 匹配结果页
- 揭晓页
- 历史记录页
- 消息中心页

### 4.4 第一组主要接口范围

- `/auth/*`
- `/user/*`
- `/survey/*`
- `/match/*`
- `/notifications/*`（设计已定，站内消息中心）

与第三组共享但由第一组接入前台的接口：

- `POST /user/report/:targetId`
- `POST /user/block/:targetId`
- `DELETE /user/block/:targetId`

补充说明：

- 当前已实现的 `PATCH /user/notifications` 只是邮件提醒开关，不等于站内消息中心
- 站内消息中心的详细边界和接口契约见 `design_docs/MESSAGE_CENTER_DESIGN.md`

### 4.5 第一组不负责什么

- 不负责圈子频道、名片、好友、联系方式解锁
- 不负责论坛帖子 / 评论 / 管理后台
- 不负责信用分规则引擎本体
- 不负责公告 / 政策更新 / 举报处理结果的规则定义

## 5. 第二组职责

### 5.1 组别定位

第二组就是“圈子与关系链组”。

它负责的平台主线是：

`加入圈子 -> 看频道 -> 看名片 -> 加好友 -> 解锁联系方式 -> 持续互动`

### 5.2 第二组具体功能

第二组负责的具体模块：

1. 圈子列表、圈子详情、加入退出
2. 圈子问卷、圈内匹配、圈内历史
3. 圈子频道与成员标签
4. 公开名片、好友名片、圈子名片覆写
5. 好友申请、通过、拒绝、删除
6. 联系方式解锁申请与审批
7. 圈子页接入论坛入口

### 5.3 第二组主要页面

- 圈子列表页
- 圈子详情页
- 我的圈子页
- 名片编辑页
- 好友页
- 联系方式解锁相关弹窗 / 页面

### 5.4 第二组主要接口范围

- `/circles/*`
- `/card/*`
- `/friends/*`
- `/contacts/*`

说明：

- 当前真实已实现并可联调的只有 `/circles/*`
- `card / friends / contacts / channel` 目前还是设计已定

### 5.5 第二组与论坛的边界

第二组可以做：

- 圈子详情页的“进入圈子论坛”
- 圈子详情页的“发布组队帖”
- 把 `circleId`、`circleName` 透传给论坛页

第二组不能做：

- `/forum/*` 页面与接口
- 帖子 / 评论模型
- 删帖、置顶、论坛管理
- 重复定义 `/circles/:circleId/forum`

### 5.6 第二组不负责什么

- 不负责论坛本体
- 不负责举报审核后台
- 不负责信用分规则引擎本体

## 6. 第三组职责

### 6.1 组别定位

第三组就是“论坛、治理与信用组”。

它负责的平台主线是：

`发帖 -> 评论 -> 举报 / 拉黑 -> 管理审核 -> 审计留痕 -> 信用约束`

### 6.2 第三组具体功能

第三组负责的具体模块：

1. 论坛列表、帖子详情、评论、回复、软删除（含帖子/评论举报接口预留）
2. 圈子专属论坛，也就是带 `circleId` 的帖子流
3. 举报、拉黑、审核处理（四种状态：`pending / reviewed / warn_update / dismissed`）、审计日志
4. 管理后台、运营看板、维护模式等治理能力
5. 平台治理体系：处罚等级（L0–L4）、违规记录、临时封禁、申诉工单、信用分
6. 多部门后台 RBAC：`super_admin / moderator / marketing_operator / support_operator / ops_runner / analytics_viewer`
7. 公告、政策更新、举报处理结果等治理类消息源（广播任务异步入队）

### 6.3 第三组主要页面

- 论坛列表页
- 帖子详情页
- 举报处理页
- 管理后台页
- 运营看板页

### 6.4 第三组主要接口范围

- `/forum/*`
- `/admin/*`
- `/user/report/*`、`/user/block/*` 的规则与治理消费侧

说明：

- 当前真实可联调的是举报 / 拉黑 / `admin/reports`
- 论坛接口本体目前还是设计已定
- 第三组负责治理类消息内容规则，但不负责消息中心页面本体

### 6.5 第三组不负责什么

- 不负责恋爱交友主匹配主线
- 不负责名片、好友、联系方式解锁业务本体
- 不负责圈子页面本体，但负责圈子帖流规则
- 不负责站内消息中心页面本体

## 7. 信用分机制

### 7.1 定位

信用分是平台级能力，不属于单独某个业务页面，而是整个系统的信任约束层。

因此建议明确：

- **第三组主责信用分机制**
- **第一组、第二组只消费信用分结果，不自行定义评分规则**

### 7.2 建议的职责分工

| 组别 | 在信用分机制中的职责 |
|---|---|
| 第一组 | 在主匹配 / 参与状态中消费信用分结果，例如低信用用户被限制参与核心匹配时给出提示 |
| 第二组 | 在圈子、好友、联系方式解锁等社交场景中消费信用分结果，例如后续限制高风险用户的社交扩散能力 |
| 第三组 | 定义信用分规则、分值变动事件、后台管理、审计记录、恢复机制 |

### 7.3 当前建议的最小版本

状态：

- `设计已定`
- 当前仓库里还没有完整实现

建议最小闭环：

1. 用户有一个平台信用分
2. 管理端能看到信用分和变更原因
3. 违规内容或确认违规行为会触发扣分
4. 时间恢复或人工复核可以回分
5. 第一组 / 第二组只根据“分数等级 / 是否受限”做前台提示和流程限制

### 7.4 建议的规则原则

为了避免被滥用，建议明确以下原则：

1. **被举报不等于扣分**
2. **被拉黑不等于自动扣分**
3. **只有审核确认后的违规事件，才进入信用分计算**
4. **所有扣分必须有原因、有操作人、有时间，能审计**
5. **信用分不要让普通用户直接看到别人的精确分值**

### 7.5 建议的前后台分工

第三组主责：

- 信用分表结构
- 分值变动记录表
- 管理端查看与调整
- 审计日志
- 恢复规则

第一组消费：

- 匹配资格限制
- 用户自己的信用状态提示

第二组消费：

- 圈子互动资格限制
- 好友 / 联系方式解锁的风险限制

### 7.6 当前建议的上线顺序

1. 第三组先做最小版信用分模型和后台展示
2. 第一组接“低信用用户限制参与主匹配”的消费逻辑
3. 第二组后续再接圈子 / 好友 / 解锁场景的限制逻辑

这样不会一开始把三组都绑死在信用分上。

## 9. 一句话结论

如果要最清楚地说：

- 第一组是“恋爱交友匹配主线”
- 第二组是“圈子与关系链”
- 第三组是“论坛、治理和信用分”

信用分机制不是单独拆出去，而是归第三组主责，第一组和第二组按各自业务场景消费它。
