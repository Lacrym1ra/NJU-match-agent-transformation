# 校园社交组队与互助平台三组共建方案

我们计划开发一套面向大学生的校园社交组队与互助平台。课程总览中的“校园互助服务平台”我们理解为参考方向，因此我们希望在满足课程要求的前提下，将主题拓展为更完整的“校园社交组队与互助平台”，使其既符合课程要求，也能形成更清晰、可并行、可验收的三组分工。

本方案的核心目标，是把项目拆分成三条边界清楚、工作量相对均衡的开发线，让三个组共同完成同一个项目，而不是分别做三个彼此割裂的子项目。这样既能保证每组都接近课程总览中一组项目的工作量，也便于后续联调、答辩和统一演示。

---

## 一、系统需求描述

### 1.1 业务背景

校园社交、组队搭子、信息互助和内容交流需求分散在多个群聊和平台中，缺少统一入口，也缺少清晰的关系建立与治理机制。按照课程总览要求，项目需要覆盖用户管理、信息发布与浏览、推荐与流程管理、评价与信用、消息通知和管理后台等基本能力，并在此基础上形成可展示、可扩展的完整系统。

### 1.2 用户角色

| 角色 | 主要行为 | 主要诉求 |
|---|---|---|
| 普通学生 | 注册登录、填写资料、参与问卷、浏览内容、发帖互动 | 获取匹配、参与活动、建立联系 |
| 圈子成员/活跃用户 | 加入圈子、维护名片、申请好友、解锁联系方式、发起组队 | 深度互动、协作和关系维护 |
| 管理员/运营人员 | 审核内容、处理举报、发布公告、查看统计、执行维护 | 管理秩序、风控与运营支持 |

### 1.3 核心功能需求

1. 账号与身份管理：注册登录、个人资料、身份状态、参与开关。
2. 信息与推荐：问卷填写、匹配结果、揭晓、历史回看。
3. 社交与关系：匿名心意表达、双向意向确认、圈子、名片、好友、联系方式解锁。
4. 内容与交流：论坛发帖、评论、回复、活动组队。
5. 治理与安全：举报、拉黑、申诉、审核、审计、公告、维护模式、运营看板。
6. 通知与反馈：站内消息中心、邮件、系统提醒、处理结果通知。

### 1.4 非功能需求

| 维度 | 要求 |
|---|---|
| 性能 | 核心页面响应及时，常用操作路径尽量简洁，能支撑课堂演示场景 |
| 安全 | 密码加密、权限隔离、审计留痕、举报与拉黑可追踪 |
| 可用性 | 页面路径短、提示明确、移动端可用 |
| 可维护性 | 前后端分离、接口清晰、文档完整、便于三组并行开发 |

### 1.5 范围边界

- 以校内学生为主要用户，不做校外开放平台。
- 不引入复杂支付、电商或商家侧系统。
- 重点完成课程要求的核心链路与可展示的扩展功能。

## 二、项目定位

### 2.1 项目名称

建议项目对外名称定为：**校园社交与互助平台**。

### 2.2 项目目标

1. 覆盖课程总览中的主要功能要求，包括用户管理、信息发布与浏览、智能推荐与关系建立、流程管理、评价与信用、消息通知和管理后台。
2. 在基础功能之外，增加能体现完整度和展示度的扩展功能，例如匿名心意表达、双向意向确认、圈子社交、论坛交流和平台治理。
3. 形成前后端分离、接口清晰、模块独立、便于三组并行推进的项目结构。
4. 保证每个小组的工作内容都不仅是单一页面开发，而是包含需求、设计、前后端、数据库、联调和测试等完整环节。

### 2.3 与课程总览的对应关系

| 课程总览要求 | 本项目对应实现 |
|---|---|
| 用户管理 | 注册登录、个人资料、身份状态、参与开关 |
| 需求发布与浏览 | 圈子帖子、论坛求助帖、活动组队、心意表达入口 |
| 智能匹配与推荐 | 问卷推荐、圈内推荐、双向意向自动确认 |
| 订单流程管理 | 意向确认、联系方式交换、完成状态 |
| 评价与信用体系 | 评分、信用分、举报与申诉反馈 |
| 消息通知 | 站内消息中心、邮件、系统提醒、揭晓提醒 |
| 管理后台 | 审核、封禁、公告、审计、统计、维护模式 |

## 三、三组分工方案

快速阅读建议：

- 如果只是想快速确认“每组到底负责什么模块”，先看 `design_docs/GROUP_RESPONSIBILITIES.md`
- 本文更偏项目总方案、工作量和课程验收说明

### 3.0 三组分工总览

| 组别 | 主要职责 | 核心交付 | 对应课程要求 | 工作量目标 |
|---|---|---|---|---|
| 第一组：用户主线与互动建立组 | 账号、资料、问卷、推荐、揭晓、通知 | 注册登录、问卷、匹配结果、揭晓页、历史记录、消息中心、互动表达 | 用户管理、智能推荐与关系建立、消息通知 | 约 220-260 人时 |
| 第二组：圈子与关系链组 | 圈子、名片、好友、联系方式解锁、圈内互动 | 圈子列表、圈子详情、名片页、好友页、解锁申请页 | 需求发布与浏览、信息展示与权限控制、关系建立 | 约 220-260 人时 |
| 第三组：论坛与治理组 | 论坛、举报、拉黑、申诉、后台、看板 | 帖子列表、帖子详情、管理后台、举报处理、运营看板、公告/政策通知 | 评价与信用、管理后台、消息通知、可维护性与安全 | 约 220-260 人时 |

### 3.1 分工原则

为了让三个组的工作量大致平衡，我们不把功能简单切成“前端组、后端组、测试组”，而是按业务闭环拆成三条主线。每条主线都包含：需求梳理、页面设计、接口开发、数据库设计、联调测试和文档整理。

同时，三组之间要满足以下原则：

1. 每组都要有可独立演示的业务闭环。
2. 每组都要包含前端、后端和数据结构方面的工作。
3. 每组都要承担一定的测试和文档工作，避免只做功能开发。
4. 三组之间尽量减少强耦合，接口边界提前约定，避免后期返工。

### 3.2 第一组：用户主线与互动建立组

**组别定位：** 负责平台最核心的用户主线，确保“注册 - 资料 - 问卷 - 匹配 - 揭晓 - 反馈”这条主流程完整可用。

**主要任务：**

1. 用户注册、登录、找回、身份认证。
2. 个人资料、参与状态、问卷填写与版本管理。
3. 核心推荐逻辑、结果生成、锁定与揭晓机制。
4. 揭晓页、历史记录、站内消息中心、通知提醒与结果反馈。
5. 扩展功能：匿名心意表达、双向意向确认、未成功后的温和提示。

**建议功能拆分：**

- 前端页面：登录页、个人资料页、问卷页、推荐结果页、揭晓页、历史页、消息中心页。
- 后端接口：认证接口、问卷接口、匹配接口、揭晓接口、消息接口。
- 数据库：用户表、问卷答案表、推荐结果表、通知表、历史记录表。
- 测试：认证流程测试、问卷提交测试、推荐结果测试、揭晓流程测试。

**工作量目标：** 约 220-260 人时。

**本组亮点：**

- 匿名心意表达可以作为扩展功能，让系统从“等待匹配”提升到“带互动感的社交”。
- 双向意向确认可以增强产品特色，也能让演示更完整。
- 核心主线是全项目主线，本组应承担最关键的业务逻辑和验收标准。

### 3.3 第二组：圈子与关系链组

**组别定位：** 负责建立用户之间更稳定的弱关系和社交链路，让平台从“单次使用”扩展到“持续互动”。

**主要任务：**

1. 圈子发现、加入、退出、成员列表和频道页。
2. 名片系统、公开名片、好友名片、展示权限控制。
3. 好友申请、通过、拒绝、删除，以及关系链管理。
4. 联系方式解锁、权限申请和内容展示控制。
5. 圈内问卷、圈内推荐、活动组队和群组互动。
6. 圈子侧论坛入口接入，但不拥有论坛本体。

**建议功能拆分：**

- 前端页面：圈子列表页、圈子详情页、名片页、好友页、解锁申请页。
- 后端接口：圈子接口、好友接口、名片接口、联系方式解锁接口、圈内推荐接口。
- 数据库：圈子表、成员表、名片表、好友关系表、解锁申请表。
- 测试：加入/退出圈子测试、好友申请测试、名片权限测试、解锁流程测试。

**工作量目标：** 约 220-260 人时。

**本组亮点：**

- 圈子与好友系统可以把平台从“单次使用”延伸到“持续社交”。
- 名片与权限控制能体现隐私分层设计，也更容易展示系统设计能力。
- 圈内活动组队和圈内推荐，能够补足单一平台功能的使用场景。
- 圈子页给论坛导流后，用户会从“看圈子”自然进入“在圈子里发帖找人”。

### 3.4 第三组：论坛与治理组

**组别定位：** 负责平台的公共交流、管理治理和运营保障，让系统具备完整的可管理性和风控能力。

**主要任务：**

1. 论坛板块、发帖、评论、回复和软删除。
2. 举报、拉黑、申诉和处理结果反馈。
3. 管理后台、审核、封禁、解封、公告和审计日志。
4. 为站内消息中心提供治理类消息源，例如政策更新、系统公告、举报处理结果。
5. 维护模式、运营看板、统计分析和质量保障。
6. 平台风控与内容安全策略。
7. 圈子接入论坛：圈子专属帖流、圈子组队帖入口、`circleId` 维度的成员校验与管理。

**建议功能拆分：**

- 前端页面：论坛列表页、帖子详情页、管理后台页、举报处理页、运营看板页。
- 后端接口：论坛接口、举报接口、拉黑接口、申诉接口、管理接口、统计接口、治理类消息源接口。
- 数据库：帖子表、评论表、举报表、拉黑表、申诉表、审计日志表、统计表。
- 测试：发帖流程测试、评论流程测试、举报处理测试、后台操作测试、审计测试。

**工作量目标：** 约 220-260 人时。

**本组亮点：**

- 论坛系统能显著增加平台的日常使用频率，不只是一次互动完成后就结束。
- 治理能力、审计日志、维护模式和看板能力，能体现系统的工程完整性。
- 这一组的工作可以和课程的管理后台、安全和可维护性要求直接对应。

## 四、为什么这样分比较平衡

### 4.1 每组都有完整闭环

- 第一组有“登录 - 问卷 - 推荐 - 揭晓 - 反馈”的主闭环。
- 第二组有“加入 - 关系建立 - 权限控制 - 关系扩展”的社交闭环。
- 第三组有“发帖 - 互动 - 举报 - 处理 - 统计”的治理闭环。

### 4.2 每组工作内容都不轻

每组都包含：

1. 至少一个主要前端页面体系。
2. 至少一组后端 API。
3. 至少两到三张核心数据表。
4. 至少一部分联调与测试工作。
5. 至少一部分文档和答辩材料整理工作。

因此，三组不会出现一组太轻、另一组太重的情况。

### 4.3 便于并行开发

三条主线之间的依赖关系可以控制在接口层：

- 第一组先定义用户、问卷、推荐和通知接口。
- 第二组在用户身份和基础资料接口稳定后推进圈子和关系链。
- 第三组在统一身份和内容模型基础上推进论坛、治理和后台。

站内消息模块边界补充：

- 第一组负责消息中心页面本体、未读/已读状态和主匹配链路相关消息。
- 第三组负责公告、政策更新、举报处理结果等治理类消息源。
- 第二组后续如果接圈子事件提醒，也接入统一消息中心，不单独做第二套信箱。

这样三组可以并行推进，减少互相等待。

## 五、工作量评估

### 5.1 单组工作量

按课程总览，每个 4 人小组按 10 周推进，团队总工时约 240 人时，折算每人约 60 小时。三组并行推进时，整体合计约 720 人时，且每组工作量应保持接近，便于满足“一组一份完整大作业”的验收标准。

### 5.2 阶段工作量分配

| 阶段 | 周次 | 人均工时 | 团队总工时/组 | 主要交付 |
|---|---|---|---|---|
| P0 项目启动 | 第1周 | 6h | 24h | 团队章程、角色分工、AI 协作契约 |
| P1 需求分析 | 第2-3周 | 12h | 48h | 需求调研、需求说明书、用例、用户故事 |
| P2 架构设计 | 第4周 | 6h | 24h | 架构、接口边界、数据库设计 |
| P3 详细设计 | 第5周 | 6h | 24h | 页面原型、类图、API 明细 |
| P4 核心编码 | 第6-7周 | 12h | 48h | 核心模块开发、联调、测试 |
| P5 功能完善 | 第8周 | 6h | 24h | 扩展功能、体验优化、问题修复 |

## 六、建议的阶段推进节奏

### 第 1 阶段：项目启动与需求分析

- 完成组队、角色分工、AI 协作契约。
- 确定项目主题与最终范围。
- 完成需求调研、需求说明书、用例图和用户故事。
- 各组分别输出自己负责模块的需求范围。

### 第 2 阶段：架构与详细设计

- 确定整体架构、接口边界、数据库结构和权限模型。
- 三组分别完成自己模块的页面原型、接口定义和数据表设计。
- 明确哪些功能是 P0，哪些功能是扩展项。

### 第 3 阶段：核心开发

- 第一组优先完成注册、问卷、推荐和揭晓主链路。
- 第二组优先完成圈子、名片、好友和解锁闭环。
- 第三组优先完成论坛、举报、后台和审计闭环。

### 第 4 阶段：联调与补齐

- 三组统一联调接口，修正边界问题。
- 补齐异常流、提示文案和错误处理。
- 完成基础测试和回归测试。

### 第 5 阶段：质量保障与交付

- 完成性能检查、安全检查和可用性检查。
- 完成演示脚本、项目总结和答辩材料。
- 统一整理文档，保证提交材料结构清晰。

## 七、建议保留的扩展功能

为了让项目更有亮点，也为了让三组工作量更充足，我们建议保留以下扩展功能：

1. 匿名心意表达：用户可以向感兴趣的人发送匿名暗示。
2. 双向意向确认：双方互相表达兴趣后，系统自动进入下一步流程。
3. 圈内搭子推荐：在圈子内推荐更合适的同伴或活动对象。
4. 论坛与活动组队：补足日常交流和协作场景。
5. 审计与治理：保证管理后台和风控能力完整。

这些扩展功能不会改变课程要求的主结构，但可以明显提升项目完整度和展示效果。

---

## 八、课程验收层面的可行性说明

我们认为，这个三组方案是可行的，原因如下：

1. 主题虽然是自主确定的，但依然能完整对应课程总览的核心要求。
2. 三条主线的功能边界清楚，便于三组并行开发。
3. 每组的任务量都足够支撑一份完整课程大作业，而不是简单做几个小页面。
4. 项目可以在 10 周内按阶段推进，不需要无限扩大范围。
5. 扩展功能是“加分项”，不是“无限扩张项”，便于控制风险。

---

## 九、希望老师确认的事项

1. 是否同意我们将项目主题定为“校园社交与互助平台”。
2. 项目拆分为“用户主线与互动建立组、圈子与关系链组、论坛与治理组”三条主线，各组工作量是否足够。
3. 是否认可三组共同完成同一个项目、但各自承担独立模块和独立验收任务的组织方式。

我们会根据老师意见进一步收敛范围，并尽快推进需求分析、架构设计和开发排期。

---

## 十、简要结论

如果按课程总览要求来衡量，这个项目适合三组共同完成，但前提是主题要从零明确、功能要重新拆分、范围要控制在主线清晰、扩展适度的水平。我们建议采用“一个项目、三条主线、每组一条完整闭环”的方式推进，既满足课程要求，也能让三个组的工作量大致平衡。
