# 举报与拉黑功能设计文档

> 版本：v1.1 | 日期：2026-04-27

## 1. 文档定位

本文用于把“举报 / 拉黑 / 审核”能力从零散任务描述，整理成可直接开发和联调的单点设计文档。

适用组别：

| 组别 | 职责 |
|---|---|
| 第一组：用户主线与互动建立组 | 在揭晓页、历史记录页补用户侧入口与交互确认 |
| 第二组：圈子与关系链组 | 后续把拉黑规则扩展到圈子、好友、联系方式解锁等场景 |
| 第三组：论坛与治理组 | 主责后端规则、管理端举报处理、审计与后续处罚能力 |

权威边界：

- 当前已实现接口与表结构，以 `backend/src/routes/user.ts`、`backend/src/routes/admin.ts`、`backend/src/db/schema.ts` 为准。
- 当前和后续任务拆分，以 `design_docs/EXECUTABLE_TASKLIST_DEV_SAFE.md` 为准。
- 本文负责把“概念、流程、接口、状态、组间分工、验收标准”讲清楚。

## 2. 先统一概念

### 2.1 “已匹配排除”与“拉黑”不是一回事

| 机制 | 作用 | 生命周期 | 是否面向用户主动操作 |
|---|---|---|---|
| 已匹配排除 | 防止同一对用户重复进入后续匹配 | 系统规则 | 否 |
| 拉黑 | 用户主动建立跨场景隔离边界 | 长期有效，直到解除 | 是 |

结论：

- “已匹配排除”解决的是算法重复问题。
- “拉黑”解决的是安全、骚扰隔离与长期关系切断问题。
- 两者并行，不互相替代。

### 2.2 举报与拉黑的关系

- 举报：把问题提交给平台处理，需要管理员查看。
- 拉黑：用户立即把对方从自己的后续接触范围里隔离出去。
- 默认不强制“举报后自动拉黑”。
- UI 上可以在举报成功后提示“如需立即阻断对方，请同时拉黑”。

如果要做这些扩展，必须单独补 schema、接口和 migration。

## 4. 数据模型（按当前实现）

### 4.1 `user_blocks`

用途：记录 A 拉黑 B 的长期关系。

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `blocker_id` | 拉黑人 |
| `blocked_id` | 被拉黑人 |
| `created_at` | 创建时间 |

规则：

- `(blocker_id, blocked_id)` 唯一
- 重复拉黑是幂等操作
- 解除拉黑只删除该方向记录

### 4.2 `user_reports`

用途：记录举报工单。

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `reporter_id` | 举报人 |
| `reported_id` | 被举报人 |
| `reason` | 原因枚举 |
| `detail` | 补充说明 |
| `status` | `pending` / `reviewed` / `warn_update` / `dismissed` |
| `created_at` | 创建时间 |

说明：

- `reason` 在数据库中是 `TEXT NOT NULL`，当前由 `POST /api/v1/user/report/:targetId` 的 zod schema 负责枚举校验。
- `status` 在迁移 SQL 中需有 `pending` / `reviewed` / `warn_update` / `dismissed` 的 CHECK 约束（注意：`warn_update` 为完整的第四种状态，表示"已提醒被举报人更新资料"，与 `reviewed` 语义不同，不能合并）。

### 4.3 `audit_logs`

当前要求：

- 管理员处理举报时，必须写审计日志
- 至少记录：动作、目标工单、处理结果、IP、时间

## 5. 当前接口契约

### 5.1 用户侧接口

#### `POST /api/v1/user/block/:targetId`

用途：拉黑指定用户。

当前规则：

- 不能拉黑自己
- 目标用户必须存在
- 重复拉黑允许直接返回成功（幂等）

期望前端交互：

- 二次确认弹窗
- 文案明确说明：“拉黑后你们不会再进入后续匹配候选池，后续圈子等场景也将逐步隔离”

#### `DELETE /api/v1/user/block/:targetId`

用途：解除拉黑。

当前规则：

- 只删除当前用户发起的拉黑关系
- 解除后只影响未来，不恢复历史状态

#### `POST /api/v1/user/report/:targetId`

请求体：

```json
{
  "reason": "harassment",
  "detail": "多次私信骚扰"
}
```

当前 `reason` 枚举：

- `harassment`
- `spam`
- `fake_profile`
- `inappropriate_content`
- `other`

**举报频率限制（后端强制）：**

- 同一举报人对同一被举报人：7 天内最多提交 3 次举报；超出返回 429，提示"你近期已多次举报该用户，请等待处理结果"
- 同一举报人总举报数：24 小时内最多提交 10 次；超出返回 429，提示"举报过于频繁，请稍后再试"
- 信用分低于 40（高风险）的用户：每周最多发起 1 次举报（见 PLATFORM_GOVERNANCE_DESIGN.md 第 5.3 节）

交互要求：

- 举报提交成功后给出明确提示
- 不默认公开处理结果时间点
- 推荐提示用户：若需立即阻断，可再执行拉黑

### 5.2 管理侧接口

#### `GET /api/v1/admin/reports`

用途：按状态获取举报列表。

查询参数：

- `status=pending|reviewed|warn_update|dismissed|all`（需 zod 校验，非法值返回 400）
- `page`
- `limit`

**⚠️ 待修复**：当前后端对 `GET` 的 `status` 查询参数未做 zod 拦截，非法值不会报错而是静默返回空列表，属于已知输入验证漏洞。应补充 zod 校验：`status` 枚举仅允许 `pending / reviewed / warn_update / dismissed / all`，其他值返回 400。

#### `PATCH /api/v1/admin/reports/:id`

支持四种状态转移：

```json
{ “status”: “reviewed”,    “adminNote”: “属实，已通知双方” }
{ “status”: “warn_update”, “adminNote”: “提醒被举报人更新资料” }
{ “status”: “dismissed”,   “adminNote”: “举报内容属平台外行为，不受理” }
{ “status”: “pending” }
```

> `pending` 状态用于将已处理工单退回重审（需填写 `adminNote`）。

**状态语义说明：**

| status | 含义 | 对举报人的通知 | 对被举报人的通知 |
|---|---|---|---|
| `reviewed` | 举报属实，已受理处理 | 已受理 | 行为提醒 + 申诉入口 |
| `warn_update` | 资料疑似有误，已提醒更新 | 已处理 | 资料更新提醒 |
| `dismissed` | 举报暂未采纳 | 暂未采纳 | 不通知 |
| `pending` | 退回待处理（重审） | — | — |

**后端校验要求：**

- `status` 字段必须通过 zod 枚举校验（仅允许上述四种值），非法值返回 400
- `adminNote` 在 `status` 非 `pending` 时为可选；在 `status = pending`（退回重审）时为必填
- 状态更新为 `reviewed` 或 `warn_update` 时，自动触发向 `notifications` 表写入 `report_result` 消息（见 MESSAGE_CENTER_DESIGN.md 第 7.6 节）

注意：

- 当前审核接口只改 `status`
- 还没有处罚动作字段
- 也没有申诉字段

管理端前端本轮必须按”工单处理面板”来做，不要误做成”完整风控裁决系统”

## 6. 业务流程

### 6.1 用户侧拉黑流程

1. 用户在揭晓页或历史记录页点击“拉黑”
2. 前端弹出二次确认
3. 调用 `POST /api/v1/user/block/:targetId`
4. 成功后提示“已拉黑该用户”
5. 当前页面可立即隐藏继续互动入口，历史记录保留只读

### 6.2 用户侧举报流程

1. 用户点击“举报”
2. 前端打开举报弹窗
3. 用户选择原因枚举并填写补充说明
4. 调用 `POST /api/v1/user/report/:targetId`
5. 成功后提示“举报已提交，我们将尽快处理”

### 6.3 管理端处理流程

1. 管理员进入举报处理面板
2. 拉取 `GET /api/v1/admin/reports?status=pending`
3. 查看举报原因、补充说明、时间
4. 执行“已处理 / 驳回”
5. 调用 `PATCH /api/v1/admin/reports/:id`
6. 写入审计日志

## 7. 三组开发边界

### 7.1 第一组：用户侧入口与主链路联动

负责：

- Reveal 页的“拉黑 / 举报”按钮
- 历史记录页的“拉黑 / 举报”按钮
- 举报弹窗与确认交互
- 拉黑成功后的前台状态反馈

不负责：

- 举报列表查询
- 举报审核
- 处罚体系
- 申诉工单

### 7.2 第二组：后续社交链扩展

当前不作为本轮前置阻塞项，但后续要消费本规则：

- 拉黑后，好友申请入口需隐藏
- 拉黑后，联系方式解锁入口需隐藏
- 拉黑后，圈子推荐与成员可见性逐步收紧

第二组当前先按圈子主线推进，不等待处罚/申诉能力落地。

### 7.3 第三组：治理主责

负责：

- 举报处理面板
- 审核状态切换
- 审计日志
- 后续处罚 / 申诉扩展设计

当前面板必须做的内容：

- 举报列表
- 状态筛选
- 详情查看
- 审核操作

当前不要做重的内容：

- 复杂工单流转引擎
- 处罚等级持久化
- 申诉工作台

## 9. 验收标准

### 9.1 第一组验收

- Reveal / 历史记录页存在清晰入口
- 用户可以完成举报提交
- 用户可以完成拉黑和解除拉黑
- 成功 / 失败都有明确反馈

### 9.2 第三组验收

- Admin 可以看到 `pending/reviewed/dismissed` 举报
- Admin 可以完成 `reviewed` / `dismissed` 处理
- 处理后能在后端看到审计日志

### 9.3 联调验收

- 同一用户不能举报自己
- 同一用户不能拉黑自己
- 举报成功不自动拉黑
- 拉黑成功后，匹配候选排除规则在后续版本接入

## 10. 开工顺序建议

1. 第三组先确认管理端字段展示与审核操作
2. 第一组并行补用户侧入口和弹窗
3. 第一组 / 第三组联调举报提交流程
4. 第三组再补审核面板
5. 第一组最后补“拉黑后的前台状态反馈”

这样可以保证两组都不需要等待一张“大而全”的治理系统文档落地后才开工。
