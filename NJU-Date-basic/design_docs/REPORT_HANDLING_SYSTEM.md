# 举报处理系统设计文档

> 版本：v2.0 | 最后更新：2026-05-07
> 覆盖范围：用户侧提交、管理端处理、邮件通知、数据模型、API 契约

---

## 1. 系统概述

举报处理系统分为两个层面：

- **用户侧**：用户在揭晓页或历史记录页对配对对象发起举报，填写原因和补充说明。
- **管理端**：管理员在后台查看举报工单，选择处理方式，系统自动向相关用户发送邮件通知。

当前版本不自动封禁或拉黑账号，所有处置依赖管理员人工判断。

---

## 2. 数据模型

### 2.1 `user_reports` 表

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | TEXT PK | 举报工单 ID |
| `reporter_id` | TEXT | 举报人用户 ID |
| `reported_id` | TEXT | 被举报人用户 ID |
| `reason` | TEXT | 举报原因，逗号分隔的枚举值 |
| `detail` | TEXT | 用户补充说明（可为空） |
| `status` | TEXT | 工单状态，见下节 |
| `admin_note` | TEXT | 管理员备注（可为空，会包含在邮件中） |
| `created_at` | TIMESTAMP | 提交时间 |

### 2.2 举报原因枚举（`reason` 字段）

| 枚举值 | 中文说明 |
|---|---|
| `harassment` | 骚扰辱骂 |
| `spam` | 垃圾信息 |
| `fake_profile` | 虚假资料 |
| `inappropriate_content` | 不当内容 |
| `other` | 其他原因 |

用户可多选，存储为逗号分隔字符串，如 `"harassment,fake_profile"`。

### 2.3 工单状态枚举（`status` 字段）

| 状态值 | 中文 | 说明 |
|---|---|---|
| `pending` | 待处理 | 初始状态，等待管理员审核 |
| `reviewed` | 已标记属实 | 举报被采纳，已通知双方 |
| `warn_update` | 已发提醒 | 被举报人收到资料更新提醒，举报人收到处理通知 |
| `dismissed` | 已关闭 | 举报未被采纳，仅通知举报人 |

> **注意**：`request_evidence`（要求补充材料）不是持久状态，执行后工单保持 `pending`，只触发一封邮件。

## 3. 状态流转

```
                          ┌─────────────────────────────────┐
                          │          request_evidence        │
                          │  （状态不变，只发邮件给举报人）     │
                          └────────────┬────────────────────┘
                                       │
         ┌─────────────────────────────▼──────────────────────────────┐
         │                          pending                            │
         └──────────┬──────────────────┬──────────────────┬───────────┘
                    │                  │                  │
                    ▼                  ▼                  ▼
               reviewed           warn_update          dismissed
          （已标记属实）         （已发提醒）           （已关闭）
```

- 只有 `pending` 状态的工单可以被执行最终处置（`reviewed` / `warn_update` / `dismissed`）。
- `reviewed` / `warn_update` / `dismissed` 为终态，不可再次变更（避免重复通知用户）。
- `request_evidence` 可在 `pending` 状态下多次执行。

## 4. 管理端处理操作

管理员处理举报时有四种操作，每种操作的邮件通知对象和状态变更如下：

| 操作 | 状态变更 | 通知举报人 | 通知被举报人 | 管理员备注是否发送 |
|---|---|---|---|---|
| **标记属实** | `pending` → `reviewed` | ✅ 受理通知 | ✅ 行为提醒 + 申诉邮箱 | ✅ 包含在被举报人邮件中 |
| **提醒更新资料** | `pending` → `warn_update` | ✅ 处理通知 | ✅ 资料更新提醒 + 更新按钮 | ✅ 包含在被举报人邮件中 |
| **要求补充材料** | 不变（仍为 `pending`） | ✅ 补充材料请求邮件 | ❌ | ✅ 包含在举报人邮件中 |
| **关闭举报** | `pending` → `dismissed` | ✅ 关闭通知 | ❌ | — |

### 4.1 管理员备注（`adminNote`）

- 可选字段，最长 500 字。
- 对于"标记属实"和"提醒更新资料"：备注附加在**被举报人**的邮件正文中。
- 对于"要求补充材料"：备注附加在**举报人**的邮件中（说明需要提供什么材料）。
- 备注同时写入 `user_reports.admin_note` 字段持久保存。

## 5. 邮件通知详情

支持邮箱：`njumatch@163.com`

### 5.1 举报人收到的邮件

#### 标记属实 / 提醒更新资料 / 关闭举报（最终处置通知）

| 场景 | 邮件标题 | 核心内容 |
|---|---|---|
| `reviewed` | 举报已被受理 | 举报已标记属实，已向相关用户发送提醒；出于隐私原因不公开处置细节 |
| `warn_update` | 反馈已处理 | 已向对方发送资料更新提醒，感谢维护社区信息准确性 |
| `dismissed` | 举报已关闭 | 暂未采纳，可能是证据不足或暂不构成处置条件 |

#### 要求补充材料

- **标题**：举报跟进 — 请补充材料
- **核心内容**：请将截图/聊天记录等发送至 `njumatch@163.com`，邮件主题注明"举报 {ID} 补充材料"，72 小时内提交
- **按钮**：发送证明材料（`mailto:` 链接，主题自动填入）
- **管理员备注**（如有）：附在正文中，说明需要提供什么类型的材料

### 5.2 被举报人收到的邮件

#### 标记属实（行为提醒）

- **标题**：社区行为提醒
- **核心内容**：收到与账号相关的举报并已审核属实，请检查资料和互动方式；提供申诉邮箱
- **管理员备注**（如有）：附在正文中

#### 提醒更新资料

- **标题**：资料更新提醒
- **核心内容**：联系方式等资料可能存在错误或过期，请登录平台在「个人设置」中更新
- **按钮**：立即更新资料（跳转设置页）
- **管理员备注**（如有）：附在正文中（如"你的 QQ 号填写有误"）

## 6. API 契约

### 6.1 用户侧

#### `POST /api/v1/user/report/:targetId`

提交举报。

**请求体：**
```json
{
  "reason": "harassment,fake_profile",
  "detail": "对方 QQ 号不存在，疑似虚假信息"
}
```

**规则：**
- 不能举报自己
- `reason` 必须是合法枚举值，多选用逗号分隔
- `detail` 可为空
- 同一用户对同一被举报人重复举报：当前允许，后端不做去重（由管理员合并判断）

---

### 6.2 管理侧

#### `GET /api/v1/admin/reports`

获取举报列表，附带举报人和被举报人的资料摘要。

**查询参数：**

| 参数 | 类型 | 说明 |
|---|---|---|
| `status` | string | `pending` / `reviewed` / `warn_update` / `dismissed` / `all` |
| `page` | number | 页码，默认 1 |
| `limit` | number | 每页数量，默认 20，最大 100 |

**响应结构：**
```json
{
  "reports": [
    {
      "id": "...",
      "reporterId": "...",
      "reportedId": "...",
      "reason": "fake_profile",
      "detail": "...",
      "status": "pending",
      "adminNote": null,
      "createdAt": "...",
      "reporter": { "email": "...", "nickname": "...", ... },
      "reported": { "email": "...", "nickname": "...", ... }
    }
  ],
  "total": 42,
  "page": 1,
  "limit": 20
}
```

---

#### `PATCH /api/v1/admin/reports/:id`

处理举报。

**请求体：**
```json
{
  "status": "reviewed" | "warn_update" | "dismissed" | "request_evidence",
  "adminNote": "可选备注，最长 500 字"
}
```

**行为说明：**

- `reviewed` / `warn_update` / `dismissed`：将工单状态更新为对应值，触发邮件通知，写入审计日志。只能对 `pending` 状态的工单执行，重复操作返回 400。
- `request_evidence`：不改变工单状态，只向举报人发送补充材料请求邮件，写入审计日志。可对 `pending` 工单多次执行。

**响应结构：**
```json
{
  "message": "举报状态已更新，通知邮件已按规则发送",
  "report": { ... },
  "notifications": {
    "reporter": "sent" | "skipped" | "failed",
    "reported": "sent" | "skipped" | "failed"
  }
}
```

---

#### `GET /api/v1/admin/users/:id`

获取指定用户的完整资料（含问卷答案和近期匹配记录），用于在举报详情面板中展开被举报人信息。

## 7. 审计日志

每次管理员操作均写入 `audit_logs`，记录字段：

| 字段 | 内容 |
|---|---|
| `action` | `review_report` 或 `request_evidence` |
| `target` | 举报工单 ID |
| `detail` | `{ status, adminNote }` |
| `ip` | 管理员 IP |
| `createdAt` | 操作时间 |

## 8. 管理端 UI 说明

### 8.1 举报列表

- 按状态筛选（待处理 / 已标记属实 / 已发提醒 / 已关闭 / 全部）
- 每行显示：举报 ID、举报人 ID、被举报人 ID、原因、说明摘要、状态徽章、提交时间、"处理"按钮
- "处理"按钮仅对 `pending` 状态激活

### 8.2 举报详情面板

点击"详情"按钮弹出，展示：
- 举报 ID、时间
- 举报人 / 被举报人 ID 及资料摘要
- 举报原因（中文展示）
- 完整补充说明
- 被举报人完整资料（按需加载，含问卷答案和匹配记录）
- 已有管理员备注（蓝色提示框）
- 若状态为 `pending`：入口按钮跳转到处理弹窗

### 8.3 处理弹窗（Action Modal）

包含：
1. **处理方式单选**：四种操作，"要求补充材料"标注"状态不变"蓝色标签
2. **管理员备注输入框**：最长 500 字，说明会出现在邮件中
3. **邮件预览**：切换举报人 / 被举报人两个视角实时预览邮件内容
4. **确认按钮**：`request_evidence` 显示"发送请求邮件"，其他显示"确认处理"

### 8.4 邮件模板预览（可折叠）

页面底部可展开查看所有场景的邮件模板，含管理员备注占位示例。

## 9. 当前未实现的能力（后续扩展）

以下能力已预留设计空间，但当前版本不包含：

| 能力 | 说明 |
|---|---|
| 处罚等级持久化 | `warning / suspend_7d / ban_permanent` 尚未入表 |
| 申诉工单 | 申诉流转和申诉工作台尚未设计 |
| 举报证据附件上传 | 当前以邮件方式收集，无平台内上传功能 |
| 举报去重 / 合并 | 同一被举报人的多条举报需要管理员人工判断 |
| 自动处罚触发 | 达到一定举报次数后自动进入限制状态 |
| 拉黑与举报联动 | 举报成功后提示用户"可同时拉黑" |
