## 2. 用户安全工具

### 2.1 拉黑（Block）

用户主动发起，立即生效，长期有效。

**已实现：**
- `POST /api/v1/user/block/:targetId`
- `DELETE /api/v1/user/block/:targetId`

**拉黑效果（当前 vs 完整）：**

| 场景 | 当前状态 | 完整设计 |
|---|---|---|
| 匹配候选排除 | ✅ 已接入 | — |
| 揭晓页 / 历史记录互动入口隐藏 | 部分实现 | 完全隐藏所有互动按钮 |
| 圈子互相不可见 | ❌ 未实现 | 双向隐藏帖子和回复 |
| 联系方式解锁拦截 | ❌ 未实现 | 拦截解锁请求 |
| 组队申请拦截 | ❌ 未实现 | 拦截组队申请 |

**设计原则：**
- 拉黑是双向静默的：A 拉黑 B，B 看不到 A 的任何互动行为（但 B 不收到通知）
- 拉黑不公开展示（不像微博有"被屏蔽"提示）
- 解除拉黑只影响未来，不恢复历史消息

## 3. 举报工单系统

### 3.1 举报流程

```
用户发起举报
    │
    ▼
提交工单（status = pending）
    │
    ├──▶ [管理员] 要求补充材料 ──▶ 举报人发送材料至邮箱 ──▶ 工单仍为 pending
    │
    ├──▶ [管理员] 标记属实（reviewed）
    │       │
    │       ├──▶ 通知举报人：已受理
    │       ├──▶ 通知被举报人：行为提醒 + 申诉入口
    │       └──▶ 触发处罚评估（见第 4 节）
    │
    ├──▶ [管理员] 提醒更新资料（warn_update）
    │       │
    │       ├──▶ 通知举报人：已处理
    │       └──▶ 通知被举报人：资料更新提醒
    │
    └──▶ [管理员] 关闭举报（dismissed）
            │
            └──▶ 通知举报人：暂未采纳
```

### 3.2 举报类型与优先级

| 类型 | 枚举值 | 优先级 | 说明 |
|---|---|---|---|
| 骚扰辱骂 | `harassment` | P0 | 包含人身威胁时立即升级 |
| 虚假资料 | `fake_profile` | P1 | 联系方式错误、照片不符 |
| 不当内容 | `inappropriate_content` | P1 | 涉黄、涉暴 |
| 垃圾信息 | `spam` | P2 | 广告、引流 |
| 其他 | `other` | P2 | 人工分类 |

### 3.3 SLA 目标（参考）

| 优先级 | 首次响应 | 处理完成 |
|---|---|---|
| P0 | 4 小时内 | 24 小时内 |
| P1 | 24 小时内 | 72 小时内 |
| P2 | 72 小时内 | 7 天内 |

### 3.4 重复举报与合并

- 同一举报人对同一被举报人：当前允许多次提交，管理员人工合并判断
- **完整设计**：7 天内同一对用户的举报合并至同一工单，超期后开新工单；被举报人被不同举报人举报 3 次以上时，自动提升优先级并推送告警

## 4. 处罚体系

### 4.1 处罚等级

| 等级 | 名称 | 措施 | 触发条件（参考） |
|---|---|---|---|
| L0 | 提醒 | 发送资料更新提醒邮件，不影响功能 | 联系方式等信息疑似有误 |
| L1 | 警告 | 写入违规记录，发送警告邮件，功能不受限 | 首次轻微违规（如发送不当内容） |
| L2 | 功能限制 | 暂停参与匹配（N 周），不能发起组队 | 重复轻微违规 / 单次中度违规 |
| L3 | 临时封禁 | 账号 7 天内可登录但无法进行任何核心操作（匹配、发帖、组队、解锁联系方式），登录后展示封禁原因和解除时间 | 严重骚扰 / 多次违规 |
| L4 | 永久封禁 | 账号永久停用，邮箱加入黑名单 | 极端违规 / 多次封禁后复犯 |

**重要原则：**
- 当前版本（L0 已实现，L1–L4 未实现）
- 处罚不自动触发，由管理员在审核举报后人工选择
- 同一账号累计违规记录，等级可逐步提升
- 永久封禁需采用**冷静期机制**：管理员提交永久封禁后，操作进入 `pending_ban` 状态，24 小时后自动生效；期间管理员可撤回（需填写撤回原因并记录审计日志）；生效后不可撤销，只能通过申诉流程处理
- 当前单人运营阶段：冷静期机制同样生效；24 小时内若无撤回则自动确认，同时将封禁原因强制写入审计日志（不允许跳过）

### 4.2 处罚累计规则

参考抖音的"积分清零"机制：

```
举报属实 +1 分 → 违规分累计

分数区间  → 处罚
1 分       → L1 警告
3 分       → L2 功能限制（暂停匹配 2 周）
5 分       → L3 临时封禁 7 天
7 分       → L4 永久封禁
```

- 每自然季度末，违规分 ≥1 且 <5 的账号自动清零（给予改正机会）
- 违规分 ≥5 的账号不参与季度清零，但 L3 封禁执行完毕后，如无新违规，违规分在下一季度末自动降至 3 分（保留警戒状态，但给予改正机会；下次违规属实才重新触发 L3）
- 永久封禁（违规分 ≥7 或管理员直接执行）不参与任何清零，也不衰减

**当前状态：** 此规则尚未实现，违规分未入表。

### 4.3 违规记录（数据模型设计）

需要新增 `user_violations` 表：

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `user_id` | 被处罚用户 |
| `report_id` | 关联举报工单（可为空，如系统直接发现） |
| `level` | `warn` / `restrict` / `suspend_7d` / `ban` |
| `reason` | 处罚原因文本 |
| `penalty_detail` | 具体限制内容（JSON） |
| `starts_at` | 生效时间 |
| `ends_at` | 解除时间（null = 永久） |
| `admin_id` | 操作管理员 |
| `created_at` | 记录时间 |
| `is_voided` | 是否已被申诉撤销（默认 false） |
| `voided_at` | 申诉撤销时间 |

**当前状态：** 此表尚未创建。

## 5. 信用体系

### 5.1 设计目标

用一个综合分衡量用户在平台的行为质量，影响：
- 匹配优先级
- 功能权限
- 限制阈值

### 5.2 信用分模型（参考设计）

初始分：100 分

| 行为 | 分数变化 |
|---|---|
| 举报被标记属实（被举报） | -10 |
| 被举报被关闭（举报人恶意举报） | 举报人 -3 |
| 主动完善资料 | +2（每次，上限 +10）|
| 问卷完成率高、更新及时 | 维持正分 |
| 临时封禁解除 | 不自动恢复，需申诉 |

### 5.3 风险等级

| 信用分 | 风险等级 | 影响 |
|---|---|---|
| 80–100 | 正常 | 无限制 |
| 60–79 | 低风险 | 管理端标记，优先审核其举报 |
| 40–59 | 中风险 | 限制每周最多发起 1 次举报 |
| <40 | 高风险 | 功能限制，等待管理员评估 |

**当前状态：** 信用体系整体未实现，`users` 表无信用分字段。

> **实现建议：** 违规分（第4.2节）与信用分当前是两套独立体系，维护成本高且规则可能产生冲突。建议落地时将两者合并为单一信用分（初始 100，违规减分，正向行为加分），违规分累计阈值直接映射到信用分区间。只有当信用体系需要更精细的"行为正向激励"维度时，才单独保留信用分字段。**在多管理员 RBAC 落地前不建议实现此体系。**

## 6. 申诉机制

### 6.1 申诉流程

```
被举报人收到处罚通知
    │
    ▼
向支持邮箱发送申诉（当前方式）
    │        或
    ▼
平台内提交申诉工单（完整设计，未实现）
    │
    ▼
管理员收到申诉，关联原举报工单
    │
    ├──▶ 申诉成立：撤销处罚，通知申诉人
    └──▶ 申诉不成立：维持处罚，通知申诉人
```

### 6.2 申诉规则

- 每次处罚只能申诉一次
- 申诉期限：处罚通知发出后 7 天内
- 永久封禁的申诉需更高级管理员复核

### 6.3 申诉与违规分/处罚的联动规则

申诉成立（`approved`）时，后端需执行以下操作：

1. 将关联的 `user_violations` 记录标记为 `voided`（不删除，保留审计）
2. 违规分回滚：将该次违规属实所加的分数从当前违规分中扣除（不低于 0）
3. 如处罚等级为 L2/L3，立即解除对应的功能限制 / 封禁
4. 如处罚已自然到期，违规分仍需回滚，处罚状态无需再更新
5. 向申诉人发送"申诉成立"通知，说明已撤销的处罚和恢复的分数

申诉不成立（`rejected`）时：

1. 维持原处罚
2. 通知申诉人说明原因
3. 不影响违规分

### 6.3 申诉数据模型（设计）

需要新增 `user_appeals` 表：

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `user_id` | 申诉人 |
| `violation_id` | 关联违规记录 |
| `report_id` | 关联举报工单（可为空） |
| `reason` | 申诉理由 |
| `evidence_urls` | 证明材料链接（JSON 数组） |
| `status` | `pending` / `approved` / `rejected` |
| `admin_note` | 复核说明 |
| `resolved_at` | 处理时间 |
| `created_at` | 提交时间 |

**当前状态：** 此表尚未创建，申诉通过邮件人工处理。

## 7. 账号状态管理

### 7.1 账号状态枚举

```
active          → 正常
restricted      → 功能受限（如暂停匹配）
suspended_temp  → 临时封禁（无法登录）
banned          → 永久封禁
deleted         → 已注销（PII 脱敏）
```

**当前状态：** `users` 表无 `account_status` 字段，只有 `is_participating`（影响匹配参与）。封禁能力未实现。

### 7.2 封禁行为规范

- 临时封禁（`suspended_temp`）：账号可以登录，登录后展示封禁原因和解除时间，但所有核心操作（匹配参与、发帖评论、组队、联系方式解锁）返回 403 并提示封禁状态；邮件同步通知封禁原因和申诉入口
- 永久封禁（`banned`）：登录接口直接返回 403，提示"账号已被永久停用，如有异议请联系申诉"
- 被封禁账号的邮箱加入黑名单，防止重新注册

## 10. 建议落地顺序

### 近期优先（影响用户安全，成本低）

1. **被举报次数显示**：在管理端用户详情中加一行"历史被举报属实次数"，纯查询，无需 schema 变更
2. **`user_violations` 表 + 违规记录写入**：每次"标记属实"后，管理员可选择同时执行处罚等级（L1/L2/L3）
3. **账号状态字段**：`users.account_status`，实现 L3 临时封禁（登录接口加校验）

### 中期（完善治理闭环）

4. **申诉工单**：`user_appeals` 表 + 管理端申诉处理面板
5. **举报合并 / 优先级自动提升**：被不同用户举报 3 次自动高亮告警

### 长期（可选）

6. **信用分体系**
7. **RBAC 多管理员**（见 ADMIN_PERMISSION_MODEL.md）
8. **平台内附件上传**

## 11. 典型案例参考

积累真实处理案例，供后续管理员判断参考。

### 案例 A：配对后在外部平台被删好友（2026-05-07）

**举报原因：** 其他原因

**补充说明：** "过了四天之后才加微信，我这边秒通过，通过微信还不讲话，20分钟左右我问候一下，发现我被删好友了。不明白他这是什么操作。"
