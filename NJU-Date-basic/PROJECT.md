## 1. 项目愿景与核心理念

### 1.1 我们要解决什么问题？

南大学生的社交痛点：

- **信息茧房**：同专业、同实验室内社交圈子高度固化，跨院系几乎没有自然认识的机会
- **社交压力**：主动搭讪的心理门槛太高；传统表白墙公开度过高，隐私无保障
- **低质匹配**：市面交友软件以"颜值筛选 + 无限滑动"为核心，浮于表面

### 1.2 我们的答案

| 原则 | 做法 |
|------|------|
| **慢社交** | 以"周"为单位，每周三晚 20:00 只推送一位匹配对象，制造期待感 |
| **深度优先** | 用 60 道灵魂问卷替代照片海选，算法基于三观、生活方式、情感偏好做深层匹配 |
| **隐私至上** | 不公开个人主页，联系方式只在双向同意后才展示 |
| **仪式感** | 拆信封、揭晓动画、AI 策展人寄语，让每次匹配都像收到一封手写信 |
| **校园专属** | 严格限制 `@smail.nju.edu.cn` 邮箱认证，杜绝校外人员 |

### 1.3 与竞品的区别

| 维度 | 传统交友软件 | 表白墙 | NJU Match |
|------|-------------|--------|----------|
| 匹配机制 | 照片滑动 | 人工投稿 | 算法深度匹配 |
| 频率 | 无限制 | 随机 | 每周一次 |
| 隐私 | 公开资料 | 半公开 | 完全私密 |
| 校园限定 | 否 | 是 | 是 |
| 科学性 | 低 | 无 | Gale-Shapley 稳定匹配 |

### 2.3 每周时间轴

| 时间 | 事件 | 系统行为 |
|------|------|---------|
| 周二 18:00 | 常规问卷提醒 | 向未完成问卷的用户发送主提醒，并向问卷版本过旧的用户发送更新提醒 |
| 周三 12:00 | 新注册补提醒 | 仅向周二新注册且仍未完成问卷的用户补发提醒 |
| 周三 18:00 | 匹配锁定与计算 | 锁定问卷提交和参与状态变更；Cron 触发匹配管线，写入 `matches(status=LOCKED)` |
| 周三 20:00 | 锦书揭晓 | Cron 批量更新 `LOCKED → REVEALED`，向开启通知的用户推送揭晓邮件 |
| 周三 20:00 ~ 周五 20:00 | 决策窗口 | 用户可查看匹配报告，做出“愿见 / 止步”选择 |
| 周五 12:00 | 到期提醒 | 向仍未回应的用户发送“今晚到期”提醒邮件 |
| 周五 20:00 | 超时过期 | Cron 将未完成回应的 `REVEALED → EXPIRED`，并自动暂停未回应用户 |
| 每天 12:00 | 永久休眠检查 | 对自动暂停满 7 天且仍未恢复参与的用户发送休眠通知 |

### 2.4 锦书揭晓状态对照

| 阶段 | 北京时间 | 数据状态 | `GET /match/current` | Dashboard 展示 | Reveal 页 / 是否可操作 |
|------|----------|----------|----------------------|----------------|------------------------|
| 揭晓前，尚无本周匹配记录 | 周三 20:00 前 | 无记录 | `WAITING` | 大倒计时 | 不可进入 |
| 已完成匹配但尚未揭晓 | 周三 18:00 ~ 20:00 | `LOCKED` | `PENDING` | 大倒计时 | 不可进入 |
| 本周未匹配到 | 周三 20:00 后至周五 20:00 前 | 无记录 | `NO_MATCH` | 显示“本周暂无锦书”与下周倒计时 | 不可进入 |
| 揭晓后待选择 / 已选择但仍在窗口内 | 周三 20:00 ~ 周五 20:00 | `REVEALED` / `MUTUAL` / `MISSED` | `REVEALED` | 显示“揭开火漆”入口 | 可进入；根据 `/match/result/:matchId` 展示等待、双向奔赴或止步 |
| 48 小时窗口结束 | 周五 20:00 后 | `EXPIRED` | `EXPIRED` | 回到大倒计时，不再显示揭晓入口 | 可展示归档内容，但不可再点“愿见 / 止步” |

说明：
- `Dashboard` 只在周三 `20:00` 到周五 `20:00` 的揭晓窗口内，为 `REVEALED` 状态展示“揭开火漆”入口。
- `MUTUAL` / `MISSED` 的详细结果通过 `GET /match/result/:matchId` 查询；`GET /match/current` 仍维持揭晓态，便于用户在窗口内回看同一期锦书。

### 4.2 硬约束过滤 (Dealbreaker Filter)

在计算分数之前，先用硬性条件淘汰不可能的配对，减少计算量：

| 过滤条件 | 规则 |
|---------|------|
| 性别偏好不匹配 | A 不接受 B 的性别，或 B 不接受 A 的性别 → 淘汰 |
| 恋爱目标冲突 | 一方选"长期关系"、另一方选"短期关系" → 淘汰 |
| 出生年份超限 | 超出对方设定的可接受年龄范围 → 淘汰 |
| 校区限制 | 对方要求同校区但分属不同校区 → 淘汰 |
| 核心价值观极端分歧 | 任一方对关键题目标记"极其重要"(权重=3)且双方分差 ≥ 5 → 淘汰 |

涉及的核心题目编号：q19, q20, q34, q35, q42, q45

### 4.3 兼容性评分公式

#### Likert 量表题 (1-7分)

```
单题惩罚值:
  Penalty_i(A→B) = Weight_A_i × |Answer_A_i - Answer_B_i|

  其中 Weight = 用户标记的重要性 (1=一般, 2=重要, 3=极其重要)

单向兼容度:
  Compat(A→B) = 1 - (ΣPenalty_i / MaxPossiblePenalty_A)

最终兼容分:
  Score(A,B) = (Compat(A→B) + Compat(B→A)) / 2
```

**设计理念**：兼容性是"不对称"的。A 觉得某个问题很重要但 B 不在意，那么 A→B 的兼容度会因此受影响，但 B→A 不会。取双向平均确保公平。

#### 其他题型评分

| 题型 | 计算方式 |
|------|---------|
| 多选题 | Jaccard 相似度 = |A∩B| / |A∪B| |
| 排序题 | Spearman 秩相关系数，归一化到 [0,1] |
| 分类题 | 精确匹配 = 1，不匹配 = 0 |
| MBTI | 兼容类型对照表加分 |

#### 维度权重

| 维度 | 包含题目 | 权重 | 理由 |
|------|---------|------|------|
| 价值观 (Values) | q15–q24 | 2.0 | 三观一致是长期关系的基石 |
| 情感沟通 (Emotional) | q38–q46 | 1.8 | 沟通方式决定关系质量 |
| 生活方式 (Lifestyle) | q25–q37 | 1.6 | 日常习惯的兼容性 |
| 吸引力 (Attraction) | q47–q52 | 1.2 | 重要但非决定性 |

最终总分 = 各维度加权平均，归一化至 [0, 1]

### 4.4 Gale-Shapley 稳定匹配算法

**为什么选这个算法？**

Gale-Shapley（延迟接受算法）解决的是"稳定婚姻问题"：在所有可能的 1:1 配对方案中，找到一个"稳定"的方案——即不存在两个人都更喜欢彼此胜过各自当前的匹配对象。

**算法流程：**

```
输入:
  提议方群组 A (例如: 所有男生)
  接收方群组 B (例如: 所有女生)
  每对 (a,b) 的兼容性分数

Step 1: 构建偏好列表
  每个 a ∈ A 按兼容性分数降序排列 B 中所有可行对象
  每个 b ∈ B 按兼容性分数降序排列 A 中所有可行对象

Step 2: 迭代匹配
  while 存在未匹配的 a 且 a 还有未提议的对象:
    a 向偏好列表中排名最高的未提议过的 b 提议
    if b 当前空闲:
      b 暂时接受 a
    else if b 更喜欢 a 胜过当前对象 a':
      b 接受 a，释放 a' (a' 重新变为未匹配)
    else:
      b 拒绝 a

Step 3: 输出所有稳定配对
```

**关键性质：**
- 算法一定终止（每个提议最多被拒绝 n-1 次）
- 结果一定是稳定的（没有"阻塞对"）
- 对于 A→B / B→A 的非对称偏好池，结果对提议方最优

### 4.5 AI 策展人寄语

匹配完成后，系统调用通义千问 (Qwen) API（通过 DashScope OpenAI 兼容接口）为每对匹配生成一段个性化的"策展人寄语"(Curator's Note)。

**输入**：双方的问卷答案（脱敏处理）
**输出**：一段温暖、有洞察力的文字，包含：
- 双方意想不到的共同偏好
- 性格上的互补之处
- 共同的稀有选择

**示例**：
> "你们都不约而同地选择了'独立书店'作为理想的周末放松方式——更巧的是，你们对亲密关系中的边界感持有几乎一致的看法。一个喜欢倾听，一个善于表达，这或许正是最好的搭配。"

## 5. 问卷体系设计

### 5.1 题库结构

60 道题目，分为 6 个章节，覆盖从硬性条件到灵魂深处：

| 章节 | 题号 | 主题 | 题型 | 用途 |
|------|------|------|------|------|
| 基础信息 | q1–q13 | 性别、年龄、校区、身高等 | 单选/数值 | 硬约束过滤 |
| 价值三观 | q14–q24 | MBTI、人生哲学、核心观念 | Likert 1-7 + 重要性 | 核心匹配维度 |
| 生活方式 | q25–q37 | 娱乐偏好、社交风格、消费观 | Likert + 多选 | 日常兼容性 |
| 情感沟通 | q38–q46 | 沟通风格、冲突处理、情感需求 | Likert + 重要性 | 关系质量预测 |
| 吸引力 | q47–q52 | 外貌偏好、浪漫表达、理想约会 | 多选/排序 | 化学反应评估 |
| 开放杂项 | q53–q60 | 爱的语言排序、核心价值多选、自定义底线 | 排序/多选/开放 | 个性化补充 |

### 5.2 重要性权重机制

对于 Likert 类题目，用户在回答分数的同时，需要标记该题对自己的重要程度：

- **权重 1** (一般)：有偏好但不是决定性因素
- **权重 2** (重要)：对关系有显著影响
- **权重 3** (极其重要)：不可妥协的核心价值

这个机制确保算法尊重每个人独特的优先级。同样回答"5分"的两个人，如果一个标记权重3、另一个标记权重1，对匹配结果的影响截然不同。

### 6.1 设计理念：东方美学 × 数字策展

NJU Match 的前端不是一个"控制面板"，而是一间**数字画廊**。

| 无边框法则 | 禁止 `1px solid` 硬边框，用背景色阶差和留白分割区域 |
| 毛玻璃美学 | 导航栏/浮层采用 `backdrop-blur(12px)` 半透明效果 |
| 衬线+无衬线 | 标题用 Noto Serif SC（诗意），正文用 Inter/PingFang SC（清晰） |

```
6. 底部呈现两个按钮：
   【愿见】（优雅金色）  【止步】（温柔灰色）
```

## 7. 安全与隐私策略

### 7.1 认证安全

| 措施 | 实现 |
|------|------|
| 校园邮箱限定 | 前后端双重正则：`*@smail.nju.edu.cn` |
| OTP 限流 | 同一邮箱 60秒内仅1次，10分钟内8次失败 → 封禁15分钟 |
| OTP 单次有效 | 验证成功后立即从数据库删除 |
| JWT 无状态 | 服务端不存储 session，Token 含 userId，密钥签名 |

### 7.2 数据隐私

| 原则 | 做法 |
|------|------|
| 微信号保护 | `wechatId` 仅在双方 ACCEPT 后通过 API 返回，平时不可见 |
| 无公开主页 | 用户资料仅匹配对象可见，不存在浏览/搜索功能 |
| 最小化暴露 | GET /profile 永远不返回 wechatId，即使是自己的 |
| 问卷答案保密 | 原始答案不对匹配对象公开，仅用于算法计算 |

### 7.3 API 安全

| 层面 | 技术 |
|------|------|
| HTTP 加固 | Helmet.js 设置安全响应头 |
| CORS 白名单 | 仅允许指定前端域名 |
| SQL 注入防护 | Drizzle ORM 参数化查询 |
| XSS 防护 | 纯 JSON API，不返回 HTML |
| 全局限流 | express-rate-limit 保护所有端点 |
